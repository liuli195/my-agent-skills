# Development Flow（开发流程）

## Purpose

提供独立于旧 Pi 开发流程的纯 Skill（技能）编排，在调用时的非 main 功能分支和同一工作树中，以固定流程工具完成需求、串行实施、验证、审查、正式规格及 PR（拉取请求）交付，同时让每项变更自行绑定目标产品的真实用户入口。

## Requirements

### Requirement: 通用开发流程入口与固定工具链

系统 MUST 通过独立的 `dev-flow` Skill（技能）固定编排子代理策略、需求设计与建模、TDD（测试驱动开发）、Build and Verify（构建与验证）、代码审查、MySpec（自有规格）及 PR Flow（拉取请求流程），并在写入前证明当前目录是干净、已登记且位于具名非 `main` 功能分支的 Git（版本管理）工作树。

#### Scenario: 从有效功能工作树开始开发

- **WHEN** 用户在干净、已登记且位于具名非 `main` 功能分支的工作树调用 `dev-flow`，且当前阶段所需流程工具可用
- **THEN** 流程在该工作树和分支进入需求阶段，不创建或切换开发工作树或功能分支

#### Scenario: 开发前提不能证明

- **WHEN** 当前分支是 `main`、处于分离状态、工作树无法证明、工作区不干净、策略无法证明或当前阶段所需流程工具缺失
- **THEN** 流程在任何写入、可写委派或正式确认前明确停止
### Requirement: 目标产品真实入口驱动实施与验证

系统 MUST 在开始开发确认前记录本次目标产品、最高真实用户入口、可观察成功结果及风险要求的失败或恢复路径，并 SHALL 让 Red→Green（红灯到绿灯）、行为验收和最终冒烟使用同一入口，而不固定 Pi、Claude、Codex 或其他具体产品测试。

#### Scenario: 确认目标产品测试接缝

- **WHEN** 流程准备开始开发确认
- **THEN** 确认内容明确目标产品、可运行的最高真实用户入口、可观察成功结果及风险要求的失败或恢复路径

#### Scenario: 串行实施并验证真实行为

- **WHEN** 开始开发已确认且一个功能、缺陷或集成纵向切片进入实施
- **THEN** 唯一 Implementer（实施者）在原工作树和分支先通过已确认产品入口产生失败检查，再完成最小实现并使同一检查通过，所有可写调用严格串行

#### Scenario: 验收完成的实施

- **WHEN** 主 Agent 验收已返回的实施
- **THEN** 主 Agent 核对实际提交、差异、工作区及目标产品冒烟，运行固定基线的 Build and Verify 并只接受 `passed` 且 `checked` 非空的结果，再对固定基线后的实际差异执行限定代码审查
### Requirement: 开发流程仅使用两次正式确认

系统 MUST 只请求“开始开发”和“规格与交付”两次正式确认，每次结果只包含“核心摘要”和“确认后进入的下一步”两个区块；确认在其已授权动作及失败恢复期间保持有效，Completion Check（完成检查）不得成为第三次授权门禁。

#### Scenario: 开始开发确认

- **WHEN** 需求、目标产品入口、纵向票据、固定基线、工作树和分支已经明确且有证据支持
- **THEN** 流程以两个输出区块请求一次“开始开发”确认，并在确认后进入串行实施与验证

#### Scenario: 已确认动作发生可恢复失败

- **WHEN** 已确认的动作在执行期间发生可恢复失败
- **THEN** 流程保留当前确认和恢复位置，恢复后继续原动作而不再次请求同一确认
### Requirement: 正式规格与 PR 连续交付

系统 MUST 在实施、风险匹配验证、非空快速验证和限定审查完成后，以一次“规格与交付”确认同时授权正式规格应用和精确 PR（拉取请求）交付动作，并在 PR 合并、目标分支同步和安全清理后执行 Completion Check（完成检查）。

#### Scenario: 确认规格与交付

- **WHEN** 完整正式规格预览及精确交付动作已准备好，且实施阶段没有未解决阻断
- **THEN** 流程以两个输出区块请求一次“规格与交付”确认，确认后应用并验证规格，再自动运行已授权 PR Flow

#### Scenario: 交付完成后检查最终状态

- **WHEN** PR 已合并、目标分支已同步且安全清理返回结果
- **THEN** Completion Check 报告最终完成或精确残留，但不请求新的正式授权
### Requirement: 按证据与风险选择流程等级

系统 MUST 在开始开发确认前记录 Fast（快速）或 Full（完整）Flow Level（流程等级）及其证据。只有当前会话已经具备可重放红灯、已核验根因、作为最高真实用户入口的现有公开测试接缝、单一纵向切片，且没有未决需求及安全、权限、数据、迁移、发布、机器状态、跨系统或破坏性风险时，才能使用 Fast 并复用这些证据；其他情况默认使用 Full。

#### Scenario: 使用快速流程

- **WHEN** 当前会话的红灯、根因、最高真实用户入口及单一纵向切片均已有可核验证据，且没有未决需求及安全、权限、数据、迁移、发布、机器状态、跨系统或破坏性风险
- **THEN** Gate 1 记录 Fast 及其证据，并复用已核验调查，不重复无关的完整需求调查

#### Scenario: 使用或升级完整流程

- **WHEN** Fast 的任一证据失效、范围扩大、出现第二个独立切片，或变更涉及安全、权限、数据、迁移、发布、机器状态、跨系统或破坏性风险
- **THEN** 流程使用或升级为 Full，并执行完整需求路径

#### Scenario: 流程等级不降低验收要求

- **WHEN** 任一流程等级进入实施与验证
- **THEN** 流程仍保留两次正式确认、Red→Green、固定基线的非空 Build and Verify、真实入口冒烟和独立审查
### Requirement: 开发流程按依赖与步骤组织代理指令

系统 MUST 让 `dev-flow` 入口保持为指向各阶段的薄路由，并 SHALL 让各阶段编排先声明必须加载和使用的依赖，再按执行顺序编排步骤，将检查、停止条件、恢复规则和可核验完成条件放在触发它们的步骤中。

#### Scenario: 代理加载开发流程入口

- **WHEN** Agent（代理）加载 `dev-flow` 入口
- **THEN** 入口只核对调用前提并按顺序指向需求、实施与验证、规格与交付三个阶段

#### Scenario: 代理加载开发流程阶段

- **WHEN** Agent（代理）加载任一阶段编排
- **THEN** 文档依次提供“必须依赖”和“流程编排”两个顶层编排模块，且每个步骤在执行位置说明适用检查、异常处理和完成条件
### Requirement: 开发门禁接受上下文明确授权

系统 MUST 在完整展示当前门禁内容后，取得用户对当前门禁动作的明确授权；授权语义不明确时 SHALL 停留在当前门禁并澄清。

#### Scenario: 用户明确授权当前门禁

- **WHEN** 当前门禁内容已经完整展示，且用户明确授权当前门禁动作
- **THEN** 流程记录一次当前门禁授权并进入获授权动作

#### Scenario: 当前授权语义不明确

- **WHEN** 当前门禁内容已经完整展示，但用户授权语义不明确
- **THEN** 流程停留在当前门禁并澄清授权范围
### Requirement: 完整需求路径核验当前会话依赖证据

系统 MUST 在 Full（完整）需求路径进入实施前，核验当前会话实际使用经策略校验的 Architect（架构师）与 `codebase-design`、`grill-with-docs`、`domain-modeling`、`to-spec` 和 `to-tickets` 的证据；缺少、不可读、未实际使用或无法核验任一必需证据时 SHALL 停在需求阶段。

#### Scenario: 完整路径缺少依赖使用证据

- **WHEN** Full（完整）需求路径缺少任一必需 Skill（技能）的当前会话实际使用证据
- **THEN** 流程报告缺口并停在需求阶段，不派发可写 Implementer（实施者）

#### Scenario: 已有单一纵向票据

- **WHEN** 当前请求已经是一个可独立观察的单一纵向票据
- **THEN** `to-tickets`（转为票据）核验无需拆分且不创建重复票据
