# Pi Development Flow

## Purpose

为 Pi（编码代理）提供一项仓库开发变更从需求确认到 PR（拉取请求）合并、清理和本地交付的统一编排入口，并按风险控制并行、验证和审查成本。

## Requirements

### Requirement: Pi 本地开发流程入口

系统 MUST 允许用户把主仓库中的 `pi-development-flow` 本地包目录注册为用户级 Pi（编码代理）Package（包），并从新 Pi 进程发现和调用 Development Flow（开发流程）Skill（技能），而不复制 Skill 来源。

#### Scenario: 从稳定主仓库路径安装

- **WHEN** 用户在变更合并后通过 Pi 正式安装入口注册主仓库中的本地包目录
- **THEN** 新 Pi 进程发现 `pi-development-flow` Skill，并将其来源识别为该本地 Package 目录
### Requirement: 单项开发变更三阶段编排

系统 MUST 把一项开发变更编排为需求确认、实施和清理收尾三个阶段，并分别保留需求产物确认、实施授权、正式规格确认和交付授权四个门禁。

#### Scenario: 创建变更后等待实施授权

- **WHEN** 用户已经确认并落盘需求、测试接缝和纵向票据
- **THEN** 系统展示结构化实施计划并等待独立实施授权，不把创建变更视为实施授权

#### Scenario: 恢复已有变更

- **WHEN** 用户提供已有 MySpec（自有规格）变更目录
- **THEN** 系统从规格、票据、Git（版本管理）、工作树和 PR 状态识别首个未完成门禁并从该处继续
### Requirement: 开发流程初始化职责边界

系统 MUST 只在用户明确请求初始化或正式入口报告前置条件缺失时检查初始化状态，并把缺失项委托给已有正式初始化入口；没有正式入口负责的缺失项 MUST 作为阻塞报告。

#### Scenario: 已初始化仓库开始新变更

- **WHEN** 用户在已完成开发流程初始化的仓库开始或恢复变更
- **THEN** 系统不重复运行完整预检，而由各正式入口在调用时校验自身条件

#### Scenario: 缺少正式初始化入口

- **WHEN** 仓库缺少 CI（持续集成）流程、工作树脚本或其他前置项且没有正式初始化入口负责补齐
- **THEN** 系统报告阻塞并停止，不自行生成初始化实现
### Requirement: 按决策规模确认开发需求

系统 MUST 根据待解决决策是否能在一个会话内厘清选择需求讨论方式，并在用户确认测试接缝、规格和纵向票据后，才把领域术语与需求产物写入隔离的变更工作树。

#### Scenario: 单会话需求确认

- **WHEN** 目标和边界能在一个会话内厘清
- **THEN** 系统使用带领域建模的需求拷问形成规格和纵向票据草案

#### Scenario: 跨会话依赖决策

- **WHEN** 需求包含相互依赖的决策、研究或原型且需要跨会话推进
- **THEN** 系统先维护决策地图和决策票据，再从已解决决策生成独立的实施票据
### Requirement: 按真实并行性选择隔离拓扑

系统 MUST 只在存在至少两张可安全并行的无阻塞票据时创建集成分支和独立票据工作树；其余变更 MUST 使用单一功能分支和单一工作树顺序实施。

#### Scenario: 所有票据均需顺序实施

- **WHEN** 票据存在依赖、核心文件冲突或只有一张可实施票据
- **THEN** 系统不创建集成分支，也不为并行而额外派遣多个 Implementer（实施者）

#### Scenario: 存在真实并行前沿

- **WHEN** 多张无阻塞票据能够在独立工作树安全实施
- **THEN** 主 Agent（代理）根据依赖、冲突、资源和整合成本决定并行数量，并要求所有 Subagent（子代理）遵循 Pi 子代理策略
### Requirement: 测试驱动与风险匹配验证

系统 MUST 要求功能、缺陷和集成行为先在已确认公开接缝出现失败检查再实现，并按变更风险和影响范围选择目标检查、快速验证、真实入口冒烟和必要的高风险路径验证。

#### Scenario: 标准变更完成实施

- **WHEN** 标准功能、缺陷或集成变更完成票据整合
- **THEN** 系统运行本次主成功路径的真实用户入口或发布形态冒烟及 Build and Verify（构建与验证）快速验证，不为每张票据重复完整端到端回归

#### Scenario: 高风险变更完成实施

- **WHEN** 变更影响安全、数据完整性、迁移、发布、失败或恢复路径
- **THEN** 系统除主成功路径外验证受影响的高风险路径，且不以快速冒烟省略明确验收要求
### Requirement: 差分限定的双层代码审查

系统 MUST 把代码审查限定在固定比较点之后的实际差异及判断该差异所需的直接上下文，只对关键票据执行整合前审查，并在全部整合后执行一次整体审查。

#### Scenario: 修复代码审查发现

- **WHEN** 开发者修复明确规则、规格或当前维护风险问题
- **THEN** 系统只定向复核修复差异和受影响行为，不重新扩查未变化实现或依赖树

#### Scenario: 单票据构成完整变更

- **WHEN** 一张票据覆盖本次变更的全部实现范围
- **THEN** 一次整体审查同时满足关键任务和整体审查门禁
### Requirement: 正式规格与 PR 交付闭环

系统 MUST 在整体审查及修复验证通过后固化正式 MySpec（自有规格），并在独立交付授权后通过 PR Flow（拉取请求流程）完成检查、实际合并、目标分支同步和非强制安全清理。

#### Scenario: PR 尚未实际合并

- **WHEN** PR 已创建、正在等待检查或返回其他 PR Flow 停止状态
- **THEN** 系统报告可恢复暂停，不宣告 Development Flow（开发流程）完成

#### Scenario: 开发流程全部完成

- **WHEN** PR 已合并、目标分支已同步、授权的本地交付已在新消费进程验证，且所有可安全移除的分支和工作树均已清理
- **THEN** 系统报告本次 Development Flow 全部完成
