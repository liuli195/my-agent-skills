# 冲突发生后使用冲突解决技能

## Problem Statement

Development Flow（开发流程）没有明确规定 Git（版本管理）合并或变基发生冲突后的处理入口，Agent（代理）可能绕过统一的冲突调查、解决和验证流程。

## Solution

当开发流程检测到正在进行的合并或变基冲突时，必须加载并使用 `resolving-merge-conflicts`（解决合并冲突）Skill（技能）；解决后重新运行受影响的检查，并从原失败步骤恢复。

## User Stories

1. 作为开发流程使用者，我希望冲突发生后统一调用冲突解决技能，以免 Agent 临时采用不一致的处理方式。
2. 作为变更审阅者，我希望冲突解决基于需求、票据、提交和测试证据，以免引入未经批准的新行为。
3. 作为交付负责人，我希望冲突解决后重新运行受影响的检查，以便确认集成结果仍然有效。
4. 作为流程恢复者，我希望冲突处理完成后回到原失败步骤，以免重开门禁或丢失恢复位置。

## Implementation Decisions

- 保持开发流程入口为薄路由，在规格与交付阶段增加条件依赖和处理步骤。
- 条件只在存在进行中的 Git 合并或变基冲突时触发。
- 冲突解决由现有 `resolving-merge-conflicts` 技能负责，不复制其内部规则。
- 解决完成后重跑受影响的检查，并从原失败步骤恢复。
- 不新增正式门禁。

## Testing Decisions

- 通过现有 Development Flow 文档测试检查条件依赖、调用时机、受影响检查和恢复步骤。
- 使用真实 Pi Package（包）资源加载入口覆盖最终发布形态。
- 使用固定基线的 Build and Verify（构建与验证）作为正式验证入口。

## Out of Scope

- 不修改 `resolving-merge-conflicts` 技能本身。
- 不改变 PR Flow（拉取请求流程）的合并和清理行为。
- 不主动制造或解决一次真实仓库冲突。
- 不新增第三个正式门禁。

## Further Notes

本变更使用 Fast（快速）Flow Level（流程等级），因为根因、现有文档测试接缝和单一纵向范围均已确认。
