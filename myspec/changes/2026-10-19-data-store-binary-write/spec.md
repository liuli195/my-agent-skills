# Data Store（数据存储）原生二进制字段写入

**Status:** ready-for-agent

目标正式发行版本：2.5.0；接口能力版本继续为二。发行清单的实际版本更新由后续 release-flow（发布流程）完成，本需求不代表已经发布。

## Problem Statement

调用项目需要持久保存已经存在的二进制字段，同时保留可直接查询的普通元数据。当前公开写入在导入有类型记录前要求整行通过 JSON（数据交换格式），不能接收 Python（编程语言）原生 bytes（字节串）。业务调用方为绕过这一限制而反复列表化或编码大字段，会增加转换成本；现有隔离实验只证明候选方向，尚未证明新公开接口的实际收益。

本次只补通用存储能力，沿用既有逻辑表、逻辑键和原子替换。数据存储不理解学习器、矩阵或调用项目的状态协议。

## Solution

在同一个公开 write（写入）入口增加可选 binary（原生二进制方式）开关，默认关闭。显式开启且提供字段类型时，顶层 BLOB（二进制字段）直接接收 bytes 或 None（空值）；其他字段继续沿用现有 JSON 转换与 from_json_strict（严格转换函数）的转换、报错行为。现有调用和已有 BLOB 字符串写入继续走原路径。

Python 读取仍通过现有点读、批量点读和显式表查询返回原生 bytes。命令行继续支持普通记录写入和元数据查询；直接输出二进制字段时明确拒绝，不再把其伪装成可无损恢复的字符串。

## User Stories

1. 作为存储调用者，我希望显式开启原生二进制写入，使原有调用保持现有行为。
2. 作为存储调用者，我希望声明顶层二进制字段并传入原生字节串，使数据不必经过列表或文本编码中转。
3. 作为存储调用者，我希望保存空字节串、任意字节内容和空值，使其读回时保留准确区别。
4. 作为存储调用者，我希望同一记录包含二进制字段和普通字段，使元数据仍能直接筛选和查询。
5. 作为存储调用者，我希望一次写入多条记录及多个二进制字段，使每行的字段始终准确对应。
6. 作为存储调用者，我希望纯二进制字段记录也可写入，使接口不依赖额外的虚设元数据字段。
7. 作为现有调用者，我希望原有类型推断、显式类型转换及失败行为不变，使升级无需修改旧调用。
8. 作为现有调用者，我希望旧式 BLOB 字符串写入仍沿用原路径，使显式字段类型本身不触发新方式。
9. 作为存储调用者，我希望错误值、缺字段、额外字段及冲突字段明确失败，使损坏记录不会发布。
10. 作为存储调用者，我希望带引号、保留词等合法字段名称按名称处理，使字段名不能变成查询表达式。
11. 作为存储调用者，我希望同键替换继续是单份完整原子发布，使中途失败保留原有完整记录。
12. 作为存储调用者，我希望继续使用现有点读、字段选择、筛选及查询入口，使读取不增加第二套接口或副本。
13. 作为命令行使用者，我希望元数据查询继续有效，而直接二进制输出给出清楚提示，使我不会误用有损结果。
14. 作为新能力消费者，我希望加载实际实现时检查二进制写入能力，使旧安装会明确停止而不是在运行中静默降级。
15. 作为其他既有消费者，我希望原有接口版本及函数检查仍有效，使不使用新能力的调用不被迫改变。
16. 作为维护者，我希望独立安装形态也通过公开入口验证，使实现不依赖源码仓库或开发缓存。
17. 作为维护者，我希望通用接口与业务恢复验证各归属其仓库，使存储层不被业务模型污染。
18. 作为使用者，我希望云端继续使用正式发布市场、本机继续使用现有源码开发市场，使接入结果符合两端各自的使用方式。

## Implementation Decisions

- Module（模块）仍为现有数据存储；Interface（接口）保持一个 write 入口，新增关键字 binary，默认 False（关闭）。不新增 write_binary（独立二进制写入函数）、存储后端、服务或矩阵协议。
- binary=True（开启）必须提供非空显式 schema（字段类型）。仅显式声明的顶层 BLOB 走原生字节写入，只接受 bytes 或 None；不支持 bytearray（可变字节数组）、memoryview（内存视图）、任意对象反序列化或嵌套字节串。
- binary=False（默认）不因 schema 中出现 BLOB 自动切换方式。已有 JSON 导入、类型推断、旧 BLOB 字符串接受行为及错误含义保留。
- 开启后，普通字段继续现有 JSON/from_json_strict 行为，包括引擎既有合法转换和缺字段失败；不新增一套不兼容的 Python 类型约束。额外字段、缺少声明字段及大小写冲突等非法输入在发布前失败。
- 纯 BLOB 记录不构造空 JSON 字段结构；混合多行的普通字段与二进制字段必须显式保持逐行对应，不依赖未承诺的行顺序连接。
- Adapter（适配实现）复用既有 DuckDB（分析查询引擎）与单个 Parquet（列式文件），保留 Zstd（压缩算法）、临时文件、原子替换和现有有限重试。不增加旁路文件、二进制内容索引、跨键事务或写后整份回读。
- read_key（单键读取）、read_keys（多键读取）和 query（查询）继续使用现有游标与安全限制，Python 读回 BLOB 为原生 bytes。未知投影字段仍报错，不为新旧字段差异回退读取整行。
- API（接口能力）版本保持 DATA_STORE_API_VERSION=2，增加 DATA_STORE_CAPABILITIES（接口能力集合），其中包含通用 binary-write-v1（二进制写入第一版）能力；正式发行号仍由后续发布流程确定，不能用能力标识冒充发行版本。新消费者必须在实际加载实现时核验该能力，旧消费者不必新增能力要求。
- 命令行不新增二进制输入协议。普通 JSON 写入不变；所有读取命令直接输出 BLOB 时明确失败并提示选择元数据或在查询中显式编码。不再以 default=str（默认转字符串）悄悄输出二进制值。
- 读取调优只记住配置判断，不保留二进制业务内容；参数含字节串时可直接跳过调优记忆，不新增哈希或缓存框架。
- 完整结果不得整体塞入不透明二进制列。调用方只把确有二进制语义的字段保存为 BLOB，结构化元数据继续单独保留并可查询；数据存储不解释其内容、长度或业务有效性。
- 不添加运行依赖。继续使用既有固定 DuckDB 版本及项目连接脚本；开发测试不得更换云端全局安装或手改插件缓存。

## Testing Decisions

- 最高公开 Seam（测试接缝）为独立复制/安装形态下的 Python write 与现有只读入口：从真实随包脚本加载，显式写入带二进制字段的普通通用记录，再通过同一公开入口读回。不得只测试私有转换辅助函数。
- 第一条红灯即在该形态调用带 binary=True 的公开 write，验证实际 bytes 往返；修复后重跑同一检查，最终真实入口冒烟继续使用同一接缝。配套命令行子进程对同一数据只选普通元数据应成功，直接输出 BLOB 应清晰失败。
- 数据存储仓库负责：bytes/None/空字节串、非文本字节、多行多 BLOB、纯 BLOB、混合字段及逐行对应、字段名转义/冲突、缺额外字段、非法或嵌套值、普通字段现有转换、默认旧路径、能力声明、Zstd、原子替换及失败后原数据可读。
- 复用既有公开读写、独立技能复制冒烟、查询安全、投影/筛选、原子替换、项目连接及构建验证入口；不创建新的测试运行器。Linux（云端系统）完成真实安装形态冒烟；Windows（视窗系统）相关字节绑定及替换行为在用户已允许的本机验证阶段确认。
- 调用项目仓库负责：实际 loader（加载器）的新能力检测与转发、业务字段格式判别和校验、模型位级相同、下一次预测/学习及随机进度一致、控制记录排除大字段、并发/恢复/迁移和真实规模成本。本票不以通用小样本替代这些业务验收。
- 实施后沿公开入口用同一真实模型副本重测保存与完整恢复各三次，再在调用项目复用同一次搜索的既定验证。记录分布、正确性、数据规模、环境和实际安装身份；不追加百种子研究，不承诺隔离实验的速度。
- 正式验证继续由 build-and-verify（构建与验证）按固定基线运行，要求 passed（通过）且 checked（已检查）非空；不以内部测试代替真实公开入口冒烟。

## Further Notes

### 领域术语与已批准决定

- 原生二进制字段：由调用者明确声明并提供原生字节值的顶层 BLOB，内容对数据存储不透明。
- 普通元数据：仍作为独立有类型字段查询的内容，不随大字段整体封装。
- 接口能力版本：现有必需接口合同为二；二进制写入能力为新增可选能力，区别于正式发行号。
- 应用状态版本：由调用项目决定其记录格式兼容性；区别于模型学习事件的 version（事件序号），二者不应混用。
- 完整记录与控制记录：是调用项目的两类记录；其协调和迁移不属于数据存储。未来业务接入采用新字段 theta_blob、a_inv_blob，保留旧数组读取；先读共同存在的稳定元数据判别应用状态版本，再读相应负载，控制记录始终不带二进制大字段。
- 设计树已收敛：通用显式 binary 开关 → 旧路径兼容 → 新旧业务字段分开 → 受控一次迁移（A）→ 命令行最小拒绝方式（A）。这些已有用户批准，不重新开启架构访谈；待确认仅为门禁一的分支、实施/审查方式与本票公开接缝。
