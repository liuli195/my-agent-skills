# 开发流程门禁一与子代理策略更新

## Problem Statement

当前开发流程在门禁一前要求已有非主干分支，并把同一工作树内的开发固定为串行；门禁一也没有让用户选择实施和审查方式。子代理策略及本机具名配置仍使用 GPT-5.6，审查者和架构师的思考强度不是用户要求的高等级。

## Solution

沿用当前工作区。门禁一展示 AI 推荐及理由，让用户可接受整套推荐或逐项选择，并必须明确确认以下三组内容：功能分支及完整名称；串行或并行及主代理或子代理开发；每票或全部完成后由子代理 Reviewer（审查者）审查。缺少任一选择不通过门禁。新建分支仅在门禁一授权后执行。

并行仅由子代理处理主代理判定为无依赖、改动和测试资源不冲突的票据；其他票据串行。所有任务使用同一工作树，共享的 Git 操作串行，主代理核验每票实际结果。审查由子代理 Reviewer（审查者）使用 `code-review`（代码审查）执行；入口不可用时停在审查步骤。门禁二不变。

四个角色的模型分别改为 Explorer 与 Implementer 的 `gpt-6-luna`、Reviewer 与 Architect 的 `gpt-6-sol`；思考强度依次为 `low`、`max`、`high`、`high`。同步本机具名配置，保留职责和读写边界。

## User Stories

1. 作为开发者，我希望在原工作区选择现有或新功能分支并确认准确名称，避免代理自行决定分支。
2. 作为开发者，我希望 AI 给出一套具体推荐和简短理由，也能逐项改选。
3. 作为开发者，我希望分别确认开发顺序、实施代理和审查时机，未确认时流程停止。
4. 作为开发者，我希望独立票据可以由子代理在同一工作树并行实施，以缩短等待时间。
5. 作为开发者，我希望主代理识别依赖和资源冲突，使会相互影响的票据串行，并核验每票结果。
6. 作为开发者，我希望审查入口不可用时明确停止，而不是悄悄改用其他方式。
7. 作为开发者，我希望技能契约与具名子代理使用同一 GPT-6 模型和思考强度。
8. 作为开发者，我希望现有真实入口测试、正式验证、门禁二和读写权限继续有效。

## Implementation Decisions

- 继续使用当前工作树；不提供新建工作区选项。门禁一之前只读核对工作树、当前分支和基线；需要新分支时先展示准确名称，在确认后创建并重新核对。
- 三组选择均须记录明确的用户答案。串行可选主代理或子代理；并行只能选子代理。推荐不构成授权。
- 并行资格由主代理按票据依赖、文件归属和测试资源判断；共享 Git 状态变更及最终正式验证串行。
- 子代理审查复用 `code-review`，不增加另一套浏览器控制实现。
- 子代理策略负责模型、思考强度和同一工作树的有条件并行规则；开发流程引用该策略，不复制模型矩阵。
- 正式规格只在门禁二授权后应用；实施阶段保存候选并保持正式规格不变。

## Testing Decisions

- 最高公开接缝是现有 Skill 包资源加载入口与具名子代理配置：检查实际加载的技能及其阶段文档、门禁选择与停止规则，以及四个配置的准确模型和思考强度。
- 使用同一入口先证明旧规则与新要求冲突，再修改技能和契约检查，使新规则通过。
- 通过仓库既有 Build and Verify 快速入口验证；检查不得为空。核对 `main`、缺少选择、无效选择、冲突票据和不可用网页审查的停止路径。

## Out of Scope

- 新工作区、多工作树、独立任务分支或新调度器。
- 更改门禁二、PR Flow、其他角色职责或读写权限。

## Further Notes

仓库词汇表当前的 Single Writer（单写者）定义与批准的条件并行规则冲突，需要同步更新。并行是可选路径；无法证明票据互不干扰时采用串行。
