# MySpec 多工作树开发绑定安全

**Status（状态）：** ready-for-agent

## Problem Statement（问题说明）

MySpec（自有规格）的开发模式通过机器级裸 `myspec` CLI（命令行程序）绑定一个源码工作树。用户从另一个隔离工作树执行规格应用时，CLI 仍可能运行旧工作树的源码，并把错误实现的结果写入当前目标规格库。

## Solution（方案）

让开发模式的规格写入操作校验源码工作树和目标规格工作树是否一致。两者不一致时，命令在创建预览、备份或替换主规格前返回稳定的可识别错误，并告诉用户如何重新绑定目标工作树。

`doctor`（诊断）同时报告源码工作树、源码提交、目标工作树、目标提交和匹配结果。公共 MySpec 技能文档说明开发模式的手工切换方式，并明确单一全局源码绑定下只能串行应用。

## User Stories（用户故事）

1. 作为规格维护者，我希望在错误工作树中执行应用时得到明确阻断，从而避免主规格被旧实现污染。
2. 作为规格维护者，我希望 `doctor` 显示实际源码绑定和目标工作树，从而能在写入前发现错绑。
3. 作为多工作树开发者，我希望用 `myspec init --dev --source <目标工作树>` 手工切换绑定，从而可以依次处理不同工作树。
4. 作为规格维护者，我希望源码和目标工作树一致时，预览、原子应用和重复应用继续通过，从而修复不会破坏正常流程。
5. 作为多工作树开发者，我希望文档明确开发模式不支持多个工作树并行应用，从而不会把全局绑定误认为每个工作树独立。

## Implementation Decisions（实现决定）

- 开发绑定识别和匹配逻辑放在现有工具生命周期管理模块中，供 `doctor` 和规格应用入口复用。
- `apply-delta`（应用增量规格）以目标规格目录所属的 Git（版本管理）工作树作为目标，不以调用进程的当前目录猜测目标。
- 匹配校验位于预览和最终原子应用共享的公开入口之前；错误必须发生在任何预览、备份、替换和工作状态清理之前。
- 发布模式保持现有行为；只读校验、差异和状态命令不新增绑定阻断。
- 不自动按当前目录动态切换全局源码，不新增多个全局源码绑定，也不新增跨工作树的全局规格运行锁。
- 保留现有开发源码的干净工作树、官方来源和提交可验证要求。

## Testing Decisions（测试决定）

- 最高测试接缝是裸 `myspec` CLI 的真实入口，不直接测试私有绑定函数。
- 回归场景建立两个隔离 Git 工作树：绑定工作树 A 后从工作树 B 运行 `doctor` 和 `apply-delta`，验证报告不匹配、返回可识别错误、目标规格和预览均无变化。
- 同一测试随后将绑定切换到 B，验证 `doctor` 匹配，预览、原子应用和重复应用成功。
- 继续覆盖混合 `LF`/`CRLF`（换行格式）的规格库，确认非目标文件字节保持不变。
- 实现阶段先用同一公开入口检查产生红灯，再以最小实现转绿；随后通过 Build and Verify（构建与验证）快速检查，并完成 Windows（视窗操作系统）真实入口冒烟。

## Out of Scope（范围外）

- 不自动根据当前目录选择或执行另一工作树源码。
- 不支持多个开发工作树并行执行写入操作；需要并行时另行设计隔离的 CLI 或运行环境。
- 不修改发布模式、Pi、Claude、Codex 客户端注册和现有规格 Delta（增量规格）语义。
- 不重新实现 PR #282 已完成的非目标规格字节保持修复。
- 不执行真实发布、推送、合并或用户环境安装同步。

## Further Notes（补充说明）

开发源码绑定是机器级单一绑定；`.local/spec-work/lock` 仍按目标工作树隔离。切换绑定可以串行处理多个工作树，但不能把多个工作树当作同时可写的独立开发运行时。
