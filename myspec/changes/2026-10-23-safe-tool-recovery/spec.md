# 安全恢复规格会话与精确维护数据

**Status（分拣）:** ready-for-human（两票实施验收完成；门禁二已确认，正式规格已应用；待PR交付、发布同步及发布后真实验收）

**Development Flow（开发流程）:** Full（完整）。涉及不可恢复数据删除、会话恢复、发布及客户端同步，采用两个正式门禁，不以方案批准替代展示后的 Gate Confirmation（门禁确认）。

**Source Worktree（源码工作树）:** 沿用现有技能仓库；当前为干净的旧发布分离提交，尚未切换分支或改变稀疏检出。拟功能分支为 codex/safe-tool-recovery，推荐并行子代理 Implementer（实施者）开发、每票独立 Reviewer（审查者）验收；推荐不等于已确认。

**Verification Baseline（验证基线）:** 固定为已取得并核对的最新 origin/main 5f5a1cfaf0fcee4f53ad068ecfc52a2c6b9fa147，不使用旧 f20442e 或当前分离提交。该基线已有 Data Store 2.5.0 二进制写入能力，实际接口能力版本仍为二；本变更不得回退该能力。

## Problem Statement（问题）

用户在使用 MySpec（自有规格）和 Data Store（数据存储）处理项目收尾时，遇到两类需要工具自身支持的恢复和维护操作。

MySpec 2.3.0 的失败预览会留下持续会话锁。输入内容变化后，旧预览不能继续，但现有公开入口不能安全中止该会话；重新初始化又被锁阻止。初始化还会静默删除已有 current（当前会话）内容，先写好的 Delta（增量规格）可能因此丢失。不能靠手工删除锁、重写指纹、修改工具实现或绕过正式规格确认恢复。本次已独立复现一个失败会话；用户表示发生过多次，历史次数尚未核实，不据此编造频率。

Data Store 已有按逻辑表和精确键读写的通用能力，但没有完成“预演精确目标、按预演的文件身份执行删除、逐项报告并恢复未完成项”的离线维护闭环。不能让每个调用项目复制大量通用清理代码，也不能把业务引用或保留政策下沉到技能，更不能将批量文件删除冒称原子事务。

## Solution（方案）

在用户技能仓库中完成两个各自可演示的纵向切片。MySpec 提供官方 state-abort（会话中止），只对身份明确、经外部确认没有活动会话且未发生正式应用的预览会话，先安全归档、再解锁；禁止初始化静默覆盖，并允许新会话显式导入保留的 Delta 后重新走分析、校验、预览及确认。Data Store 提供逻辑表＋精确键的批量离线维护预演和按计划执行，完整预检、核验文件身份、输出部分失败明细，并支持同一计划恢复。

实施复用现有命令、状态、路径限制、名称校验、测试与发布能力，不建立通用锁服务、数据治理系统或新框架。按 Development Flow 完成验证、独立审查、正式规格预览及 PR（拉取请求）交付后，使用既有发布工作流发布 MySpec npm（软件包）及独立市场、Data Store 共享市场，再同步实际消费端，分别回到原规格恢复与数据维护任务验收。发布成功、同步成功和项目实际验收分别报告。

## User Stories（用户故事）

1. 作为规格使用者，我希望通过官方 state-abort 中止已放弃或失败的预览，以免手工删锁绕过保护。
2. 作为规格使用者，我希望中止前明确看到目标会话及其精确身份，以免误操作另一个目标工作树。
3. 作为规格使用者，我希望工具要求外部确认没有活动会话，而不是凭锁时间或短命命令进程猜测安全。
4. 作为规格使用者，我希望中止保留完整 Delta、决定及失败记录，以便之后核对或重建预览，而不是丢弃工作。
5. 作为规格使用者，我希望归档失败时保留原锁和原会话，以免未留证据就放行新写入。
6. 作为规格使用者，我希望部分正式应用、未知状态或身份不匹配时明确拒绝中止，以免释放需要事务恢复的现场。
7. 作为规格使用者，我希望重复中止能安全识别已完成结果，不误归档后来出现的新会话。
8. 作为规格使用者，我希望 state-init（会话初始化）发现已有内容时明确拒绝，不静默删除预先写好的 Delta。
9. 作为规格使用者，我希望初始化失败只撤回该次实际新建的锁，不删除其他会话的锁或已有内容。
10. 作为规格使用者，我希望新会话能显式导入保留 Delta，但不继承旧确认、逐项决定或 ready（就绪）状态，以便输入和正式规格重新核验。
11. 作为规格使用者，我希望旧格式失败会话的支持范围明确，不能仅因缺少新版字段就假称已恢复，也不能靠补写历史身份伪造兼容。
12. 作为数据维护者，我希望只提供明确逻辑表和精确键，就能预演实际要删除的记录组文件，不手写或猜测物理路径。
13. 作为数据维护者，我希望计划冻结数据根、规范化目标及可核验文件身份，以免稍后误删同名替换文件。
14. 作为数据维护者，我希望在任何删除前完成整个计划的预检，非法、越界、重定向或身份漂移时明确失败。
15. 作为数据维护者，我希望执行前再次核验目标身份，检测到变化就保留该文件，不用旧计划授权新内容。
16. 作为数据维护者，我希望批量执行如实区分成功、失败、未执行和结果不确定，不把部分成功说成事务成功。
17. 作为数据维护者，我希望同一计划可恢复尚未完成项，不重复删除已完成项，也不把后来重建的同键文件视作旧目标。
18. 作为项目维护者，我希望业务引用、保留条件和允许删除什么由项目决定，通用技能不扫描全库推断孤儿或自动清理业务锁。
19. 作为普通调用者，我希望离线维护不改变既有读写、查询、缓存、依赖或项目共用连接的正常执行成本。
20. 作为插件使用者，我希望新能力既在源码入口可用，也在实际发布包及市场安装形态可用，并能验收原来的两个任务。

## Implementation Decisions（实施决定）

### MySpec：保留草案的会话中止

- 新增官方 state-abort，不提供忽略身份的普通 unlock（解锁）或 force-unlock（强制解锁）。通过裸 myspec CLI（命令行程序）使用；文档与既有四个技能入口同时说明适用范围和拒绝条件。
- 必须匹配目标工作树、工作根及保存的精确会话身份，并取得外部“无活动会话”确认。不依赖锁时间自动清理，不把 state-init 命令已退出等同于会话已无人使用，不建立常驻所有者服务。
- 仅处理可证明未修改正式规格的失败／放弃预览；按需保留当前状态、Delta、预览、决定和失败材料，在工作根内部创建唯一的 aborted（已中止）归档。归档可靠完成后才释放本次会话锁；不得删除 Delta、覆盖旧归档或触及其他工作根。
- 身份不匹配、缺少必要证明、状态未知、正在应用或可能部分替换正式规格时，明确拒绝并保留恢复现场。中止不能替代正式应用事务的恢复；本票不扩建一般事务恢复平台。必要的最小应用阶段标识只用于使危险状态可识别，不借此放宽既有原子应用及回滚要求。
- 旧格式失败预览会话必须有明确且受限的证明标准；现存 2.3.0 锁只有命令文字，不能假设它具备新版归属／应用阶段字段。必须兼容已核验的这种旧格式：调用方明确确认无活动会话，精确提供并匹配旧锁命令、保存状态及目标工作树／路径身份；当前正式规格须与状态中原规格基线一致，相关规格父目录不能存在备份或其他部分应用现场。输入内容或失败预览变化本身不禁止中止，但必须归档现有草案，不能继承旧确认。不得要求旧状态不存在的新版字段、偷偷补写身份或仅凭时间抢锁；任一旧证据不足仍拒绝，保留现场。
- state-init 不得静默递归删除已有 current 内容；发现已有会话／草案时明确拒绝并给出官方恢复路径。初始化失败仅撤回本次确实新建且仍属于本次的锁，不清理他人的锁、会话或草案。
- 新会话可显式导入已归档的 Delta，导入只复用内容，不复用旧身份、决定、最终确认或 ready 状态；按当前证据与正式规格重新初始化、处理必要决定、校验 Delta、生成并展示完整预览，仍须既有正式确认后才能应用。

### Data Store：精确目标的离线维护

- 增加逻辑表＋精确记录键的批量预演／执行闭环，沿用现有名称及大小写规则，规范化去重；不提供通配符、全表、全库或路径列表删除入口。
- 预演不修改业务数据，输出可复核计划，绑定唯一计划身份、精确数据根、规范化逻辑目标及足以辨别同名替换和内容漂移的文件身份。不能仅凭文件名或逻辑键判断计划仍有效。
- 执行要求明确批准的精确计划，并要求调用方确认处于无相关活动读写的离线维护状态。先对全部目标完整预检，再开始逐项执行；各项实际删除前重新核验文件身份。重定向、越界、缺失、不可读、身份变化及其他错误须区分，不能静默扩大范围或当作成功。
- 批量删除不是原子事务。执行记录逐项目标、原身份、成功、失败、未执行或结果不确定；报告实际已发生的删除，不因后项失败伪称前项未发生或全部已回滚。
- 恢复只沿同一计划处理尚未可靠完成项，并再次核验身份；已完成项不重做，后来出现的同键新文件不受旧授权覆盖。删除后回执保存失败等不确定结果须如实报告，不能靠重新匹配同名文件盲目重试。
- 业务反向引用、成果保留政策和清理资格仍由调用项目确定；技能不扫描混合历史推断孤儿、不搬入原项目大型清理器、不删除业务锁文件。只删除计划精确指定的完整记录组分片，不做行级删除或数据迁移。
- 不改变正常读写热路径，不新增每次查询的锁探测、全目录扫描、常驻连接或安装状态查询，不新增独立长期业务数据库。保留最新基线的二进制写入、原生 BLOB（字节字段）类型、接口能力版本二及既有错误语义。维护计划／回执不作为一份业务数据副本，不写入业务数据表。

### 交付与分发

- 保留现有 Tool Implementation Closure（工具实现闭包）、Toolchain Identity（工具链身份）、Development Source Binding（开发源码绑定）和目标工作树隔离，不从整个仓库提交猜测单工具身份。
- 用户已认可两个工具对应两张票据，不新增拆分；票据技术上互不阻塞，按最新确认并行实施与每票独立审查，不以执行顺序伪造代码依赖。两票作为需求产物保存，但完整门禁一仍待展示后确认；共同发布、消费端同步及原两任务复验要求两个切片都已验收。
- 发布复用既有 release-flow（发布流程）的 preflight（发布前检查）及 publish（发布）和现有 GitHub（代码托管平台）工作流。MySpec 走 npm 包及包内独立市场，Data Store 走既有共享市场；准确版本和标签依据当次 Release Baseline（发布基线）确定，不混用仓库版本和插件版本，不另造上传或发布脚本。
- MySpec 消费端同步委托其自身 update／doctor（更新／诊断）；Data Store 使用既有 plugin-sync（插件同步）及项目共用连接更新，必要重启如实报告。先验证发布和市场可消费，再在原目标项目使用已发布形态验收；不能以开发源码冒充发布包验证。

## Testing Decisions（测试决定）

- 最高真实用户接缝为裸 myspec CLI 的初始化、中止、显式导入及既有预览／应用流程；Data Store 为随已安装技能提供的公开维护命令和原公开读写入口。不得以直接删文件、内部函数调用次数或整段模拟状态机替代用户可观察闭环。
- 复用现有 MySpec、Data Store 与项目接入测试先例，使用临时目标工作树和隔离数据根；新增用例接入既有 Build and Verify（构建与验证）统一入口，不新建测试运行器。
- MySpec 覆盖失败预览／指纹变化后的安全中止、无活动确认缺失、外来会话、跨工作树、未知／部分应用拒绝、归档失败保锁、重复中止不误伤新会话、已有 Delta 不覆盖、初始化失败只撤本次锁、导入后不继承旧确认及完整重新预览。
- 应用安全通过可控故障注入覆盖正式规格替换前后边界；结果必须证明未知或未完成事务不能经 state-abort 放行，原正式规格及必要恢复材料保持。不能只验证新增命令的正常退出。
- Data Store 覆盖规范化去重、非法／空目标、目录越界及重定向、无关文件不访问、计划后同名替换或内容变化、完整预检无副作用、执行前再次核验、部分失败明细、回执失败后的不确定结果、同计划恢复及同键新文件保护。
- 使用一小组及一个代表批量规模测量维护预演、核验和恢复的成本，明确内容散列或文件身份核验的工作量；正常单键／多键读写前后采用同条件交替小规模检查，不能把接口调用数当作物理输入输出次数，不新增大规模性能实验或固定通用秒数门槛。
- 两票各自运行公开 CLI 与正式可分发形态的快速冒烟；MySpec 使用工具已有受控打包／隔离安装验证，Data Store 验证自包含市场运行目录和项目共用连接，不在需求阶段改变全局安装。
- 发布后分别记录固定版本、市场对应内容、实际安装／加载来源和公开入口结果。原规格任务只用新官方安全中止及重新准备，未获正式交付门禁不得应用主规格；原数据任务依项目业务资格及当次精确删除授权执行，不把工具有能力视为可任意删数据。
- 上述最高公开接缝和两票粒度尚待用户在完整门禁一展示后确认；架构核对发现接缝改变时先更新需求，不先写实现。

## Out of Scope（范围外）

- 不手删规格锁、手改指纹、绕过决定／最终确认、替用户认定活动会话已结束或以时间自动抢锁。
- 不提供普通强制解锁、通用锁服务、完整跨程序认证或事务恢复平台；部分正式应用仍保留并走既有受控恢复，不能假称一键解除安全。
- 不做 Data Store 通配／全库／行级清理、业务引用扫描、孤儿推断、保留策略、混合历史迁移、锁文件删除或全局后台维护。
- 不改变普通模拟、GA（遗传算法）训练／停止标准或业务项目其他功能；原项目的清理资格与身份规则不迁入技能。
- 不改仓库规则、正式规格、源码、分支、稀疏配置、发布配置或当前全局安装；本稿只记录需求，实施和正式交付分别受既有门禁约束。
- 不把首次发布准备、远端检查、市场同步或项目真实验收视作天然成功；不绕过尚未具备的发布权限或认证。
