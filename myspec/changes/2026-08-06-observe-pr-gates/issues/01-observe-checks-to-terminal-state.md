# 01 — 观测检查从尚未报告到终态

**What to build:** 让维护者在创建或更新 PR（拉取请求）后运行一次 `complete`（收尾），即可从检查尚未报告持续观测到等待或终态；`diagnose`（诊断）使用相同状态语义但不等待。

**Blocked by:** None — can start immediately.

**Status:** completed

## 技术设计架构

### Module、Interface 与 Seam（模块、接口与接缝）

- 建立一个内部“合并门禁观测” Module（模块），集中拥有检查查询、状态解释、刷新、期限控制和提交一致性复核；删除调用方各自判断空检查、退出码或汇总状态的做法。
- Module 的 Interface（接口）接收项目、初始 PR 快照、等待策略和观测模式，返回一个门禁观测结果；调用方只处理结果，不再理解 GitHub CLI（命令行工具）的原始状态组合。
- 最高测试 Seam（接缝）保持为公开 `complete` 和 `diagnose` 命令。检查查询、PR 刷新、时钟和休眠是 Module 内部 Seam，只用于现有命令替身和确定性时间测试，不暴露给用户。
- 继续使用现有 GitHub CLI Adapter（适配器），不引入新的 GitHub SDK（软件开发工具包）或第二套远端实现。

### 观测结果

每次观测必须返回当前 PR 的源提交、目标提交、原始检查证据、查询错误和以下互斥状态之一：

| 状态 | 判定 | 流程动作 |
|---|---|---|
| `NOT_REPORTED` | 必需检查与 PR 检查汇总均为空 | `complete` 短暂等待；`diagnose` 立即说明检查尚未报告 |
| `PENDING` | 任一有效检查明确处于排队或运行中 | 进入既有检查等待期限 |
| `PASSED` | 非空必需检查全部明确通过 | 允许进入后续审查和合并门禁 |
| `FAILED` | 任一检查明确失败或超时 | 要求修复检查 |
| `CANCELLED` | 任一检查明确取消 | 要求重新触发检查，不自动创建提交 |
| `UNAVAILABLE` | 鉴权、网络、格式或未知状态导致证据无法成立 | 安全停止并保留原始错误 |

`FAILED` 和 `CANCELLED` 优先于 `PENDING`；只有非空必需检查能够证明 `PASSED`。PR 汇总可以证明等待、失败或取消，不能单独证明通过。

### 时间与刷新策略

- `NOT_REPORTED` 的初始观测窗口最多 60 秒，刷新间隔不超过 5 秒；该窗口不新增用户配置。
- 一旦观测到 `PENDING`，切换到既有 `timeoutSeconds` 和 `pollSeconds` 配置，不重置已经消耗的整体安全期限。
- `diagnose` 使用同一状态解释，但只观测一次，不休眠。
- 每次刷新 PR 后都必须与初始快照比较源提交和目标提交；任一变化立即使当前证据失效。

### 输出契约

- 保留现有顶层停止状态。
- 初始窗口结束仍为空时使用独立原因表达“检查尚未报告”，不得回退为网络或访问故障。
- 每个非通过结果都包含可复制的下一步命令或明确下一步动作，并保留当前源、目标提交及观测证据。

## 验收标准

- [x] `空必需检查 + 空检查汇总` 被识别为检查尚未报告，并在 `complete` 中进入最多 60 秒的有界观测。
- [x] 已报告的等待、通过、失败、取消和查询不可用状态拥有互斥分类及对应恢复动作。
- [x] `complete` 和 `diagnose` 通过同一观测 Interface（接口）输出一致语义，未知状态不得进入审查或合并。
- [x] 每轮刷新后复核源提交和目标提交，变化时当前观测失效并安全停止。
- [x] 公开命令回归先证明当前实现对 `空 + 空 → pending → pass` 错误停止，再覆盖修复后的完整序列、永久未报告、失败、取消、查询错误和提交变化。
