# PR Flow 有界观测合并门禁

## Problem Statement

维护者在创建或更新 PR（拉取请求）后立即运行 PR Flow `complete`（收尾）时，GitHub（代码托管平台）可能尚未注册 Required Check（必需检查）。当前流程把“检查尚未报告”当成检查不可用并立即停止，迫使维护者人工等待后重新运行同一命令。检查通过后，规则集状态传播也可能短暂拒绝合并；现有自动合并恢复路径不能保证 PR 已实际合并便进入清理。

## Solution

PR Flow（拉取请求流程）通过一个统一的有界门禁观测过程区分检查尚未报告、检查等待、通过、失败、取消和查询不可用。`complete`（收尾）在安全期限内观测状态变化，复核源提交和目标提交，并仅在普通合并确认成功后清理；`diagnose`（诊断）复用相同状态语义但不等待。

## User Stories

1. 作为刚创建 PR 的维护者，我希望单次 `complete` 能等待 GitHub 注册检查，以便无需机械重跑。
2. 作为维护者，我希望检查尚未报告与检查查询不可用被明确区分，以便知道应等待还是排查访问问题。
3. 作为维护者，我希望已开始的检查在既有等待期限内继续被观测，以便正常路径能在同一次命令中完成。
4. 作为维护者，我希望失败检查和取消检查得到不同恢复提示，以便采取修复或重新触发动作。
5. 作为维护者，我希望未知或不可读取的检查状态安全停止并保留原始证据，以便不会误合并。
6. 作为维护者，我希望 `diagnose` 与 `complete` 使用相同状态语义，以便两个入口不会互相矛盾。
7. 作为维护者，我希望规则集状态传播延迟时流程能有界重试普通合并，以便不必人工等待后重跑。
8. 作为维护者，我希望持续的真实规则集阻塞保留平台错误，以便继续处理规则、审查或权限。
9. 作为仓库维护者，我希望每次观测和合并前都复核源提交与目标提交，以便旧门禁证据不会用于新提交。
10. 作为仓库维护者，我希望只有 PR 已确认合并后才执行清理，以免自动合并排队被误报为完成。
11. 作为仓库维护者，我不希望流程创建空提交、使用管理员绕过或无限重试，以便保留安全和审计边界。
12. 作为插件使用者，我希望通过 Pi 的 `pr_flow` 真实入口验证创建后立即收尾，以便发布形态覆盖用户可观察结果。

## Implementation Decisions

- 建立一个内部有界门禁观测 Module（模块），其 Interface（接口）返回 `NOT_REPORTED`、`PENDING`、`PASSED`、`FAILED`、`CANCELLED` 或 `UNAVAILABLE` 及观测证据；检查查询与 PR 汇总继续作为现有 GitHub CLI（命令行工具）Adapter（适配器）。
- 空的必需检查和空的 PR 检查汇总表示 `NOT_REPORTED`；网络、鉴权、格式错误或不可解释状态表示 `UNAVAILABLE`。
- `complete` 对 `NOT_REPORTED` 使用最多 60 秒的初始观测窗口，并以不超过 5 秒的间隔刷新；观测到 `PENDING` 后使用既有等待上限和轮询间隔。
- `diagnose` 只读取一次并报告当前状态；它不执行等待或合并。
- 失败和取消保持不同状态及恢复动作；流程不自动创建提交或绕过检查。
- 每轮刷新后以及合并前复核源提交和目标提交；任一变化都会使当前观测失效并安全停止。
- 必需检查通过只是合并必要条件；普通 `gh pr merge --match-head-commit` 是完整规则集的最终裁决。
- 普通合并因规则集拒绝后，流程在 60 秒内有界刷新并重试普通合并；持续拒绝时保留 `ruleset_merge_blocking` 和原始平台错误。
- 删除 `--auto`（自动合并）恢复路径。流程只有在普通合并成功后才能报告 `merge_complete` 并进入清理。
- 不新增依赖、后台任务、持久状态机或配置字段。

## Testing Decisions

- 最高公开测试 Seam（接缝）是 Pi 插件提供的 `pr_flow` 工具；真实冒烟从该入口创建 PR 后立即运行一次 `complete`，并观察最终合并与清理。
- 确定性回归通过公开 `complete` 和 `diagnose` 命令入口运行，使用现有 GitHub CLI 命令替身提供连续状态，而不是只测试单次分类函数。
- 核心回归必须覆盖 `空 + 空 → pending → pass → 合并 → 清理`。
- 其他回归覆盖永久未报告、等待超时、失败、取消、网络或格式错误、源提交变化、目标提交变化、规则集传播后成功和持续规则集阻塞。
- 删除被统一观测接缝替代的浅层实现测试；测试断言公开停止状态、恢复动作、合并命令和清理结果。
- 使用 Build and Verify（构建与验证）运行风险匹配的最终验证及快速验证，且快速验证必须选中非空检查。

## Out of Scope

- 修改 GitHub Rulesets（规则集）、CodeQL（代码扫描）、分支保护或仓库权限。
- 自动创建空提交、自动重跑无法直接重跑的动态检查或使用管理员绕过。
- 引入 GitHub SDK、后台守护进程、持久任务状态或新的用户配置项。
- 修改工作树清理、热修复、发布或其他插件流程。

## Further Notes

本变更修复 Issue #107 的共同根因，而不是继续为单个 GitHub 返回值增加分支。现有 `PUSH_REQUIRED`、`DISPATCH_REQUIRED`、`REPLY_OR_FIX_REQUIRED` 和 `EXCEPTION_REQUIRED` 顶层停止状态保持不变；新增或调整的原因必须明确对应观测状态。
