# 按场景规范 Pi 子代理调用

**Status:** ready-for-agent

## Problem Statement

主 Agent（代理）可以按任务临时选择任意子代理类型、模型、思考强度和提示词。相同的探索、实施或审查任务因此可能使用不同配置，既浪费高能力模型，也可能让低成本模型承担高风险工作。现有 Pi Subagents（Pi 子代理）扩展虽然支持持久化 Agent（代理）定义，但缺少一个会在每次子代理调用前生效的统一策略。

用户希望继续由高能力主 Agent（代理）完全决定是否、何时以及如何派遣子代理，同时让每次已经决定的派遣都按场景使用固定角色。该策略还必须发现缺失、被项目覆盖或无法使用的持久化配置，避免静默继承主 Agent（代理）模型后继续执行。

## Solution

提供 Pi 专用、可由模型自动加载的 `pi-subagent-policy` Skill（技能）。当主 Agent（代理）已经决定调用任意子代理时，该 Skill（技能）先检查当前项目中实际生效的三个持久化 Agent（代理）定义，再要求主 Agent（代理）按委托场景选择唯一匹配的角色：

- Explorer（探索者）：GPT-5.6 Luna、Low（低）思考强度，只读调查、搜索、资料整理并提供证据。
- Implementer（实施者）：GPT-5.6 Terra、Medium（中）思考强度，按已确认要求编写代码或文档并验证结果。
- Reviewer（审查者）：GPT-5.6 Sol、Medium（中）思考强度，独立只读审查代码或文档并提供带严重程度的证据。

Skill（技能）不决定是否派遣，不规定任务提示模板，也不固定前后台、并行、隔离、轮次或对话继承方式。具体委托提示完全由主 Agent（代理）编写。主 Agent（代理）在采纳结果或宣告完成前仍负责核验。

三个 Agent（代理）的角色描述、系统提示词、模型、思考强度和工具权限由 Pi Subagents（Pi 子代理）扩展持久化配置。其余内置或自定义角色不再提供。配置缺失、不匹配、被项目级配置覆盖或模型不可用时，Skill（技能）停止本次子代理调用并提示需要修复的配置；不得临时覆盖或静默降级。

## User Stories

1. 作为主 Agent（代理），我想完全保留是否派遣子代理的决定权，以便根据当前任务和上下文自行统筹工作。
2. 作为主 Agent（代理），我想在决定派遣后自动加载统一策略，以便不必记忆每个角色的模型和思考强度。
3. 作为主 Agent（代理），我想把只读调查委托给 Explorer（探索者），以便用较低成本获得可核验的信息和证据。
4. 作为主 Agent（代理），我想让 Explorer（探索者）访问代码库搜索和网页搜索，以便同一角色可以完成内部与外部资料调查。
5. 作为主 Agent（代理），我想让 Explorer（探索者）保持只读，以便调查任务不会意外改变仓库或机器状态。
6. 作为主 Agent（代理），我想把明确的代码实施委托给 Implementer（实施者），以便由均衡模型完成受约束的修改和验证。
7. 作为主 Agent（代理），我想把明确的文档实施委托给 Implementer（实施者），以便文档编写与代码编写遵守同一实施边界。
8. 作为主 Agent（代理），我想先以 Terra Medium（中）作为唯一实施配置，以便先验证综合性价比，再依据实测决定是否增加 High（高）变体。
9. 作为主 Agent（代理），我想把代码审查委托给 Reviewer（审查者），以便由更强模型独立发现实施问题。
10. 作为主 Agent（代理），我想把文档审查委托给 Reviewer（审查者），以便规格、任务和成品文档也获得独立检查。
11. 作为主 Agent（代理），我想让 Reviewer（审查者）保持只读，以便审查发现与修复责任不会混在同一个角色中。
12. 作为主 Agent（代理），我想自由编写每次委托提示，以便根据仓库、规格和任务传递恰当上下文，而不受固定模板限制。
13. 作为主 Agent（代理），我想自由选择前台、后台、并行、隔离和上下文继承方式，以便角色策略不替代我的调度判断。
14. 作为主 Agent（代理），我想在每个会话首次准备调用子代理时检查有效配置，以便尽早发现缺失或被覆盖的角色。
15. 作为主 Agent（代理），我想在模型不可用时收到明确提示，以便不会在不知情时继承主模型并违反成本策略。
16. 作为主 Agent（代理），我想只看到 Explorer、Implementer 和 Reviewer 三个可用角色，以便不会绕过策略调用其他默认角色。
17. 作为主 Agent（代理），我想让三个角色继承当前主 Agent（代理）的系统规则和仓库约束，以便委托任务继续遵守授权、安全和开发流程。
18. 作为主 Agent（代理），我想先收到子代理结果再自行核验，以便最终判断和完成声明仍由主 Agent（代理）负责。
19. 作为维护者，我想通过本地目录直接加载该 Pi package（包），以便源码保留在仓库中而无需新增安装脚本。
20. 作为维护者，我想用多个独立 Pi（编码代理）会话验证自动加载和角色选择，以便验收真实随机模型行为，而不是只检查 Markdown（标记文档）文本。
21. 作为维护者，我想覆盖错误项目配置和诱导使用其他角色的压力场景，以便证明策略在不利输入下仍会生效。
22. 作为未来维护者，我想在领域词汇表中看到三个正式角色，以便后续规格、测试和改动沿用同一语言。

## Implementation Decisions

- 本能力限定 Pi（编码代理）使用，不提供 Claude（代码代理）或 Codex（代码代理）适配。
- Skill（技能）名称固定为 `pi-subagent-policy`，并采用模型自动调用；描述明确覆盖主 Agent（代理）准备调用任意子代理的场景。
- Skill（技能）只负责调用规则和配置检查，不负责决定是否派遣子代理。
- 当前允许的角色集合是封闭的，只包含 Explorer（探索者）、Implementer（实施者）和 Reviewer（审查者）。不匹配任一角色的工作由主 Agent（代理）处理，或通过后续变更新增正式角色。
- 三个角色通过已安装的 Pi Subagents（Pi 子代理）扩展进行持久化配置。Skill（技能）不在调用时传入临时模型或思考强度。
- Explorer（探索者）固定使用 GPT-5.6 Luna 与 Low（低）思考强度，只提供读取、搜索、只读命令和网页搜索能力。
- Implementer（实施者）固定使用 GPT-5.6 Terra 与 Medium（中）思考强度，提供完成代码或文档实施所需的完整工具。
- Reviewer（审查者）固定使用 GPT-5.6 Sol 与 Medium（中）思考强度，只提供读取、搜索和只读命令能力。
- 三个角色使用 `append`（追加）提示模式，以继承主 Agent（代理）的系统规则与仓库约束。
- 三个固定角色提示词保持通用且简短；每次任务的目标、上下文、范围和交付内容完全由主 Agent（代理）决定。
- 前后台、并行、隔离、最大轮次、持久会话和上下文继承均不在角色配置中固定。
- 每个会话首次准备调用子代理时检查实际生效的角色定义，包括项目级覆盖优先级、描述、提示模式、模型、思考强度、工具权限和固定提示词。
- 配置检查失败或模型不可用时，主 Agent（代理）提示具体差异并停止本次调用。不得自动修改配置、临时覆盖或使用回退模型。
- 关闭 Pi Subagents（Pi 子代理）扩展自带的默认角色，并移除现有的其他全局角色定义，使有效角色列表只保留三个正式角色。
- Pi（编码代理）通过本地目录 package（包）能力直接加载仓库中的 Skill（技能），不新增安装或同步脚本。
- 主 Agent（代理）必须在采纳子代理结果或宣告完成前核验结果，但 Skill（技能）不规定固定核验模板或复审链。
- 在根领域词汇表中记录 Subagent role（子代理角色）及三个正式角色；不创建 ADR（架构决策记录）。

## Testing Decisions

- 测试只观察公开行为：Pi（编码代理）从本地 package（包）发现 Skill（技能），主 Agent（代理）在准备调用子代理时自动加载 Skill（技能），随后选择正确的持久化角色或在配置错误时停止。
- 唯一主要测试接缝是运行真实 Pi（编码代理）会话并观察 Skill（技能）加载与 Agent（代理）调用记录；不以直接解析 Markdown（标记文档）正文替代主验收。
- 仓库内先留下因本地 package（包）尚不存在而失败的检查，再实现最小 Skill（技能）使同一检查通过。
- 压力测试使用八个相互独立的 Pi（编码代理）会话：两个探索表述、两个实施表述、两个审查表述、一个诱导使用禁用角色或临时模型的表述，以及一个项目配置故意覆盖错误角色的场景。
- 每个正常场景必须核对 Skill（技能）确实加载、`subagent_type`（子代理类型）正确、实际模型和思考强度正确、工具权限符合角色。
- 诱导场景必须证明主 Agent（代理）不会调用 `general-purpose`、`Plan` 或临时模型配置。
- 错误配置场景使用受控项目级覆盖，不破坏真实全局配置，并证明主 Agent（代理）提示差异且没有启动子代理。
- 实施与审查压力场景使用来源明确、可清理的受控内容，不修改两个大型仓库中与本变更无关的文件。
- 完成仓库改动后使用现有 Build and Verify（构建与验证）入口执行构建检查和快速验证。
- 先完成仓库来源验证；只有获得单独的全局配置与本地 package（包）安装授权后，才执行真实全局配置调整和八会话压力测试。
- 现有本地插件 package（包）契约检查与 Pi Skill（技能）发现方式作为测试先例，不新增测试框架。

## Out of Scope

- 由 Skill（技能）决定是否或何时派遣子代理。
- 固定每次 Agent（代理）调用的任务提示模板。
- 自动把复杂 Implementer（实施者）任务升级为 High（高）思考强度。
- 新增 Implementer High（高）变体、规划角色、通用角色或其他专业角色。
- 允许调用 `general-purpose`、`Plan` 或未登记的临时角色。
- 自动修复、安装或同步用户级 Agent（代理）配置。
- 在模型不可用时自动降级或继承主 Agent（代理）模型。
- 修改 Pi（编码代理）本体或 Pi Subagents（Pi 子代理）扩展源码。
- 为 Claude（代码代理）、Codex（代码代理）或其他客户端提供相同策略。
- 修改两个大型仓库各自的业务流程或量化研究裁决边界。
- 在本轮仓库标准变更阶段修改用户级配置、安装本地 package（包）或运行压力测试。

## Further Notes

- 官方资料将 GPT-5.6 Sol 定位为旗舰模型、Terra 定位为性能与成本均衡模型、Luna 定位为高性价比模型。当前公开 API（应用程序接口）价格与本机 Pi（编码代理）模型目录中的旧价格快照存在差异，因此本策略依赖能力层级和相对定位，不把本地价格数字写成长期契约。
- Implementer（实施者）先固定为 Terra Medium（中）。只有实际实施质量不足时，后续变更才评估增加 High（高）配置。
- 压力测试用于验证模型自动调用的稳定过程，不要求每次自然语言输出完全相同。
