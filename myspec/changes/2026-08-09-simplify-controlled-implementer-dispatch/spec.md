# 收窄受控 Implementer 派发并强化 Gate 2 编排

## Problem Statement

Issue #306 暴露了可写 Implementer（实施者）可能在错误工作区执行的问题。现有 `dispatch_implementer_in_worktree` 虽能绑定工作树，却同时验证票据路径并构造固定提示词；这些流程职责使它偏离普通 Implementer 调用，也让审查修复等正常写入目标难以复用同一入口。

Issue #312 暴露了另一层问题：Implementer 的完成报告可能在没有检查新提交、差异、工作区、验证和审查证据时被当作票据完成。当前 Gate 2 文本还允许主 Agent（代理）直接实施，并把派发、验收和修复规则分散在多处，容易造成主 Agent 接管修改或在子代理返回后过早结束。

当前门禁文本还混淆了“用户已经确认”和“确认后的动作已经完成”。后续动作失败时可能错误地再次请求同一门禁，降低流程稳定性。

## Solution

把受控派发器收窄为透明的工作树适配器。调用方提供 `prompt`（提示词）、`description`（描述）、`worktree_path`（工作树路径）和 `expected_branch`（预期分支）；派发器只验证并绑定指定非主工作树，固定启动 Implementer，并原样传递提示词和描述。票据、提示词内容、提交、测试、审查和验收不进入派发器。

所有 Gate 2 流程规则集中到现有 Skill（技能）文件。顶层 Skill 只负责阶段路由、门禁顺序和强上下文指针；实施文档使用 Single Writer（单写者）规则，并按 `READY → RETURNED → ACCEPTED / REWORK_REQUIRED / BLOCKED` 的文本状态组织准备、派发、证据检查、审查修复、整合和验证。每个步骤都有可检查的完成标准。

主 Agent 负责编排、读取实际证据和调用正式验证，不直接编辑实施内容。Implementer 返回只表示 `RETURNED`（已返回）；只有实际提交、差异、工作区、验证、真实冒烟和必要审查满足不可变 Approved Ticket（已批准票据）后，流程才能进入 `ACCEPTED`（已验收）。返工和审查修复由 Development Flow 构造新的自包含提示词，再通过同一透明派发器执行。

每个 Gate Confirmation（门禁确认）只请求一次，并在确认后的执行和恢复期间持续有效。后续动作失败时只报告准确恢复动作；需要新增危险授权时只请求该动作，不重新开放已经确认的门禁。恢复成功后自动进入下一门禁。

## User Stories

1. 作为开发流程使用者，我希望 Implementer 被强制绑定到指定工作树，避免修改主工作区或错误功能分支。
2. 作为主 Agent，我希望自己构造的提示词和描述原样交给 Implementer，不被派发器补写或解释。
3. 作为维护者，我希望票据格式变化不会要求修改派发器。
4. 作为维护者，我希望派发器不理解提交、测试、审查、验收或流程状态。
5. 作为流程使用者，我希望 Gate 2 的实施和审查修复只有一个受控可写入口。
6. 作为流程使用者，我希望主 Agent 不直接接管 Implementer 的未完成修改。
7. 作为 Implementer，我希望每次收到一个无需父会话即可执行和停止的自包含写入目标。
8. 作为 Reviewer（审查者），我希望以 Gate 1 已批准且不可变的票据作为审查基准。
9. 作为流程使用者，我希望子代理返回后必须检查实际证据，而不是相信完成报告。
10. 作为流程使用者，我希望证据不足或审查失败时通过新的 Implementer 派发返工。
11. 作为恢复流程的使用者，我希望缺失证据可以从 Git（版本管理）和重新验证中恢复，而不依赖额外状态文件。
12. 作为流程使用者，我希望一个门禁只确认一次，后续失败恢复不会再次索要同一确认。

## Implementation Decisions

- 保留 `dispatch_implementer_in_worktree` 作为唯一受控可写 Implementer 入口。
- 派发接口只公开提示词、描述、目标工作树和预期分支；角色固定为 Implementer。
- 工作树限制包括绝对路径、Git 工作树根、登记状态、非主工作树和预期分支校验，并把规范路径设为实际工作目录。
- `prompt` 和 `description` 按调用值原样传递；派发器不生成、追加、改写或解释提示词。
- 删除 `ticket_path`、票据路径检查、固定票据提示词及派发器中的流程语义。
- 派发器不增加特殊模型、思考强度、资源模式、恢复、超时或状态行为；持久角色配置和普通 Implementer 生命周期继续保持权威。
- 保留直接 `Agent` 调用护栏，继续阻断 Implementer、未知角色和恢复型可写调用绕过受控入口。
- Gate 2 使用 Single Writer：Git 可见的实施、测试、必要整合和审查修复由绑定工作树的 Implementer 完成；Reviewer 只报告，主 Agent 只编排和验收。
- 每次写入派发只有一个明确目标；票据实施目标只对应一张已发布票据。
- Development Flow 在现有实施文档中维护自包含提示词短清单，不新增模板文件，也不把固定模板移入派发器。
- 提示词包含可观察结果、不可变验收标准、相关源码和审查发现、固定验证基线、红灯/绿灯与真实冒烟、预期 Git 结束形态和停止条件。
- Approved Ticket 在 Gate 2 期间不写回实施证据或修订；需求改变时返回需求阶段。
- `RETURNED` 必须进入实际证据检查。证据满足时进入 `ACCEPTED`，可修复时进入 `REWORK_REQUIRED`，来源不明或无法安全判断时进入 `BLOCKED`。
- 审查阻断项由新的自包含提示词重新派发给 Implementer；修复后只复审修复差异和受影响行为。
- Gate 确认与确认后执行分离：确认只消费一次，恢复状态保留确认并指向失败动作。
- 不新增 Skill、引用文件、运行时状态机、证据账本、公开验证工具或依赖。
- 只优化本次 Gate 2 执行路径和一次性门禁确认相关文本，不全面重写其他流程文档。

## Testing Decisions

- 最高公开测试接缝是由真实 Pi Package（包）加载的 Development Flow 和 `dispatch_implementer_in_worktree` 工具。
- 派发接口检查使用任意提示词和描述，严格断言 RPC（远程调用）收到的值未改变、角色为 Implementer、实际工作目录为规范目标工作树。
- 删除票据路径拒绝检查；保留主工作树、错误分支、未登记路径、取消、正常生命周期和直接可写 Agent 阻断回归。
- Skill 文本契约检查关键标题、步骤完成标准、五个文本状态、自包含提示词清单、全新派发修复循环和一次性门禁确认；不复制整篇文案到测试。
- 回归必须证明 Skill 不再允许主 Agent 直接实施，不再声明派发器构造提示词或验证票据路径，也不把 `RETURNED` 当成 `ACCEPTED`。
- 真实 Pi 冒烟在临时主工作区和已有功能工作树运行：第一次 Implementer 返回但没有合格提交或留下脏状态时，流程进入返工而不接受票据；第二次以新的自包含提示词派发，只有聚焦提交、干净工作区、限定差异、验证和审查满足后才接受。
- Reviewer 返回阻断项时，真实入口应观察到新的工作树绑定派发和后续定向复审。
- 主工作区及已知副作用目录在真实冒烟前后保持不变。
- 使用固定 Git 基线运行 Build and Verify（构建与验证）；`status: skipped` 或空 `checked` 不算通过。
- 高风险完成证据包括受影响自动检查、真实 Pi 主路径及失败恢复路径、风险匹配验证和有边界的整体审查。

## Out of Scope

- 不修改 Pi 本体、Pi 安装目录或第三方子代理源码。
- 不增加新的 Skill、引用文件或提示词模板。
- 不增加主 Agent 工作树切换、双实施路径、hotfix（热修复）路径或 session handoff（会话交接）。
- 不在派发器中解析票据、构造提示词、检查提交、运行测试、执行审查或判断验收。
- 不增加运行时流程状态机、证据文件或通用写入沙箱。
- 不修改持久角色的模型、思考强度、工具或 Skill 配置。
- 不为旧 session 中的旧派发参数增加兼容层。
- 不全面重写 Gate 1、Gate 3 或 Delivery（交付）流程。
- 不执行插件安装、客户端同步、市场刷新、发布或 PR（拉取请求）交付。

## Further Notes

本变更属于 High risk（高风险），因为它修改唯一可写实施接缝和公开工具契约。Skill 文本不能替代运行时沙箱；本变更保留现有直接调用护栏，并通过清晰步骤、完成标准和真实 Pi 冒烟降低职责漂移风险，但不宣称主 Agent 的所有文件系统副作用都受到运行时阻断。
