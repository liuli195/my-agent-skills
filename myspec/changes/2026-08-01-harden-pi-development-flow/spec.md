# 强化 Pi Development Flow（Pi 开发流程）关键边界

## Problem Statement

Pi Development Flow（Pi 开发流程）已经规定需求确认、纵向票据、子代理实施和交付清理步骤，但四个关键边界仍依赖普通说明文字：需求阶段可能把 `grill-with-docs`（带文档拷问）静默替换为普通 `grilling`（拷问）并漏掉 `domain-modeling`（领域建模）；多张独立票据可能被合并到一次 Implementer（实施者）调用；子代理工作目录只写在提示中而没有由工具强制绑定到目标工作树；未请求的本地安装、客户端同步和 Release Flow（发布流程）可能被误判为开发完成门槛。

这些问题会造成需求入口失效、票据边界失效、主工作区污染和越权修改机器状态。

## Solution

分别修复四个边界：为需求阶段增加明确的 MUST（强制）块；在实施阶段定义“主 Agent（代理）可直接实施，但每次 Implementer 委派只能绑定一张票据”；增加最小 Pi Extension（Pi 扩展）包装入口，通过 `subagents:rpc:spawn`（子代理跨扩展调用）的 `options.cwd`（工作目录选项）强制绑定已有工作树；把本地安装、客户端同步、市场刷新和 Release Flow 默认排除在开发流程之外，仅响应用户明确提出的具体操作。

## User Stories

1. 作为开发流程使用者，我希望需求讨论使用准确的技能入口，以免需求在错误入口下继续推进。
2. 作为开发流程使用者，我希望普通 `grilling`（拷问）不能替代 `grill-with-docs`（带文档拷问）。
3. 作为开发流程使用者，我希望需求阶段必须使用 `domain-modeling`（领域建模），以便规格和票据使用一致术语。
4. 作为开发流程使用者，我希望指定 Skill（技能）不可用时流程停止，而不是静默降级。
5. 作为主 Agent（代理），我希望可以在功能工作树中逐票直接实施顺序任务，而不被强制调用子代理。
6. 作为开发流程使用者，我希望无论直接实施还是委派，每张票据都有独立实现和验收边界。
7. 作为开发流程使用者，我希望每次 Implementer（实施者）调用只负责一张已发布票据。
8. 作为开发流程使用者，我希望无法独立实施的票据返回票据设计阶段，而不是在派发时临时合并。
9. 作为主 Agent，我希望子代理由工具强制运行在目标工作树，以免依赖提示中的 `cd`（切换目录）。
10. 作为开发流程使用者，我希望不能证明目标工作树和分支时拒绝派发可写子代理。
11. 作为仓库维护者，我希望子代理的编辑、检查、缓存和运行产物不会误落到主工作区。
12. 作为开发流程使用者，我希望子代理完成后正常退出，不留下阻止主进程结束的残留生命周期。
13. 作为开发流程使用者，我希望 PR（拉取请求）合并、主干同步和安全清理完成后能够正常结束开发流程。
14. 作为开发流程使用者，我希望没有明确请求时，流程不询问或执行任何本地安装、客户端同步、市场刷新或发布。
15. 作为开发流程使用者，我希望“继续收尾”只恢复已经授权的步骤，不能产生新的机器状态修改授权。
16. 作为开发流程使用者，我希望 Codex/Claude（代码代理）市场仍为旧版本时，不会因此阻塞开发流程完成。
17. 作为开发流程使用者，我希望明确要求某个具体本地动作时，流程只执行并验证该动作，不扩大到其他客户端或发布操作。

## Implementation Decisions

### 需求阶段 MUST（强制）块

- Requirements（需求）阶段增加一个独立、醒目的 MUST（强制）块，不把核心规则埋在普通步骤中。
- 单会话需求讨论开始前，当前会话必须真实读取 `grill-with-docs`（带文档拷问），并按照它的要求真实读取和使用 `domain-modeling`（领域建模）。
- 禁止使用普通 `grilling`（拷问）替代 `grill-with-docs`。
- 任一指定 Skill（技能）缺失、不可读或加载失败时必须停止并报告。
- 调用 `to-spec`（生成规格）和 `to-tickets`（拆分票据）前，必须能从当前会话工具记录确认两个指定 Skill 已加载。
- 不新增由模型自行维护的状态文件、布尔标记或伪运行时门禁。
- MUST（强制）块只用于这项会破坏整个需求阶段的核心规则，其余执行规则仍放在实际步骤中。

### 主 Agent 决定实施方式，委派时一票一次调用

- Development Flow 不强制顺序票据使用子代理；主 Agent 根据风险、上下文规模和委派收益决定直接实施或委派。
- 对于顺序票据，主 Agent 可以在同一个功能工作树中逐票直接实施，不产生子代理调用。
- 直接实施仍须完成当前票据的实现、检查和验收后再进入下一票。
- 如果决定委派，一次 Implementer（实施者）调用必须且只能绑定一张已发布票据，不得为了减少调用次数合并多票。
- 顺序票据可以复用同一个功能工作树，但每张被委派的票据使用独立调用，并在上一票验收后再派发下一票。
- 允许混合实施，例如主 Agent 直接实施票据 1 和 3，只把票据 2 委派给 Implementer。
- 并行票据如果委派，仍须一张票据、一个子代理调用和一个对应工作树。
- 如果一张票据无法独立实施或验证，返回 `to-tickets`（拆分票据）重新设计，不在派发时合并。
- 是否委派遵循 `pi-subagent-policy`（Pi 子代理策略）；票据存在本身不构成必须委派的理由。

### 工具级工作树绑定

- 增加一个最小 Pi Extension（Pi 扩展）包装入口，只负责安全派发 Implementer（实施者）。
- 包装入口复用现有 `subagents:rpc:spawn`（子代理跨扩展调用），不重新实现子代理运行器。
- 包装入口只接受一张位于目标工作树、状态为 `ready-for-agent` 的已发布票据路径，并由工具构造固定提示；不接受可夹带多票的任意派发提示。
- 通过 `options.cwd`（工作目录选项）传入目标工作树的规范绝对路径，并固定使用现有 Implementer 角色配置。
- 以 isolated（隔离）模式启动 Implementer，只保留内置工具，避免子会话扩展或 MCP（模型上下文协议）资源阻止外层 Pi 进程退出；只有票据明确需要并提供对应生命周期验证时才扩大工具范围。
- 派发前确认目标路径是当前仓库登记的已有 Git worktree（Git 工作树），且当前分支与调用方声明的预期分支一致。
- 不依赖提示中的 `cd`（切换目录），也不自动创建额外工作树。
- RPC（跨扩展调用）不可用、工作树不唯一、分支不匹配或无法强制工作目录时，在派发前失败并给出从目标工作树交接 Pi（编码代理）会话的方法。
- 不采用 Orca（代理开发环境）作为正式路径或隐式后备路径。
- 实现前先诊断真实测试中“已经返回完成结果但外层 Pi 进程没有退出”的原因；只有“派发、子代理完成、结果返回、资源释放、外层进程退出”的生命周期得到证明后才能交付。
- 等待完成必须有固定上限；超时或取消时停止对应子代理并释放事件监听器。

### 默认排除本地交付和发布

- Development Flow 默认只包含 PR（拉取请求）交付、目标分支同步和安全清理。
- 默认不包含 Pi 本地安装、Codex/Claude（代码代理）客户端同步、市场刷新、Release Flow（发布流程）或发布后市场同步。
- 不主动列出这些可选动作，也不询问用户是否需要。
- 只有用户明确提出具体目标和动作时才执行并验证该项。
- “继续收尾”“完成剩余流程”等一般表达只能恢复当前已授权步骤，不能产生新的本地安装、同步或发布授权。
- 未请求动作不进入完成条件，也不作为阻塞项或主动报告的后续任务。
- 如果明确请求的客户端同步依赖尚未授权的发布，不得自动发布；单独报告该请求无法完成，但已完成的 Development Flow 仍可正常结束。
- 正式 MySpec（自有规格）的完成场景同步移除“本地交付默认属于完成条件”的含义。

## Testing Decisions

- 使用已有 Pi Package（Pi 包）真实资源加载入口验证 Skill（技能）契约，不新增文档解析框架。
- 使用真实 Pi 新进程验证需求入口确实加载 `grill-with-docs`（带文档拷问）和 `domain-modeling`（领域建模），并验证交付阶段在未请求时不询问、不执行、不列出本地动作。
- 使用三张顺序纵向票据覆盖全部直接实施、全部委派、混合实施和非法多票委派四种场景。
- 全部直接实施允许零次子代理调用，但必须保留三个验收节点；全部委派必须产生三次独立 Implementer 调用；混合实施只为被委派票据产生调用。
- 在临时 Git 仓库创建主工作区和已有功能工作树，通过真实 RPC（跨扩展调用）验证子代理目录、分支、编辑和运行产物都位于目标工作树。
- 对比主工作区前后的 Git 可见内容及预先记录的已知缓存、脚本缓存和验证产物目录。
- 验证分支不匹配和非工作树路径在子代理启动前失败。
- 验证完成结果返回后，外层 Pi 进程在限定时间内退出，且没有属于本次测试的残留子进程。
- 所有正式检查通过 Build and Verify（构建与验证）入口运行。

## Out of Scope

- 不建设通用子代理编排框架。
- 不替换 `@tintinweb/pi-subagents`（Pi 子代理扩展）。
- 不使用 Orca（代理开发环境）承担正式派发。
- 不自动创建票据工作树。
- 不强制主 Agent 为顺序票据调用子代理。
- 不修改 Release Flow（发布流程）或 Plugin Sync（插件同步）的内部行为。
- 不执行任何实际本地安装、客户端刷新或发布。
- 不把普通规则全部升级为 MUST（强制）块。
- 不修改 Pi 本体或全局 Pi 安装目录。

## Further Notes

本变更属于 High risk（高风险）Flow Level（流程等级），因为它同时涉及 P1（高优先级）流程失效、可写子代理的工作区隔离和机器状态授权边界。

四个问题保持四张独立票据。票据在需求上没有真实前置依赖；由于修改相邻流程内容和共同测试入口，在一个功能工作树中顺序实施并逐票验收，不制造虚假并行。
