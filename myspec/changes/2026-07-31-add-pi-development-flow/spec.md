# Pi Development Flow（Pi 开发流程）

## Problem Statement

当前仓库缺少一个 Pi（编码代理）专用入口，用于把需求确认、隔离实施、验证审查、规格固化、PR（拉取请求）交付和安全清理组织为可恢复的完整 Development Flow（开发流程）。现有能力彼此独立，容易造成重复预检、过度审查、过重回归、无效并行或未经授权直接实施。

## Solution

提供 `pi-development-flow`（Pi 开发流程）Skill（技能），按 Flow Level（流程等级）编排现有 Skill，使用需求确认、实施、清理收尾三个阶段和四个独立门禁，并通过渐进式披露只在需要时加载阶段规则。流程只在真实需要时启用并行、集成分支、关键任务审查和高强度验证。

## User Stories

1. 作为开发者，我希望通过一个入口启动完整开发变更，以便不必手工串联多个 Skill（技能）。
2. 作为开发者，我希望继续已有 MySpec（自有规格）变更，以便跨会话恢复。
3. 作为开发者，我希望初始化只在明确请求或正式入口报错时检查，以免重复消耗上下文。
4. 作为开发者，我希望缺失前置项时委托已有初始化入口，以免流程重复实现初始化能力。
5. 作为开发者，我希望没有正式初始化入口时明确停止，以免生成未经验证的仓库基础设施。
6. 作为开发者，我希望按决策规模选择需求讨论方式，以免简单需求进入大型规划流程。
7. 作为开发者，我希望确认的领域术语与规格和票据同时落盘，以免污染主仓库。
8. 作为开发者，我希望实施票据均为可独立验证的纵向切片，以便每张票据产生完整结果。
9. 作为开发者，我希望创建需求产物不自动授权代码实施，以便先审阅具体实施计划。
10. 作为开发者，我希望实施计划以表格展示并行分组、执行角色、验证和审查门禁，以便快速判断成本。
11. 作为开发者，我希望没有真实并行需求时只使用单一功能分支和工作树，以免产生无收益的整合成本。
12. 作为开发者，我希望有真实并行需求时使用集成分支和独立票据工作树，以便隔离修改。
13. 作为开发者，我希望并行数量由主 Agent（代理）根据依赖、冲突和资源判断，以免固定上限造成空转。
14. 作为开发者，我希望所有子代理遵循 Pi 子代理策略，以便角色和模型配置保持一致。
15. 作为开发者，我希望功能、缺陷和集成行为先出现失败检查再实现，以便证明测试对目标行为敏感。
16. 作为开发者，我希望普通票据不强制单独审查，以降低审查成本。
17. 作为开发者，我希望关键任务整合前接受限定范围审查，以免错误成为后续工作的基础。
18. 作为开发者，我希望整体审查关注最终差异和跨票据组合，以免重复深挖已审查且未变化的局部实现。
19. 作为开发者，我希望审查修复只定向复核受影响差异，以免陷入无限重复审查。
20. 作为开发者，我希望票据只保存行为验证证据，以免重复记录 Git（版本管理）已有状态。
21. 作为开发者，我希望票据阶段使用最小行为检查而不是完整端到端回归，以降低重复验证成本。
22. 作为开发者，我希望最终验证从真实用户入口或发布形态运行风险匹配的冒烟，以保留用户层质量证据。
23. 作为开发者，我希望高风险、安全和数据完整性路径不能被冒烟策略错误省略。
24. 作为开发者，我希望整体审查和验证完成后再固化正式规格，以免把待修正行为写入长期事实源。
25. 作为开发者，我希望冲突能从规格和证据判断时由主 Agent（代理）解决，语义互斥时才暂停询问。
26. 作为开发者，我希望票据整合验证后由主 Agent（代理）自动安全清理，以免产生重复确认。
27. 作为开发者，我希望 PR（拉取请求）实际合并、目标分支同步和现场清理后才宣告完成。
28. 作为开发者，我希望暂停时保留现场，取消时必须明确授权，以免丢失未整合成果。
29. 作为开发者，我希望 Skill（技能）使用渐进式披露，以免每次调用加载完整流程规则。
30. 作为开发者，我希望通过用户级本地目录安装该 Skill，以便在第三方 GitHub 仓库复用。
31. 作为开发者，我希望合并前通过隔离 Pi（编码代理）包加载验证，合并后再从稳定主仓库路径安装。
32. 作为仓库维护者，我希望验证规则不再无条件要求完整端到端回归，以便按风险平衡成本和质量。

## Implementation Decisions

- 第一版仅支持 Pi（编码代理）和 GitHub（代码托管平台）仓库。
- 固定阶段为需求确认、实施、清理收尾。
- 固定门禁为需求产物确认、实施授权、正式规格确认和交付授权；创建需求产物不得被视为实施授权。
- 使用轻量、标准和高风险三级 Flow Level（流程等级）；受保护类别不得降级。
- 单会话可厘清需求使用带领域建模的拷问；跨会话依赖决策使用路径规划。
- 需求地图、决策、规格和实施票据统一保存在同一 MySpec（自有规格）变更中。
- 主 Skill 只保留入口、阶段顺序、门禁和完成条件；初始化、需求、实施、交付和恢复规则按需加载。
- 使用 `writing-great-skills`（优秀技能编写）指导内容层级、上下文指针和删重。
- 无并行时使用单一功能分支和工作树；有真实并行时才建立集成分支及票据工作树。
- 每个工作树必须使用目标仓库已有初始化入口。
- 子代理是否使用及并行数量由主 Agent（代理）决定。
- 审查复用现有双轴方法，只补充关键任务触发、上下文边界、小补丁范围、定向复核和组合审查规则。
- 正式规格在整体审查及修复验证完成后固化，不进入代码审查范围。
- 不新增流程状态机、Hook（钩子）、初始化脚本或其他运行时代码。
- 初始化只检查并委托正式入口；正常运行不重复预检。
- 用户级安装引用主仓库中的本地包目录，不复制技能来源。
- 暂停保留现场；取消只有在明确授权且能够证明安全时才执行非强制清理。

## Testing Decisions

- 通过 Pi（编码代理）真实包资源加载器验证本地目录包发现，而不是直接解析 Markdown（标记文档）。
- 测试确认技能来源、名称、调用元数据和按需参考文件均可用。
- 合并前使用隔离 Pi 配置运行一次真实技能调用冒烟。
- 合并后验证用户级本地安装、技能发现和新进程调用。
- 功能实施遵循同一检查的红灯和绿灯循环。
- Build and Verify（构建与验证）仍是唯一构建检查与验证入口。
- 票据阶段运行目标行为检查，整合阶段运行快速验证，最终按风险运行真实入口冒烟。
- 外部客户端或系统适配完成后立即运行该端最小真实冒烟。
- 不为每个说明段落建立脆弱的关键词测试。

## Out of Scope

- Claude/Codex（代码代理）适配。
- GitHub（代码托管平台）以外的托管平台。
- 自动生成第三方仓库的 CI（持续集成）或工作树初始化脚本。
- 独立状态机、运行时扩展或强制 Hook（钩子）。
- npm（包管理平台）或 Git（版本管理）远端安装。
- 自动移动 MySpec（自有规格）变更目录到归档目录。
- 修改全局 `/code-review`（代码审查）或其他依赖 Skill（技能）。
