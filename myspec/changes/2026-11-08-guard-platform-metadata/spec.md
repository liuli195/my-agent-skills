# 普通守卫平台元数据传递修复

**Status（状态）：** `ready-for-human`；门禁一已确认，本仓库实施、快速验证和独立审查完成，等待门禁二；跨平台持续集成、发布及 Quant（量化项目）消费验收尚未完成。

## Problem Statement（问题）

Quant（量化研究项目）的既有完整验证在 Windows（视窗系统）多组并行时，普通受保护工作进程首次读取标准平台信息会重新查询系统；系统查询超时后尝试启动系统命令，被守卫正确拒绝，导致正常测试失败。已复现的是平台元数据传播缺口，不是文档业务错误，也未证明操作系统内部超时的最终原因。

完整现场为运行 42416161815、任务 128534614535：保持原14组、检查间并行7、每组2个工作进程，记录8次操作系统查询超时、24次被拒绝的回退启动、4个失败组，416项断言通过。不能把单组偶尔通过或重跑通过当作问题消失。

## Solution（解决方式）

一次验证真正需要执行普通检查时，由可信父进程只采集一次完整平台元数据快照，供本次根进程和全部受支持本地工作进程使用。在项目加载前恢复快照，正常读取不再重新探测系统。全部守卫拒绝、违规证据、并行和失败退出规则保持不变。

## User Stories（用户故事）

1. 作为验证使用者，我希望普通测试读取平台信息不会被误判为业务启动系统命令，以便正常计算顺利完成。
2. 作为验证使用者，我希望根进程与工作进程看到同一份完整平台信息，包括处理器和合法空字段，以便不因首次导入或延迟查询失败。
3. 作为安全边界维护者，我希望真实的业务进程启动仍被拒绝，吞掉异常也不能变成成功。
4. 作为并行验证使用者，我希望保持原两层并行，不以串行或角色放宽换取通过。
5. 作为缓存使用者，我希望旧守卫产生的成功缓存不能冒充修复后的验证结果。
6. 作为使用者，我希望元数据采集或传递失败时明确失败，而不是收到伪造、缺字段或静默降级的信息。
7. 作为使用者，我希望全缓存命中、仅真实检查及旧模式不会因本次修复增加平台采集开销。
8. 作为维护者，我希望沿用现有发布入口和测试，不增加重度固定冒烟或平行验证框架。
9. 作为 Quant 使用者，我希望现有拉取请求消费修复后的精确构建与验证来源，在原完整验证配置下真实通过。
10. 作为仓库所有者，我希望永久保存完整需求规格和票据，但清理本次临时诊断数据、临时工作区和过程产物，不留恢复包。

11. 作为仓库维护者，我希望近期新写的正式规格只描述可观察行为，避免把内部算法、文件或装配位置固化为产品要求，同时保持已经批准的功能、安全与性能约束。

## Implementation Decisions（实现决策）

- 流程等级为 Full（完整），因为改动涉及守卫安全边界及跨项目工具消费。架构阶段由用户指定的 GPT-6-A 中等强度只读子代理完成，实际使用代码库设计、带文档追问、追问和领域建模技能；没有未解决的架构选型。
- “平台元数据快照”限定为一次验证调用内的数据，不是磁盘缓存，也不是进程全局跨调用缓存。其内容为默认平台字符串及已物化的六个标准系统字段；合法空字符串不能视为缺失。
- 父进程在确认普通待执行检查且尚可调度后采集一次，再交给各组；覆盖现有两条调度路径，不在各调度线程重复采集。
- 复用既有内部命令参数传结构化快照；根进程在站点与项目导入前恢复，工作进程转发同一载荷，不重新采样或调用系统命令补全。
- 保留现有 Python（编程语言）3.12以上支持边界；标准系统结果的构造与延迟处理器字段分别正确恢复，不增加新兼容层。
- 严格拒绝非法结构、长度或类型。父采集失败、子进程解码失败必须明确失败，不启动伪造快照的普通检查，也不写入通过缓存。
- 升级既有适配器版本，使旧通过缓存失效；不改变配置格式、公开命令、命令参数、字符串与列表语义、引号、空格、中文及 Node.js（节点运行时）分支。
- 不增加系统命令白名单，不关闭系统查询，不放宽真实角色，不降低并行，不更改 Quant 业务、测试组、预算或 MySpec（自有规格）来源。
- 工具修复经验证与独立审查后使用现有发布流程；预计仅构建与验证插件由2.9.2升2.9.3，最终以发布预检核实。正式发布与合并仍遵循对应门禁。
- Quant 复用现有第52号拉取请求，只更新构建与验证工具的精确来源提交和实现身份；保留自有规格项及开发模式。先补齐该请求内与新增消费改动对应的需求票据，再验收，不另建重复修复请求。
- 主规格的可观察行为增量留在第二门禁，经已核验的随包 MySpec 命令完成分析、预览、完整差异、最终确认后才应用；本需求准备不修改主规格或其锁。
