# 统一开发工具身份并解耦 MySpec 目标工作树

**Status（状态）：** ready-for-agent

## Problem Statement（问题说明）

开发模式通过机器级 `npm link`（本地链接）为 MySpec（自有规格）和 Build and Verify（构建与验证）选择本地源码实现。当前 MySpec 把 Source Worktree（源码工作树）与 Target Worktree（目标工作树）相同作为写入条件，导致主工作树提供工具实现时，独立功能工作树无法完成正式规格流程。

现有开发 Toolchain Identity（工具链身份）又使用整个源码工作树的当前提交。PR Flow（拉取请求流程）在同一工作树写入工具链记录和生成工作流后，即使工具实现没有变化，提交身份也会变化，因此只能通过临时的同工作树阻断避免自引用。Build and Verify 的验证缓存则只绑定发布包版本，开发实现变化但包版本未变时可能复用旧实现生成的缓存。

工具来源与规格数据目标也没有形成统一的运行约束。调用方一旦混用不同工作树的规格和预览，或把已删除的预览目录交给差异命令，可能得到与目标工作树不一致的结果。

## Solution（方案）

保留机器级开发和发布模式。开发模式下，每个工具继续通过一次显式 `npm link` 指向长期存在的本地主工作树；所有目标工作树统一运行该实现，不复制运行包，也不根据当前目录自动切换源码。发布模式继续运行固定发布包，只有显式更新才升级。

为 MySpec 和 Build and Verify 分别计算 Tool Implementation Closure（工具实现闭包）身份。每个身份只覆盖决定该工具实际运行和受控打包结果的插件内容与共享生命周期输入，不覆盖工具链记录、生成工作流、规格、测试或普通仓库配置。单独修改一个插件只改变该插件身份；修改两个插件共同使用的生命周期输入会同时改变两者身份。

开发运行使用实现闭包的稳定内容身份。需要由 PR Flow 和 CI（持续集成）复现时，工具链记录引用最近一次实际改变该闭包、且能重建相同内容的源码提交，而不是整个工作树当前提交。没有可复现提交时不得发布一个看似有效的开发工具链记录。

MySpec 的一次规格运行固定精确目标工作树、规格根、Delta（增量规格）根、预览根、规格与输入指纹以及 MySpec 实现身份。源码工作树只提供代码，不参与推导规格数据路径。预览、差异和最终应用必须使用同一运行上下文；最终替换结果必须与用户确认的预览一致。

当目标规格、输入或 MySpec 实现身份变化时，旧预览失效并使用当前主工作树实现重新生成。重新生成后的可观察差异不变时可以沿用原确认；差异改变时必须重新展示并确认。跨工作树数据路径、缺失预览、失效指纹或无法确认的实现身份必须在写入前停止。

Build and Verify 的 fast verify（快速验证）与 full verify（完整验证）缓存使用当前工具实现身份。开发实现变化自动失效旧缓存；项目配置、命令和输入仍通过各自现有摘要参与缓存判断，但不改变工具身份。旧缓存不需要人工删除。

PR Flow 分别记录 MySpec 与 Build and Verify 的稳定身份。工具链记录和生成工作流提交不改变任一身份；同一工作树第一次同步写入所需文件，之后在实现未变时再次运行保持无差异，不再使用同工作树临时阻断。

## User Stories（用户故事）

1. 作为 MySpec 使用者，我希望开发模式只绑定一次本地主工作树，从而可以在任意目标工作树直接使用裸 `myspec`。
2. 作为规格维护者，我希望工具源码位置与规格数据目标严格分离，从而不会把主工作树规格和功能工作树预览混在一起。
3. 作为规格审批者，我希望最终应用与已确认预览一致，从而工具或输入变化不会绕过确认。
4. 作为多工作树使用者，我希望每个目标工作树继续拥有独立的规格状态和锁，从而不同目标可以独立运行。
5. 作为 MySpec 开发者，我希望实际工具实现变化会使旧预览失效，而普通配置变化不会被误判为实现变化。
6. 作为 Build and Verify 使用者，我希望开发工具实现变化会自动失效旧验证缓存，从而不会复用另一份实现产生的通过结果。
7. 作为 Build and Verify 使用者，我希望项目配置和输入仍按自身变化控制缓存，从而工具身份不会承担无关职责。
8. 作为工具维护者，我希望 MySpec 与 Build and Verify 拥有独立身份，从而修改其中一个不会无故更新另一个。
9. 作为共享生命周期维护者，我希望共享实现变化同时更新两个工具身份，从而两个插件都不会漏掉共同运行逻辑的变化。
10. 作为 PR Flow 使用者，我希望在工具源码与交付目标为同一工作树时也能完成工具链同步，从而无需临时切换发布模式。
11. 作为 CI 使用者，我希望开发工具链记录能检出精确重建该实现的提交，从而本地身份可以在远端复现。
12. 作为发布模式使用者，我希望固定包版本和显式更新行为保持不变，从而本次修复不会改变发布生命周期。
13. 作为功能分支开发者，我希望分支中的工具修改继续通过受控 Tarball（压缩包）和统一验证入口测试，而不是改变全局裸命令绑定。

## Implementation Decisions（实现决定）

- Toolchain Identity 继续作为生命周期和 PR Flow 的公共身份接口，但开发身份改为实际工具实现闭包，而不是整个工作树当前提交。
- 实现闭包由受控打包输入定义；两个插件分别拥有自己的闭包，共享生命周期输入同时属于两个闭包。
- MySpec 的运行状态保存目标路径、规格与输入指纹、预览身份和实现身份；旧状态缺少必要身份时按失效处理，不静默信任。
- Source Worktree 与 Target Worktree 不同只作为诊断信息，不再构成写入错误。
- MySpec 的目标工作树使用精确工作树根区分；共享同一个 Git（版本管理）仓库不代表属于同一目标工作树。
- 缺失预览必须显式失败，不再等价为空规格目录。
- 最终应用复核已确认预览的身份和内容，并保持现有原子替换及失败恢复保证。
- Build and Verify 缓存继续同时考虑配置、命令、输入和运行环境；仅把原有发布版本字段扩展为发布版本或开发实现身份。
- PR Flow 只消费两个工具已经公开验证的身份，不重新实现每个插件的身份算法。
- 不增加新的用户命令；现有 `doctor`、裸工具命令和 PR Flow 入口继续承担公开诊断与操作。
- 不创建 ADR（架构决策记录）；该选择可通过后续实现替换，当前变更规格已足以保存取舍。

## Testing Decisions（测试决定）

- 最高公开测试接缝是受控打包并安装后的裸 CLI（命令行程序），以及公开 PR Flow 入口；私有函数测试不能替代这些入口。
- MySpec 票据通过真实开发绑定和两个关联工作树运行 `doctor`、状态命令、预览、差异及最终应用，断言只修改目标工作树且结果与预览一致。
- MySpec 测试覆盖源码与目标不同、缺失预览、跨工作树路径、规格或输入变化、实现变化后差异相同和差异改变。
- Build and Verify 票据连续运行公开 `doctor` 和 `verify`，证明缓存命中、开发实现变化失效、无关仓库变化不改变工具身份，以及配置变化仍通过配置摘要失效。
- 双插件身份测试覆盖：只改 MySpec、只改 Build and Verify、修改共享生命周期输入、修改排除项四种情况。
- PR Flow 票据通过同一工作树公开入口完成第一次同步和第二次无差异运行，并验证两个工具身份可以独立更新且 CI 检出提交能够重建记录内容。
- 每张票据完成时运行对应真实用户入口冒烟；整体完成后通过 Build and Verify 运行风险匹配的最终验证和非空 fast verify（快速验证）。

## Out of Scope（范围外）

- 不为每个工作树创建独立工具安装、运行包或 `npm link`。
- 不复制运行时快照到目标工作树。
- 不根据当前目录自动切换机器级开发源码绑定。
- 不自动同步或拉取远端主分支。
- 不要求功能工作树中的工具源码通过全局裸 CLI 自举；该源码继续使用受控打包测试。
- 不新增仓库级全局规格锁，也不改变不同目标工作树的现有锁隔离。
- 不改变发布模式的固定包版本、显式更新及客户端同步边界。
- 不在 Gate 3（第三门禁）中打包、安装、切换模式或修复工具环境。
- 不执行本地插件安装、客户端同步、市场刷新或发布。

## Further Notes（补充说明）

本变更解决 GitHub Issue（问题）#296。三个实施票据严格按公开工具纵向切分：先完整跑通 MySpec，再完整跑通 Build and Verify，最后使用两个已验证身份跑通 PR Flow。共享代码不单独形成水平票据。
