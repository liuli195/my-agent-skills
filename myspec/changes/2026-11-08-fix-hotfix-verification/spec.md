# 热修复完整验证真实性

**Status（状态）:** ready-for-agent

## Problem Statement（问题陈述）

维护者通过 PR Flow（拉取请求流程）的 hotfix（热修复）入口直推受保护目标分支前，需要可信的完整验证。当前入口会消费受管工具映射，却让验证子进程继续继承该映射，而且仅凭退出码为 0 判断验证通过。这不能证明检查真实执行、非空且通过，可能导致未完成有效验证的热修复被推送，并留下成功审计。

历史本机审计出现过标准输出为空、标准错误包含 Node（运行时）MODULE_NOT_FOUND（模块未找到）、退出码为 0，却记录 passed（通过）的情况。该记录是问题证据，不是本次验证结果；具体引号处理和吞掉退出码的机制尚未独立复现，不能写成已证实根因。后续补跑也不能倒推原验证有效。

## Solution（解决方案）

沿用现有热修复入口与 Build and Verify（构建与验证）完整验证入口，只修复受管命令映射的环境边界，并在完整验证结果上增加必要证据门禁。满足退出成功、最终报告通过、最终检查非空及最终明确未跳过完整验证，才能继续热修复。任何不满足条件的情况均沿用现有验证失败路径，不推送、不记成功审计。

自定义验证命令保持原退出码语义和环境；快速验证及其他工具模式不套用完整验证证据门禁。

## User Stories（用户故事）

1. 作为热修复维护者，我希望从现有热修复入口确认完整验证真实通过，以便放心继续授权范围内的推送。
2. 作为热修复维护者，我希望退出码为 0 但无输出或无检查时停止，以免把没有执行验证当成通过。
3. 作为热修复维护者，我希望最终报告失败或跳过完整验证时停止，以免较早的通过记录掩盖最终结果。
4. 作为热修复维护者，我希望验证进程非零退出时仍停止，以免报告内容掩盖进程失败。
5. 作为受管工具使用者，我希望已消费的工具映射不再传给受管验证子进程，以免再次改写其命令解析。
6. 作为同一进程中的其他操作使用者，我希望父环境和无关环境变量保持原样，以免一次热修复影响后续操作。
7. 作为未配置工具映射的维护者，我希望完整验证仍执行相同证据门禁，以免是否配置映射改变安全要求。
8. 作为自定义验证命令使用者，我希望原有命令环境、退出码语义和 Windows（操作系统）路径继续兼容，以免修复破坏现有配置。
9. 作为快速验证或其他工具模式使用者，我希望不被强加完整验证报告要求，以免扩大本次变更影响。
10. 作为维护者，我希望合法标准错误警告不被单独判为失败，以免已满足全部证据的完整验证被误拦截。
11. 作为审计记录使用者，我希望异常验证既不推送也不记录热修复成功，以便记录与实际结果一致。
12. 作为后续开发者，我希望技能说明与精简回归描述同一契约，以便今后不会再次把空验证视为通过。

## Implementation Decisions（实施决策）

- 保持现有热修复验证函数接口及流程，不引入新的运行器、通用抽象、验证入口或临时启动器；复用现有受管工具解析、失败详情和审计能力。
- 依据命令解析后的逻辑入口识别受管工具，识别发生在工具映射展开之前。逻辑入口为 build-and-verify（构建与验证工具）时，先消费已有 PR_FLOW_TOOL_COMMANDS（工具命令映射）得到参数，再复制子进程环境并仅移除已消费的该变量；父环境不修改，其他变量保留。未消费映射时不凭空清理环境。
- 四项证据门禁仅适用于逻辑 build-and-verify（构建与验证工具）的 verify（验证）命令且含 --full（完整模式）；无论是否配置工具映射都适用。须同时满足：进程退出码为 0；标准输出最后报告的 status（状态）为 passed（通过）；最后 checked（已检查项）非空；最后 full-not-run（完整验证未运行）为 false（否）。以最终报告值为准，不能被较早记录覆盖。
- 缺失证据、空输出、空检查、skipped（跳过）、最终 failed（失败）或非零退出均沿用 hotfix_verify_failed（热修复验证失败），阻止推送及成功审计。合法标准错误警告本身不增加失败条件。
- 自定义命令保持原退出码语义及环境；fast（快速模式）与其他工具模式不套用完整证据门禁。保留现有跨平台命令解析兼容行为。
- GitHub（代码托管平台）分支保护、授权短语、推送前远端复核，以及构建和发布入口均保持不变。
- 单张无前置依赖的纵向票据同时交付最小修复、对应技能说明和精简回归；不先行重构，不拆成横向层次票据。

## Testing Decisions（测试决策）

- 最高层级真实用户入口为 `pr_flow.py hotfix`（热修复命令）。优先复用 `tests/support/pr_flow_invocation.py` 的 `invoke_pr_flow`（流程调用接缝），真实调用 `main(argv)`（主入口），验证用户可观察的停止、推送与审计结果。
- 沿用 `tests/test_pr_flow_cli.py` 已有 Git（版本管理）与子进程替换方式；不替换本次目标验证函数。检查异常分支不会推送且不会产生成功审计，成功分支在满足其他既有条件时可继续。
- 精简证据矩阵覆盖完整通过、空输出、缺字段、空检查、跳过、最终失败覆盖较早通过、非零退出及合法标准错误警告；映射存在与不存在都受门禁约束。
- 精简环境矩阵确认映射被实际消费后仅从子环境移除、父环境不变且其他变量保留；自定义命令保持环境与退出码语义，快速及其他工具模式保持兼容。复用已有 Windows（操作系统）路径兼容回归，不因覆盖断言扩张测试成本。
- 门禁一批准开发后，云端实施和独立审查，本机通过既有 build-and-verify（构建与验证）入口执行红绿验证、正式验证和真实入口快速冒烟，以 GitHub（代码托管平台）功能分支同步。不新增入口，不运行全仓完整回归。完整流程等级不等于扩大测试范围。
- 本次仅产出需求文档，未运行测试、构建或冒烟；历史记录及架构分析均不作本次通过证据。
