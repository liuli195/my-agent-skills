## Why（原因）

仓库中的 `.build-and-verify/config.json`（配置文件）可能随代码、脚本和测试入口演进而遗漏检查项，或留下错误分类、重复项、失效路径和不完整缓存输入。现有 `build-and-verify-init`（构建与验证初始化）能够发现候选检查项，但没有独立入口审查已有配置并生成可确认的优化草案。

## What Changes（变更内容）

- 新增独立 `build-and-verify-review` Skill（构建与验证审查技能）。
- 直接复用初始化入口的生态识别规则，不复制或另建扫描实现。
- 同时审查 `build.checks`（构建检查项）和 `verify.checks`（验证检查项），其中完整性重点是可发现验证入口是否被配置覆盖。
- 静态检查命令来源、分组、重复关系、`paths`（受影响路径）、`inputs`（缓存输入）、废弃字段和副作用风险。
- 按置信度生成逐项可接受或拒绝的修改建议；整体确认前不修改配置。
- 用户确认后复用现有定向依赖检查、环境检查、备份及 runtime（运行时）初始化覆盖命令。
- 写入后运行一次完整验证；失败时报告原因，不自动回滚。

## User Stories（用户故事）

1. 作为仓库维护者，我希望扫描已有构建与验证配置，以便发现仓库入口与配置之间的偏差。
2. 作为仓库维护者，我希望识别尚未配置的高置信度验证入口，以便补齐本地验证主流程。
3. 作为仓库维护者，我希望看到分类错误、重复检查项和失效检查项，以便减少无效或重复执行。
4. 作为仓库维护者，我希望检查受影响路径和缓存输入，以便快速验证不会漏跑且缓存会正确失效。
5. 作为仓库维护者，我希望风险候选不会被默认加入，以便避免意外发布、部署、删除或迁移。
6. 作为仓库维护者，我希望逐项选择建议并查看最终差异，以便只接受有意的配置修改。
7. 作为仓库维护者，我希望配置在明确确认后才写入并自动备份，以便保护已有手写规则。
8. 作为仓库维护者，我希望修改后运行完整验证，以便证明新配置可执行并覆盖真实主流程。
9. 作为仓库维护者，我希望完整验证失败时保留诊断现场而非自动回滚，以便区分配置错误和真实仓库问题。

## Capabilities（能力）

### New Capabilities（新增能力）

None.

### Modified Capabilities（修改能力）

- `test-framework-plugin`: 增加构建与验证配置审查、确认式优化和写入后完整验证行为。

## Impact（影响）

- Affected plugin package: `plugins/build-and-verify/`（构建与验证插件）。
- Affected specs: `test-framework-plugin`（测试框架插件规格）。
- Affected tests: 构建与验证插件的模板完整性测试和一次端到端审查流程模拟。
- No runner（运行器）语义、配置格式、依赖安装、用户级配置或 CI（持续集成）变更。
