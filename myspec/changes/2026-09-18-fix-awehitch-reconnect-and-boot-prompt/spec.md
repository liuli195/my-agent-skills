# 修好单工作区下的重新连接与引导词发送

## Problem Statement

使用者的需求只有一条：**手动切到某一个工作区，启动 Agent（代理），让它顺畅地通过技能流程连上 ChatGPT**。不需要多工作区之间交接工作。

现在这条需求在两个地方断掉。

**一、重启之后连不上。** 隧道是临时的，重启即失效；地址一变，ChatGPT 那边的连接器就指向死地址。技能里「reconnect after address reclaim」那一节把触发条件挂在 `chatgptSetup.needed` / `chatgptRepair.needed` 上，而这两个标志在真实重启场景里**不会亮**：bridge 已死 → doctor 无法确认状态 → 直接跳过连接器检查。即使标志亮了，真实链路还漏了唯一真正重建连接的那一步（`connector-setup`）。照技能走会卡住，而**卡住的原因在界面上看不出来**——doctor 一切显示绿灯。

**二、连上之后，新会话拿不到角色设定。** 引导词 **1361 字节且不以 `[C2C]` 开头**，而唯一能发任意文本的通道硬性要求「`[C2C]` 开头」且「≤1024 字节」——两条都踩，**永远发不出去**。使用者看到的是 ChatGPT 行为不稳定：有时像规划层，有时不像。根因是每个 Agent（代理）临场自己压一版发出去，压成什么样全凭运气。

## Solution

三处改动，对应三个独立缺陷。

**一、让 bridge 认得出「记录已死」。** bridge（桥接服务）的判断顺序反了：先探端口、后查进程。重启后旧记录里的端口往往已被**另一个工作区**占用，于是判为「状态不明」并**拒绝启动**。改为先查记录里的进程、进程已死即判「已停止」——记录里的进程都不在了，那份记录就是废的，端口现在谁用着都无所谓。

**二、把重新连接那一节按实测链路重写。** 连接只有「能不能用」一个判据，所以先试一次最小往返，而不是先跑诊断命令去猜；不通就一条命令重建。

**三、把引导词压到能发出去。** 只保留**能改变 ChatGPT 行为**的信息（角色、用哪个连接器、怎么读工作区、按什么格式回话、验收纪律），去掉不改变任何决策的表述。压缩后 816 字节，余量 208 字节。

## User Stories

1. 作为使用者，我希望重启电脑后启动 Agent（代理），它能自己把连接恢复起来，以便我不用记住任何手动步骤。
2. 作为使用者，我希望连接失败时 Agent（代理）能**明确告诉我它在做什么**，而不是反复跑诊断命令、或者干脆卡住不动。
3. 作为使用者，我希望「连不上」这件事有一个**单一、可靠的判据**，以便 Agent（代理）不需要靠猜。
4. 作为使用者，我希望 Agent（代理）先**试一次真实往返**再决定要不要修，以便本来就是好的连接不被多余的修复动作打扰。
5. 作为使用者，我希望重建连接是**一条命令**，以便失败时的人工成本最低。
6. 作为使用者，我希望重建连接**默认全自动**，只有确实需要我登录时才找我要一次操作，以便我不必每次都守着。
7. 作为使用者，我希望新建对话时 ChatGPT 收到的角色设定是**完整且一致**的，以便它的表现不随 Agent（代理）的临场发挥而波动。
8. 作为使用者，我希望引导词能**真的发出去**，而不是表面成功、实际被发送通道拒绝。
9. 作为使用者，我希望引导词告诉我账号下**三个 awehitch 连接器里该用哪一个**，以便它不会读错工作区。
10. 作为使用者，我希望引导词里**没有空话**——每一句都能改变 ChatGPT 的行为，以便 1 KB 的额度花在有用的地方。
11. 作为使用者，我希望引导词留出**余量**，以便以后想补一条规则时不必推倒重压。
12. 作为使用者，我希望技能里**不存在「看着合理但永远不会触发」的分支**，以便 Agent（代理）照它走时不会走进死路。
13. 作为使用者，我希望同一个模式（工作区校验）在技能里的两处说法**互相一致**，以便不会一处改了、另一处还指着旧判据。
14. 作为维护者，我希望这三处改动的**行为**都有可复核的检查，以便以后回归时能立刻发现。
15. 作为维护者，我希望「哪些文本是要发出去的」这条约束**能被断言**，以便有人往后往里加内容时超限会被挡住，而不是等到线上发不出去才发现。
16. 作为维护者，我希望补丁脚本继续保持**幂等与自检**，以便 `npm update` 之后一条命令就能全部重放。
17. 作为维护者，我希望三处改动**各自一个提交**，以便将来能单独定位和回滚。
18. 作为使用者，我希望这次改动**不引入新的手动步骤**，以便我的既有习惯不被打断。

## Implementation Decisions

三处改动都通过仓库既有的本地补丁机制落地（`scripts/awehitch-local-patches.ps1`，幂等、带自检、"判不准不动手"）。补丁改的是本机 `npm` 全局安装的第三方包，`npm update -g awehitch` 会冲掉，因此补丁必须表达为可重放的配方，而不是一次性手工改动。

**补丁 5 — bridge 判断顺序（行为改动）**

- 把「记录里的进程是否还在」的检查**提到端口探测之前**；进程已死直接判「已停止」，不再探测端口。
- 保留既有的保守分支：进程仍在但端口探不到服务时，仍然判「状态不明」并拒绝启动（宁可拒绝，不可误杀活体服务）。
- **明确不修**「进程号被系统回收」那一支：修它必须把「状态不明」降级，而端口探测只是一次 HTTP 试探，服务短暂卡顿就会被误判成死亡，**存在误杀活体服务的风险**。当前那一支是保守（拒绝启动）而非错误。
- 安全性：进程已死 → 判已停止 → 启动新 bridge；若默认端口被别的实例占用，新实例会自行退到临时端口，**不会打断邻居**。

**补丁 6 — 技能里的重新连接流程（内容改动）**

- 「reconnect after address reclaim」一节**整节替换**为三步：① 试一次最小 `[C2C]` 往返 → ② 回复报出本工作区名即为已连上 → ③ 不通则跑 `awehitch connector-setup -w <仓库>`，然后回到第 ① 步。
- 删除对 `chatgptSetup.needed` / `chatgptRepair.needed` 的依赖。改写理由必须**准确**：不是在重启场景里「永远不亮」，而是「bridge 状态为『状态不明』时永不点亮；为『已停止』时会点亮，但**只在一次运行的窗口内有效**，跑完即自熄」。
- **同步修改同一模板里另一处引用同一套标志的地方**（doctor 门禁那段）。两处必须一起改，否则技能文本自相矛盾。
- 同时删除 doctor 门禁本身（"本地不全绿就不开 ChatGPT"）：它既不亮也不准，实测误导。
- 登录表述更正为**异常路径**：默认全自动，只有返回 `needsLogin` 时才需要人登录一次。浏览器配置是持久化的，登录态跨重启保留。

**补丁 7 — 引导词与工作区校验词（内容改动）**

- 引导词改为：**`[C2C]` + `STATE: BOOT` 开头**，正文只保留能改变 ChatGPT 行为的信息。
- **连接器名保留**（账号下有多个 awehitch 连接器，不点名就可能读错工作区），且它是字节预算里最值钱的一条。
- **删除**不改变任何决策的表述：「只检查需要的文件」「避免不必要的重写」「要有实质内容」。后者与技能里"PLAN 只有一句话就追问理由"重复，技能侧已能兜住。
- 合并同类项：「产出简洁计划」与「代理会用自己框架执行」并入抬头角色说明；「不要因为代理说成功就信」并入「EXECUTED 后核对真实差异」。
- 工作区校验词同样加 `[C2C]` 头（该词不超限，只缺前缀）。
- **字节预算必须在渲染后断言，不能在模板上断言**：模板里的连接器名占位符会被替换掉，而连接器名的长度不受本仓库控制（可能长于当前工作区的 27 字节）。预算按最坏长度计算。

**交付形态**

- 三处改动**各自一个提交**，同一个 PR（延续当前分支上已开的 PR）。

## Testing Decisions

**测试的对象是外部行为，不是实现细节。** 断言的是「从真实入口进、能得到什么可观察结果」，不是「某个内部函数被怎么调用」。

仓库当前对 awehitch **零测试覆盖**（`tests/` 与 `.build-and-verify/` 内 grep 零命中）。新增测试挂进**既有的** `verify.build-and-verify` 检查项，**不新增构建或验证入口**。新增测试文件按**文件名**加入该检查项，**不使用通配**——仓库里有一条挑选不变量（改某个测试文件必须选中 `verify.runtime-boundaries` 且不能选中 `verify.build-and-verify`），通配会破坏它。

**接缝一（补丁 5）：`awehitch status -w <仓库> --json`**

- 这是补丁 5 最高层级的公开接缝：命令行进、JSON 出，只读、不启动守护进程、不碰网络。
- 用官方的状态目录环境变量覆盖机制指向一个临时目录，预置一条运行记录，断言 `state` / `reason`。
- 断言的核心行为：**记录里的进程已死 → 判「已停止」**（而不是「状态不明」）。

**接缝二（补丁 6 / 7）：渲染后的技能文本**

- 最高层级接缝是**渲染产物**，经由产生该缺陷的那一步（模板渲染函数，两个客户端共用）。
- 断言形式：**凡技能里声明为「要发出去」的围栏文本块，渲染后必须以 `[C2C]` 开头，且按最坏长度连接器名替换后的字节数不超过 1024。**
- 断言必须落在**渲染输出**上，不能落在模板上。

**先例**：仓库里已有「测一个 PowerShell 脚本」的测试模板（静态文本断言 + 真跑一次脚本打向临时假树），本次沿用同一形态。

**必须显式接受的约束**：补丁 5 那个检查需要**本机装着被改过的包**才跑得起来——它本质是机器相关的，不是纯持续集成测试。这是「改动落在第三方安装包上」的固有代价，本次接受。

## Out of Scope

- **多工作区之间的交接** —— 使用者明确排除，只需要单工作区内连得上。
- **「进程号被系统回收」那一支** —— 见补丁 5，有误杀活体服务的风险，需单独立项并实测。
- **CHATGPT 的项目指令路线** —— 曾评估用 ChatGPT「项目设置 → 指令」承载固定角色信息（不受 1 KB 限制）。因其需要每个工作区一次人工操作、且在本连接器方案下**未经验证**，本次不做。引导词压缩后余量已从 30 字节涨到 208 字节，该路线的紧迫性消失。
- **重构本地补丁体系**（补丁即数据 / 脚本可注入 / 内容归仓库）—— 会把「修三个缺陷」扩大成「重做补丁体系」，本次不做。
- **给技能模板加可机读标记** —— 超出范围，且会多一处补丁面。
- **向 awehitch 上游报告缺陷** —— 累积三条（写坏配置、引导词无可用发送通道、重连被拒），待本次改动真跑通一段时间后再报。
- **控制面浏览器被其他工作区争抢** —— 未实测过真实争抢，不猜、不写。

## Further Notes

**子代理模型回退**：本次流程指定的三个模型在本宿主均不可用，按子代理策略的回退规则改用宿主默认模型承载同一角色，已在委派提示词与返回报告中显式声明。架构师角色的结论**不具备被指定模型的背书**。

**术语漂移（待收尾时决定是否记录）**：本次同时用了「补丁」一词指三种不同的东西——**行为**改动（改第三方包代码）、**内容**改动（改一份引导文档）、**一次性存量清理**。内容改动本可以由本仓库自己拥有，不必替换第三方产物；三类混用一个词会遮掉这个判断。

**架构师的核心发现**：补丁 7 修的是**文档**，不是代码。这条决定了将来若要减少补丁面，优先考虑的是把内容类改动收归仓库自己拥有。

**已核验的关键事实**（源码级）：唯一能发任意文本的工具是 `awehitch_send_state`，其校验为「必须 `[C2C]` 开头」且「UTF-8 字节数 ≤ 1024」；默认端口全机共享且被占用时静默退到临时端口；doctor 的两个修复标志只在一次运行的窗口内有效。
