# 设计优先的需求讨论

## Problem Statement（问题说明）

Pi Development Flow（Pi 开发流程）会在需求阶段直接进入拷问，且没有要求先使用 `codebase-design`（代码架构）形成和确认整体方案。使用者因而无法先对整体方向达成一致，也可能在已回答的细节上被重复提问。

## Solution（方案）

Requirements（需求）阶段先读取并使用 `codebase-design`（代码架构）形成按风险缩放的整体方案；用户以正常对话确认方向后，才读取 `grill-with-docs`（带文档拷问）和 `domain-modeling`（领域建模），逐项讨论仍未确认的细节。

方向确认不是新的 Gate（门禁），不要求固定措辞，也不发布需求产物。后续答案只有改变范围、模块（Module）、接口（Interface）、接缝（Seam）、最高公开测试接缝或流程等级（Flow Level）时，才回到整体方案确认。

## User Stories（用户故事）

1. 作为开发流程使用者，我希望需求讨论先给出整体方案，以便先确认方向再讨论细节。
2. 作为开发流程使用者，我希望已确认的方案不被重复拷问，以便讨论只处理真正未决的问题。
3. 作为开发流程使用者，我希望方向确认不成为额外门禁，以便不增加实施、发布或提交授权。
4. 作为维护者，我希望 `codebase-design`（代码架构）与现有需求技能一样被明确核验，以便缺失时流程安全停止。
5. 作为 Pi（代理）使用者，我希望 Development Flow（开发流程）技能仍可从本地 Package（包）自然发现，以便不复制或安装全局技能来源。

## Implementation Decisions（实现决定）

- Requirements（需求）阶段的核心依赖先加载 `codebase-design`（代码架构）；方向确认后再加载 `grill-with-docs`（带文档拷问）及其要求的 `domain-modeling`（领域建模）。
- 生成规格和票据前，当前会话的工具调用证据必须包含三个需求技能；缺失、不可读、加载失败或被替代时停止并报告 Gate 1 — Complete Requirements（完成需求）。
- 整体方案按风险缩放。轻量变更只说明可观察结果、范围和测试接缝；仅在确有结构设计时使用模块（Module）、接口（Interface）和接缝（Seam）。
- 已确认事项保留在当前会话；不新增流程状态文件。多会话路线将已确认方向作为 `wayfinder`（路径规划）的目标，后续决策票据只处理未决事项。
- 开发流程入口说明需求阶段的顺序，以便 Pi（代理）在任务匹配时自然发现此流程。
- 初始化检查明确列出需求阶段所需技能；不复制、内置或安装 `codebase-design`（代码架构），因为它由 Pi（代理）的既有技能发现机制提供。
- 保持四个既有 Gate（门禁）的编号、语义与授权边界不变。

## Testing Decisions（测试决定）

- 复用现有 Pi Development Flow（Pi 开发流程）本地 Package（包）资源加载测试，验证技能仍被自然发现。
- 在同一测试接缝验证需求文档的依赖顺序、方向确认的非门禁性质、整体方案失效时的回退条件，以及规格和票据前的三项技能证据。
- 测试技能文本规定的外部行为，不新增模型端到端测试、解析框架或独立测试入口。

## Out of Scope（范围外）

- 修改全局 `codebase-design`（代码架构）、`grill-with-docs`（带文档拷问）、`grilling`（拷问）或 `wayfinder`（路径规划）技能。
- 新增 Gate（门禁）、流程状态文件、Package（包）依赖、安装配置或通用编排框架。
- 改变 Implementation（实施）或 Delivery（交付）阶段的授权与行为。

## Further Notes（补充说明）

本变更属于 Standard（标准）流程等级：它改变用户可观察的需求讨论行为，但不涉及安全、数据、发布或机器状态修改。
