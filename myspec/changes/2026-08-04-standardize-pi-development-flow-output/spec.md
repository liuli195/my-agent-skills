# 统一 Pi Development Flow（Pi 开发流程）输出与完成检查

## Problem Statement

Pi Development Flow（Pi 开发流程）的四个门禁目前只规定了需要展示的内容，没有规定统一的输出标题、区块名称和顺序。代理可能自行命名区块、铺开长篇计划或差异，导致重点不突出、不同门禁格式不一致，也难以稳定检查。

Issue #163 的前置多工作树逻辑已经完成；其剩余问题是 PR 合并后 Git（版本管理）登记和分支已清理，但实体工作树目录仍可能残留。流程需要在最终结论前报告这一状态，并在用户明确授权后才允许强制清理。

## Solution

为四个正式门禁和其后的 Completion Check（完成检查）定义一个唯一输出模板。每次输出严格使用固定门禁标题和以下四个区块：`状态与待确认`、`核心内容摘要`、`引用`、`下一步`。各门禁只在核心摘要中展示自己的重点内容，长规格、计划、差异和证据通过引用访问。

Gate 4 — Authorize PR Delivery（授权 PR 交付）完成后执行 Completion Check（完成检查）。只有验收、验证、正式规格、PR（拉取请求）合并、目标分支同步和安全清理均有证据时，才报告最终完成。检测到实体工作树残留时，流程报告残留路径和原因，询问是否授权对该精确残留执行强制清理；不自动强制删除，拒绝授权时不报告最终完成。

## User Stories

1. 作为 Development Flow 使用者，我希望所有门禁使用固定标题和四个固定区块，以便快速识别状态、重点、引用和下一步。
2. 作为需求确认者，我希望 Gate 1 只摘要目标、测试接缝、票据和工作树信息，以便确认需求而不被完整规格淹没。
3. 作为实施授权者，我希望 Gate 2 摘要实施计划、验证方式和风险，以便决定是否授权实施。
4. 作为交付使用者，我希望 Gate 3 摘要正式规格差异和校验结果，并沿用 `my-spec-add`（新增自有规格）的原始确认。
5. 作为 PR 交付授权者，我希望 Gate 4 摘要最终差异、验证审查结果和准确交付动作，以便决定是否授权交付。
6. 作为流程使用者，我希望完成检查明确区分最终完成、未完成和阻塞，以免把部分清理误报为完成。
7. 作为工作树维护者，我希望清理残留显示精确路径和原因，以便判断是否需要人工处理。
8. 作为仓库所有者，我希望强制清理必须经过明确授权，避免流程删除未知或仍需保留的文件。
9. 作为维护者，我希望未请求的本地安装、客户端同步、市场刷新和发布不影响 Development Flow（开发流程）完成。

## Implementation Decisions

### Fixed output contract（固定输出契约）

- 五个流程节点使用固定标题：四个既有 Gate（门禁）和 `Completion Check — 完成检查`。
- 每次输出严格按以下顺序包含且仅包含四个区块：
  1. `状态与待确认`
  2. `核心内容摘要`
  3. `引用`
  4. `下一步`
- `状态与待确认` 同时展示状态和当前需要用户确认的内容；没有待确认内容时写明无。
- `核心内容摘要` 只展示当前门禁作出判断所需的重点；完整内容不复制到输出中。
- `引用` 指向完整规格、实施计划、差异、验证证据或恢复文档；没有引用时写明无。
- `下一步` 只说明下一门禁、流程结束或恢复位置。
- 代理不得自行改名、调换、拆分、合并或新增这四个区块。

### Gate-specific summaries（门禁专属摘要）

- Gate 1 摘要需求目标、范围、测试接缝、票据及其阻塞关系、变更工作树。
- Gate 2 摘要票据顺序和并行组、执行隔离、验证与审查、风险和停止条件。
- Gate 3 摘要正式规格差异和校验结果；最终确认沿用 `my-spec-add`，不增加第二套确认。
- Gate 4 摘要最终差异、验证审查结果、已知风险和准确交付动作。
- Completion Check 摘要最终完成条件、实际状态和清理残留。

### Completion Check（完成检查）

- Completion Check 是 Gate 4 之后的完成判定，不新增第五个正式授权门禁。
- `最终完成` 只在所有验收、要求的检查、正式规格、PR 合并、目标分支同步和安全清理均被证明完成时使用。
- Git 清理登记已完成但实体工作树目录仍存在时，状态为 `未完成`，并报告精确路径、残留原因和引用证据。
- 只有检测到残留时才询问是否授权强制清理；流程不自动执行强制删除。
- 用户拒绝强制清理时，保留残留并报告恢复位置；用户授权后，完成受限清理并重新执行 Completion Check。
- 未请求的本地安装、客户端同步、市场刷新和发布不属于完成条件，也不阻塞完成结论。

### Scope boundary（范围边界）

- 本变更只调整 Development Flow 的输出契约和最终完成判定。
- Issue #163 已完成的多工作树并行、状态隔离和基线逻辑不在本变更中重做。
- 本变更不新增强制删除实现，不修改 PR Flow（拉取请求流程）的底层清理命令。

## Testing Decisions

- 扩展现有 Pi Development Flow 契约检查，验证五个固定标题、四个区块的精确名称、顺序和唯一性。
- 验证三个阶段参考文档均引用唯一输出模板，且没有复制另一套模板。
- 验证每个门禁的核心摘要包含对应的最小重点；Gate 3 保留 `my-spec-add` 原始确认，不产生重复确认。
- 验证 Completion Check 明确最终完成条件、残留报告、强制清理授权和拒绝后的未完成状态。
- 通过本地 Pi Package（包）资源加载入口进行真实加载冒烟，确认新 Pi 进程可发现该技能及其引用文档。
- 使用 Build and Verify（构建与验证）快速入口运行相关契约检查，不执行无关的完整端到端回归。

## Out of Scope

- 重做 Issue #163 已完成的多工作树并行支持。
- 自动或默认强制删除实体工作树、目录链接或临时文件。
- 修改 PR Flow 的底层清理状态实现。
- 本地安装、客户端同步、市场刷新或 Release Flow（发布流程）。
- 修改 Pi 本体、用户级 Skill（技能）或机器配置。

## Further Notes

Issue #163 的两条后续评论表明，最后清理可能只完成 Git 登记和分支清理，实体目录仍因 Windows（视窗系统）文件锁或长路径等原因残留。本变更把该状态纳入 Development Flow 的最终完成检查，并保持非强制、需授权的安全边界。
