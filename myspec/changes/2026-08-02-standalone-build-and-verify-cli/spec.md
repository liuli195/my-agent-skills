# 独立 Build and Verify CLI（命令行程序）与工具链同步

**Status（状态）：** ready-for-agent

## Problem Statement（问题说明）

Build and Verify（构建与验证）目前把运行时快照复制进每个目标仓库。版本同步、旧快照维护和 CI（持续集成）入口因而分散；MySpec（自有规格）已具备的发布版／源码版生命周期也无法复用。PR Flow（拉取请求流程）不知道本机实际使用的工具身份，外部仓库的 CI 不能稳定地与本机工具对齐。

发布流程已用单一发布版本和 `bumpPlugins`（提升插件列表）选择本次发布范围，但 npm（软件包管理器）发布仅为 MySpec 实现。首次 npm 发布还需要人工完成认证、双重验证和 Trusted Publisher（可信发布者）准备，自动流程不能把这些前提误报为可发布状态。

## Solution（方案）

将 Build and Verify 发布为独立 npm 包 `@liuli195/build-and-verify`，提供稳定 CLI（命令行程序）及 Pi、Claude、Codex 所需插件资源。它采用与 MySpec 相同的发布版／源码版模式、`init`（初始化）、`doctor`（诊断）和 `update`（更新）生命周期；两包仍独立安装和独立演进。

MySpec 和 Build and Verify 的 `doctor` 输出同一机器可读工具身份。PR Flow 只消费该身份，把选择的发布版或受信任源码身份写入 Git 可见的工具链记录，并由专用受管工作流安装相同工具。现有工作流不被 PR Flow 改写。

Pi Development Flow（Pi 开发流程）的派发器只验证精确票据路径、目标非主工作树和预期分支；票据状态由追踪流程表达，不作为重复的派发器正文解析门禁。

Release Flow（发布流程）保持现有单一发布版本和 `bumpPlugins` 语义：本次选中的插件及其 npm 包统一使用该版本；未选中的包保持原版本且不发布。发布逻辑从 MySpec 专用处理最小泛化为对选中 npm 包逐一打包、隔离快速验证、完整性核对和发布。首次发布使用既有发布工作流的准备模式，只产生并验证候选包，等待人工完成认证准备后再走正常发布。

## User Stories（用户故事）

1. 作为仓库使用者，我希望用稳定的 `build-and-verify` CLI（命令行程序）运行构建和验证，以便不维护仓库复制的运行时快照。
2. 作为 MySpec 使用者，我希望 `doctor`（诊断）给出可由其他工具读取的身份，以便 CI（持续集成）使用与本机一致的工具。
3. 作为 Build and Verify 使用者，我希望发布版和源码版切换明确，以便本机、Agent（代理）和 CI（持续集成）不会静默使用不同来源。
4. 作为 Pi、Claude 或 Codex 用户，我希望两个工具都能从各自 CLI（命令行程序）初始化，以便不维护三套安装步骤。
5. 作为外部仓库维护者，我希望 PR Flow（拉取请求流程）记录固定工具身份，以便 CI（持续集成）可重现地安装工具。
6. 作为源码开发者，我希望 CI（持续集成）使用精确公开提交打包的工具，以便验证未发布源码而非 npm（软件包管理器）旧版本。
7. 作为安全维护者，我希望 CI（持续集成）拒绝任意工具来源、目录和包名，以便工具链记录不能被改成任意代码执行入口。
8. 作为旧 Build and Verify 用户，我希望新 CLI（命令行程序）快速验证成功后自动清理识别的旧运行时，以便迁移不留下双重入口。
9. 作为旧仓库维护者，我希望迁移只在干净 Git（版本管理）工作区中提交自身改动，以便不会混入来源不明的文件。
10. 作为现有 PR Flow 用户，我希望原有工作流保持不变，以便工具链同步不重写我的业务 CI（持续集成）。
11. 作为 PR Flow 使用者，我希望工具链记录变化被有界地自动提交和重新检查，以便流程不会用过期基线继续。
12. 作为发布维护者，我希望沿用 `RELEASE_VERSION`（发布版本）和 `bumpPlugins`（提升插件列表），以便选择部分包发布时不改变未选包版本。
13. 作为发布维护者，我希望每个选中 npm 包都从同一候选 Tarball（npm 包文件）验证并发布，以便发布内容与验证内容一致。
14. 作为首次发布维护者，我希望自动流程在远端发布前停止并给出人工准备事项，以便认证、双重验证和可信发布者配置不会失败后才暴露。
15. 作为维护者，我希望首次发布准备模式只验证并上传候选包，以便不创建标签、GitHub Release（GitHub 发布）或市场更新。
16. 作为维护者，我希望发布前检查仓库元数据与 provenance（来源证明）要求，以便避免 npm 发布时的远端元数据拒绝。
17. 作为维护者，我希望快速冒烟覆盖本次可观察行为，以便不因该迁移新增端到端回归。
18. 作为现有仓库维护者，我希望未显式迁移的旧 PR Flow 保持旧行为并收到提示，以便升级不会被隐式推断。
19. 作为 Pi Development Flow（Pi 开发流程）使用者，我希望派发器不因票据状态的 Markdown（标记文档）格式拒绝已指定票据，以便精确路径和工作树绑定成为唯一派发门禁。

## Implementation Decisions（实现决定）

- Build and Verify 作为独立 npm 包发布，保留其构建与验证业务语义，不与 MySpec 合并，也不新增依赖。
- 两个工具分别维护发布版／源码版状态、安装锁和可继续操作；模式可彼此不同。
- `doctor`（诊断）以稳定机器可读字段输出模式、包名、发布版本，或源码模式的官方仓库、完整 Git 提交和固定包目录。PR Flow 只读取这些字段，不猜测安装位置或来源。
- 源码工具链只允许各受支持工具的官方源码根、固定包目录和固定包名；提交必须是完整且可检出的公开提交。打包和隔离安装均禁用安装脚本。
- Build and Verify 的项目初始化在发现识别的旧运行时时，先确认 Git 工作区及暂存区干净，并用新 CLI 完成约定快速验证；成功后删除识别的旧运行时并只提交迁移文件。它不扫描或改写任意既有调用方。
- 调用方迁移由其所属变更完成；本仓库的自动化、技能说明和正式规格在本变更中改为 CLI（命令行程序）入口。
- Plugin Sync（插件同步）只委托两个工具各自的生命周期；不再同步 Build and Verify 仓库运行时版本或删除共享市场与无关插件。
- PR Flow 初始化创建 Git 可见工具链记录及唯一专用受管工作流。诊断只读；完整流程和小改流程在身份变化时仅提交受管记录，随后从新提交重新读取基线、检查和 PR（拉取请求）状态，并使用有界重试。
- 自动同步只在原工作区和暂存区干净时运行，且不得暂存或提交受管文件外的变更。旧仓库须由用户显式初始化升级，未迁移仓库继续旧行为。
- Pi Development Flow（Pi 开发流程）派发器不解析票据正文状态；其派发边界仅为一个目标非主工作树、精确分支和位于该工作树发布票据目录中的单一 Markdown（标记文档）票据。
- Release Flow 保持单一发布版本、`bumpPlugins`、标签和 GitHub Release（GitHub 发布）语义。仅将 npm 发布逻辑泛化到本次选中的包；未选包不改版本、不打包、不发布。
- 选中 npm 包从当前发布提交打包、隔离安装并执行快速冒烟；完整性比较逐包进行。发布前检查包的 `repository.url` 与单仓库包目录元数据。
- 若本次所选 npm 包中存在未完成首发准备的包，正常发布在任何远端发布操作前停止。准备模式复用既有发布工作流，只验证并上传候选 Tarball（npm 包文件）；人工完成 npm 登录、双重验证和可信发布者准备后才可正常发布。
- 现有要求本变更新增 Tarball（npm 包文件）端到端验证的规格应改为与快速冒烟策略一致；不新增单独的 OIDC（开放身份认证）端到端发布验证。

## Testing Decisions（测试决定）

- 复用现有 CLI（命令行程序）、受控 npm（软件包管理器）及 Git（版本管理）替身测试接缝，观察命令、退出码、生成记录和工作区结果，不测试私有辅助函数。
- 以从当前检出打包并隔离安装的候选包验证 CLI（命令行程序）资源完整性和快速用户入口；不新增完整端到端回归。
- 使用临时干净 Git（版本管理）仓库验证旧运行时清理、验证失败停止和仅迁移文件提交。
- 使用工具链记录和生成工作流的确定性测试验证发布版、源码版、安全拒绝和自动同步后的基线重读。
- 使用 Pi Development Flow（Pi 开发流程）派发器的受控事件替身验证不含状态标记的票据仍被精确绑定，同时错误分支、主工作树和目录外路径继续被拒绝。
- 使用受控发布命令验证选中包、未选包、逐包完整性、首次发布准备停止及 provenance（来源证明）预检；首次真实人工发布仅作为人工引导冒烟。

## Out of Scope（范围外）

- 合并 MySpec（自有规格）和 Build and Verify（构建与验证）为同一 npm 包或强制二者版本一致。
- 逐包版本映射、一次发布中为选中包分配不同版本，或改变既有发布版本输入。
- 新增每仓库来源白名单、通用信任配置、迁移命令或新的发布工作流。
- PR Flow 重写已有业务工作流、升级本机 CLI（命令行程序）、安装依赖，或迁移未显式初始化的旧仓库。
- Build and Verify 自动扫描或改写任意旧调用方。
- 自动完成 npm 登录、双重验证、可信发布者配置或真实首次发布。
- 新增完整端到端回归或 OIDC（开放身份认证）端到端发布验证。

## Further Notes（补充说明）

本变更会更新与 MySpec 分发、Build and Verify、Plugin Sync、PR Flow 和 Release Flow 有关的正式 MySpec（自有规格）契约；现有运行时快照契约及 MySpec 专用 npm 发布契约将被最小替换，而不是保留并行实现。
