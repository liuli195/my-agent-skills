# MySpec 工作树锁与 Gate 3 来源语义对齐

**Status（状态）：** ready-for-agent

## Problem Statement（问题说明）

MySpec（自有规格）的实际运行已经按目标工作树隔离规格运行状态，但公共技能文案仍使用“仓库级锁”的宽泛表述。与此同时，Gate 3（第三门禁）的外部项目技能重复维护了 MySpec 规格收口流程，并错误地把 Tarball（压缩包）打包带入 Gate 3，导致 Gate 3 与完整验证、发布流程的边界不清晰。

## Solution（方案）

统一公共语义：MySpec 的状态锁属于当前目标工作树；发布模式下不同关联工作树保持独立，可以并行；开发模式继续使用机器级单一开发源码绑定，源码工作树与目标工作树不一致时阻止写入，多个开发工作树只能切换后串行处理。

Gate 3 只通过官方 MySpec 技能入口执行规格操作，不打包、不安装、不强制选择 dev/release 模式，也不向外暴露内部锁和工作树实现。完整验证和发布继续使用受控打包入口。对齐正式文档后删除外部重复的规格收口技能。

## User Stories（用户故事）

1. 作为规格维护者，我希望看到“目标工作树锁”而不是“仓库级锁”的准确说明，从而知道哪些运行会互相阻塞。
2. 作为发布模式的多工作树用户，我希望不同工作树的规格运行状态互不阻塞，从而可以独立处理各自的规格变更。
3. 作为开发模式的多工作树用户，我希望知道全局开发源码绑定仍然是单一的，从而不会误以为开发写入支持并行。
4. 作为 Gate 3 使用者，我希望只面对官方 MySpec 入口，而不需要理解 Tarball、打包、安装或模式切换，从而避免误用错误的打包入口。
5. 作为仓库维护者，我希望只有仓库正式技能和工作规格描述 Gate 3 与 MySpec 的规则，从而避免外部重复技能产生漂移。

## Implementation Decisions（实现决定）

- 本变更只校正文案和正式规格语义，不改变 MySpec 运行时代码、锁实现、打包入口或发布工作流。
- 公开 MySpec 技能继续作为 MySpec 操作接口；Gate 3 只依赖该接口，模式、绑定、工作树和锁细节由 MySpec 内部处理。
- 正式规格描述目标工作树级运行锁、发布模式跨工作树隔离，以及开发模式单一源码绑定和错绑阻断。
- 不新增仓库级全局锁，不新增 Gate 3 专用 CLI（命令行程序），不增加开发模式并行绑定。
- 对齐仓库内语义后删除外部项目记忆中的重复技能；该删除属于用户环境清理，不作为仓库源码复制或运行时依赖。

## Testing Decisions（测试决定）

- 本次不新增运行时回归测试，因为运行行为不变；复用现有已安装 MySpec CLI 的公开入口测试作为行为依据。
- 保留并运行开发模式多工作树测试，确认绑定不一致时阻止写入、切换绑定后正常应用。
- 使用 MySpec 正式规格校验和仓库既有快速验证检查文档与规格工件；不把空检查结果当作验证证据。
- 继续确认完整验证和发布入口使用受控打包脚本，但不在 Gate 3 中执行打包。

## Out of Scope（范围外）

- 不修改 `management.py` 或 `spec_ops.py` 的运行逻辑。
- 不修改 `package.json`、`pack.py`、完整验证工作流或发布工作流。
- 不支持开发模式多个源码工作树并行写入。
- 不新增发布模式并发机制或仓库级锁。
- 不新增 Gate 3 专用包装命令。
- 不安装或同步任何客户端插件。

## Further Notes（补充说明）

开发模式的串行限制来自机器级单一开发源码绑定，而不是目标工作树锁；发布模式的并行边界来自各目标工作树的独立规格运行状态。两者必须在技能和正式工作规格中分别表达。
