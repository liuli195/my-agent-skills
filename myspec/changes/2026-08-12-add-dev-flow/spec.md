# Dev Flow（开发流程）

## Problem Statement

现有 `pi-development-flow` 依赖 Pi（编码代理）专属子代理策略、受控实施派发器和多工作树能力。它适合隔离和并行开发，但对于希望在当前工作树和当前功能分支中顺序完成开发的场景过重。直接改名或改造旧策略还会破坏旧流程的自举依赖；让新流程负责首次安装自己同样形成自举循环。

## Solution

保留旧轨 `pi-development-flow → pi-subagent-policy` 原样可用，另建完全独立的新轨 `dev-flow → subagent-policy`。两个新 Package（包）仅包含 Skill（技能）文档，不包含脚本、Extension（扩展）、运行时代码或安装器。

`subagent-policy` 提供宿主无关的固定角色契约，并在本次仅提供已验证的 Pi 映射。`dev-flow` 在调用时的同一工作树和同一非 `main` 功能分支中编排需求、串行实施、验证、审查、规格与交付；完整 PR Flow（拉取请求流程）只在最终交付阶段获准切换分支和清理。首次安装由本次仍在运行的旧流程完成源码交付后，依据用户的精确授权执行一次性本机切换，新流程不安装自己。

## User Stories

1. 作为开发者，我希望通过一个简洁入口完成开发变更，以减少手工串联 Skill（技能）的成本。
2. 作为开发者，我希望旧开发流程和旧子代理策略保持原样，以便新轨验证前仍可完成本次交付。
3. 作为维护者，我希望新旧两轨没有交叉依赖，以避免兼容层和自举循环。
4. 作为开发者，我希望当前分支为 `main` 或分离状态时流程在写入前停止，以避免绕过 PR（拉取请求）纪律。
5. 作为开发者，我希望开发和验证始终使用调用时的工作树和功能分支，以避免无收益的工作树与分支切换。
6. 作为开发者，我希望最终交付仍能执行完整 PR Flow（拉取请求流程），以保留合并、同步和安全清理能力。
7. 作为开发者，我希望四个固定 Subagent roles（子代理角色）保持清晰职责，以便不同宿主以后映射相同语义。
8. 作为开发者，我希望每个角色使用固定模型、思考强度、能力和提示词，以获得稳定执行结果。
9. 作为开发者，我希望角色或模型无法证明时在派发前停止，以避免静默降级。
10. 作为开发者，我希望 Architect（架构师）负责总体设计和困难诊断，以集中高成本推理。
11. 作为开发者，我希望 Explorer（探索者）只做只读调查，以避免调查阶段产生意外写入。
12. 作为开发者，我希望 Implementer（实施者）是唯一写入者并严格串行，以避免同一工作树发生并发冲突。
13. 作为开发者，我希望 Reviewer（审查者）独立审查实际差异，以避免实施者自行放行。
14. 作为开发者，我希望主 Agent（代理）根据实际分支、提交、差异、工作区和验证结果验收子代理，而不是相信完成报告。
15. 作为开发者，我希望新流程只保留“开始开发”和“规格与交付”两次正式确认，以减少重复门禁。
16. 作为开发者，我希望门禁确认在失败恢复期间继续有效，以避免重复确认同一动作。
17. 作为开发者，我希望功能、缺陷和集成行为先出现失败检查再实现，以证明检查对目标行为敏感。
18. 作为开发者，我希望 Build and Verify（构建与验证）仍是唯一验证入口，并拒绝空检查通过。
19. 作为开发者，我希望代码审查限定于固定基线后的实际差异和必要上下文，以控制成本。
20. 作为开发者，我希望正式规格和 PR（拉取请求）在最终确认后连续交付，以减少交付中断。
21. 作为 Claude 或 Codex 用户，我希望缺少本次未提供的子代理适配时得到明确停止结果，而不是假装完整支持。
22. 作为 Pi 用户，我希望新进程能从共享目录联接发现新轨两个 Skill（技能），以复用同一源码。
23. 作为维护者，我希望首次安装在新 PR 合并后由旧流程中的主 Agent（代理）执行，以消除自安装循环。
24. 作为维护者，我希望新轨真实验证成功后才停用旧两个 Pi 包登记，以保留安全回退路径。
25. 作为维护者，我希望首次切换失败时恢复本次用户配置和目录联接修改，以避免留下部分安装状态。

## Implementation Decisions

- 旧 `pi-development-flow`、旧 `pi-subagent-policy`、相关测试和正式规格保持不变。
- 新建仅含 Skill（技能）的 `subagent-policy` 本地 Package（包），不提供运行时派发或配置安装。
- 新建仅含 Skill（技能）的 `dev-flow` 本地 Package（包），通过渐进式披露加载需求、实施和交付规则。
- `Subagent Policy（子代理策略）` 是宿主无关角色契约；本次只实现和验证 Pi 映射，Claude 与 Codex 适配后续另行开发。
- Pi 固定矩阵为：Explorer 使用 `openai-codex/gpt-5.6-luna` 与 low（低）；Implementer 使用同一模型与 max（最大）；Reviewer 使用 `openai-codex/gpt-5.6-sol` 与 medium（中）；Architect 使用同一模型与 max（最大）。
- 策略校验角色描述、模型、思考强度、能力、提示模式和提示词；任何差异都会停止本次委派。
- 新流程使用 Policy-validated Agent dispatch（策略校验 Agent 派发），不使用 `dispatch_implementer_in_worktree`。
- 新流程的硬前提是当前 Git（版本管理）工作树干净、当前分支为非 `main` 功能分支且非分离状态；流程不创建或切换开发工作树和功能分支。
- 只读子代理仅在稳定状态下并行；任一时刻最多一个 Implementer 写入，主 Agent 不直接修改 Git 可见实施文件。
- 新流程使用两次正式 Gate Confirmation（门禁确认）：开始开发，以及规格与交付；Completion Check（完成检查）不是第三次授权门禁。
- 新门禁结果只包含“核心摘要”和“确认后进入的下一步”。
- 最终交付复用完整 PR Flow（拉取请求流程）；该阶段允许其切换目标分支并执行安全清理。
- 首次安装不是 `dev-flow` 的运行阶段。新源码 PR 合并后，当前旧流程中的主 Agent根据精确授权创建 `.agents\skills` 和 `.claude\skills` 目录联接，验证三个新客户端进程，再停用旧 `pi-development-flow` 与 `pi-subagent-policy` 的 Pi 包登记。
- 首次安装不新增安装 Skill（技能）、安装插件或脚本。

## Testing Decisions

- 最高公开测试接缝是 Pi、Claude 和 Codex 的真实新进程 Skill（技能）发现和调用入口，不以直接解析 Markdown（标记文档）代替。
- Pi 成功路径验证新进程发现两个新 Skill、策略接受固定四角色配置、`dev-flow` 在非 `main` 功能分支进入正式流程，并证明直接子代理继承当前工作目录。
- Pi 停止路径分别验证 `main`、分离状态、错误角色、错误模型、错误思考强度、错误能力或无法证明工作目录时零写入停止。
- Claude 和 Codex 本次只验证发现新 Skill，并在缺少宿主适配时明确停止。
- 功能行为遵循 TDD（测试驱动开发），先通过同一公开接缝产生失败检查，再做最小实现。
- Build and Verify（构建与验证）是唯一构建检查和验证入口；快速验证必须报告 `passed` 且 `checked` 非空。
- 首次本机切换前备份目标配置和目录状态，切换后分别运行真实客户端冒烟；失败时恢复并比较备份。
- 旧轨测试保持通过，证明新增新轨未改写旧源码行为。

## Out of Scope

- Claude 和 Codex 的固定角色配置、模型映射及原生子代理适配。
- 新派发器、安装器、脚本、Extension（扩展）、Hook（钩子）或运行状态机。
- 修改、重命名、删除或兼容包装旧 `pi-development-flow` 与旧 `pi-subagent-policy`。
- 多工作树、并行写入、自动模型降级和兼容入口。
- 让 `dev-flow` 安装或更新自己。
- 市场发布、版本发布和其他未点名的客户端同步。

## Further Notes

整体按 High risk（高风险）处理，因为最终切换会修改用户配置和目录联接；纯 Skill（技能）源码部分仍采用与行为风险匹配的最小验证。首次切换属于本次明确请求的独立本机动作，不成为未来 `dev-flow` 的默认交付职责。
