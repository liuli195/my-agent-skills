# 发布前校验 npm 来源证明仓库元数据

**Status:** ready-for-agent

## Problem Statement

Release Flow（发布流程）的发布前检查没有验证待发布 npm（软件包管理器）包声明的仓库地址和包目录是否与当前 GitHub（代码托管平台）仓库一致。错误配置可能在构建和完整验证均通过后，直到 `npm publish --provenance`（带来源证明发布）才被拒绝，造成整轮发布失败和重复交付。

当前发布工作流包含针对本仓库的重复硬编码检查，但这些检查发生较晚，不能作为 Release Flow（发布流程）的通用发布契约，也不能在日常构建阶段提供反馈。

## Solution

Release Flow（发布流程）维护唯一的 npm 来源证明仓库元数据校验规则。Build and Verify（构建与验证）通过仓库构建配置调用该规则，在日常构建阶段提前发现问题；发布前检查、本地发布触发和远端发布计划仍分别强制执行同一规则，避免任何入口绕过。

构建检查验证所有已登记的 npm 包；发布入口只验证本次选择发布的 npm 包。源码清单通过校验后，发布工作流继续确认 Tarball（npm 软件包）中的仓库元数据没有在打包过程中丢失或改变。

## User Stories

1. 作为维护者，我希望构建检查验证所有已登记 npm 包的来源证明仓库元数据，以便在进入发布流程前发现错误。
2. 作为发布操作者，我希望发布前检查只验证本次选择发布的 npm 包，以便无关包不会阻断其他插件发布。
3. 作为发布操作者，我希望仓库地址缺失、仓库不匹配或大小写不匹配时立即停止，并看到清单位置、实际值、期望值和恢复动作。
4. 作为单仓多包维护者，我希望包目录缺失或指向错误目录时立即停止，即使错误目录真实存在。
5. 作为发布操作者，我希望无法确定当前 GitHub 仓库身份时失败关闭，而不是静默跳过来源证明校验。
6. 作为直接调用发布命令的操作者，我希望远端工作流只在元数据通过校验后触发。
7. 作为持续集成维护者，我希望本地检查和远端发布计划使用同一规则，以免两套判断发生漂移。
8. 作为软件包消费者，我希望发布工作流确认 Tarball 中的仓库元数据与已校验的源码清单一致。
9. 作为仓库维护者，我希望删除工作流中的仓库名称硬编码，同时保留包名、公开访问、安装和完整性检查。
10. 作为 MySpec（自有规格）维护者，我希望现有 Tarball 打包、隔离安装、诊断和完整验证继续通过。

## Implementation Decisions

- Release Flow（发布流程）拥有仓库元数据规则及错误语义；Build and Verify（构建与验证）只负责编排仓库配置声明的命令，不内置业务规则。
- 深化 Release Flow（发布流程）现有项目校验 Interface（接口），不新增顶层命令、配置来源、依赖或独立校验程序。
- 构建检查调用项目校验并检查所有已登记且实际存在的 npm 包。
- 发布前检查和发布触发只检查本次选择发布的 npm 包；远端发布计划继续调用相同发布前检查。
- 本地仓库身份来自 Git `origin`（远端）；GitHub Actions（GitHub 自动化任务）中的仓库身份来自受信任的工作流环境。
- 接受 HTTPS（安全超文本传输协议）、SSH（安全外壳协议）、`git+https` 和可选 `.git` 后缀，并归一化为 GitHub 所有者和仓库名；所有者和仓库名保持大小写敏感。
- 无法取得 GitHub 仓库身份、仓库身份冲突或使用不支持的主机时失败关闭。
- 单仓多包的 `repository.directory` 必须存在，并精确指向包含该包清单的仓库相对目录。
- 失败输出必须包含稳定错误类型、包清单位置、期望值、实际值和可执行恢复提示。
- 打包后检查比较源码清单与 Tarball 清单中的仓库元数据，不再写死当前仓库名称或包目录。
- 不新增领域术语或 ADR（架构决策记录）。

## Testing Decisions

- 最高公开测试接缝是 Build and Verify（构建与验证）的真实 `build`（构建检查）命令，以及 Release Flow（发布流程）的项目校验、发布前检查和发布命令。
- 使用真实命令行测试，而不是把内部解析函数作为主要测试表面。
- Red（红灯）必须覆盖仓库地址缺失、错误仓库、错误大小写、错误但存在的目录、无法确定 GitHub 仓库身份和正确配置。
- 发布测试必须证明元数据错误时不会触发远端工作流。
- 远端发布计划测试必须证明发布前检查发生在候选包打包之前，并与本地检查使用同一行为。
- 构建配置测试必须证明构建命令检查所有已登记 npm 包；快速验证在相关包清单、Release Flow（发布流程）或发布工作流变化时选择对应检查，且 `checked`（已检查项）非空。
- 打包后检查必须证明 Tarball 仓库元数据与源码一致，同时保留现有包名、公开访问、隔离安装、诊断和完整性检查。
- 最终使用 Build and Verify（构建与验证）执行有效快速验证和完整验证，并从真实构建命令及发布前检查命令执行最小冒烟。

## Out of Scope

- npm 首次建包、双重验证和 Trusted Publisher（可信发布者）配置。
- 自动修改或修复包清单。
- 私有仓库、GitHub Enterprise（GitHub 企业版）或其他代码托管平台。
- OIDC（开放身份认证）配置、签名或透明日志验证。
- 修改包名、发布访问级别、完整性算法或打包器。
- 自动执行真实 npm 发布。
