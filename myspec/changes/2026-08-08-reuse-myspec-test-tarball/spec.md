# 复用 MySpec 测试候选包

## Problem Statement（问题陈述）

MySpec（自有规格）的快速验证需要证明当前检出的真实 npm Tarball（npm 软件包）能够在隔离环境运行，但现有本地验证在大量测试中重复执行同一次官方打包和隔离安装。单次 `verify.my-spec`（MySpec 验证）长期耗时数分钟，并且现有覆盖尚未直接证明 Windows/Linux 安装路径以及宿主 PATH（可执行文件搜索路径）不会污染隔离运行。

## Solution（解决方案）

每次非缓存 `verify.my-spec`（MySpec 验证）在并行工作进程启动前，通过现有官方打包 Interface（接口）生成一次当前检出的只读候选 Tarball（压缩包），或复用 CI（持续集成）明确提供的同一候选包。所有工作进程共享该只读包；只有需要证明发布形态的场景执行独立安装和真实 CLI（命令行程序），普通逻辑分支通过进程内 Interface（接口）和模拟命令运行，并保持用户目录、日志和运行状态隔离。验证同时锁定 Windows/Linux 路径推导、宿主 PATH 隔离，以及至少一条完整的裸 `myspec` 发布形态流程。

## User Stories（用户故事）

1. 作为贡献者，我希望一次 MySpec 快速验证只打包一次当前检出内容，以便更快得到可信反馈。
2. 作为贡献者，我希望本地验证和 CI 使用同一官方打包入口，以便两种环境验证相同发布形态。
3. 作为维护者，我希望并行测试共享只读候选包但不共享可写状态，以便性能优化不会引入顺序依赖或并行污染。
4. 作为发布维护者，我希望验证通过隔离安装后的裸 `myspec` 执行完整业务流程，以便机器预装版本不能代替候选版本。
5. 作为跨平台维护者，我希望 Windows 与 Linux 的 npm 安装布局都有确定性覆盖，以便路径推导不会只在 CI 暴露问题。
6. 作为测试维护者，我希望宿主 PATH 中已有同名命令时隔离测试仍只使用受控命令，以便开发机器状态不会产生假通过。
7. 作为审查者，我希望性能报告包含可复现的前后耗时和打包次数，以便确认优化真实有效且没有降低覆盖。
8. 作为后续维护者，我希望模拟旧版或升级包继续作为独立测试输入，以便运行级候选包复用不会改变版本迁移场景。

## Implementation Decisions（实施决策）

- 复用现有官方打包 Module（模块）及其命令 Interface（接口），不增加平行打包实现。
- 在测试控制进程启动并行工作进程之前建立运行级候选包 Seam（接缝）；本地生成与 CI 提供是该 Seam 的两个既有 Adapter（适配器）。
- 候选包在一次测试运行中只读共享；真实发布形态测试的安装前缀以及全部测试的 HOME、USERPROFILE、MySpec 运行目录、日志和状态保持隔离。
- 只有需要证明 Tarball（压缩包）、启动器、安装或进程行为的场景执行真实安装或 CLI；普通 management/spec_ops 分支复用每个工作进程的轻量只读包树并通过进程内模拟命令运行。
- 删除不再提供独立行为证据的重复 E2E（端到端）逻辑；不得删除票据 01 的完整真实发布形态路径或尚无其他测试接缝覆盖的行为。
- 测试生成的其他版本、故障注入包或启动标记包不是当前候选包，继续按场景独立生成。
- 不共享可写安装结果；需要修改包内容或安装状态的模拟场景使用测试级私有轻量副本。
- CI 已提供候选包时继续复用并验证其存在；本地标准入口缺少候选包时自动生成一次。
- 本变更不增加依赖，不修改 MySpec 产品行为、包格式、官方打包实现或 Build and Verify（构建与验证）运行器。

## Testing Decisions（测试决策）

- 最高公开测试 Seam（接缝）是以变更前固定 Verification Baseline（验证基线）运行 Build and Verify（构建与验证）快速验证。
- 最终结果必须命令成功、`checked`（已检查）非空且包含 `verify.my-spec`，并报告 `status: passed`（通过）。
- 至少一条测试通过当前检出生成的 Tarball（压缩包）完成隔离安装，并从隔离 PATH 中调用裸 `myspec` 执行校验、预览、差异和正式应用。
- 使用 Windows 与 Linux 合成安装路径锁定 npm 前缀推导。
- 在宿主 PATH 放置同名假命令，证明隔离环境只解析测试安装的 `myspec`，且不会发现宿主 `pi`、`claude` 或 `codex`。
- 在 4 个并行工作进程下证明当前候选包只生成一次、所有进程消费同一只读包，而每个测试的可写状态互不相同。
- 性能比较在同一机器和同类非缓存环境中对变更前后各运行三次，记录 `verify.my-spec` 耗时、总耗时、打包次数、`checked` 和最终状态；单次检查稳定在约 30 秒为通过标准。
- 直接定向测试只能作为 Red/Green（红灯/绿灯）证据，不能替代最高公开测试 Seam（接缝）。

## Out of Scope（范围外）

- 修改 MySpec 业务命令、生命周期行为、包内容或发布流程。
- 修改官方打包 Module（模块）或 Build and Verify（构建与验证）运行器。
- 复用同一个可写 npm 安装前缀、用户目录或 MySpec 运行状态。
- 自动操作真实 Pi、Claude 或 Codex 的机器级状态；相关工作仍属于 Issue #220 和 #221。
- 删除尚无其他测试接缝覆盖的独立可观察行为，或删除票据 01 的真实发布形态覆盖。
- 在本变更中降低现有超时，或宣称单项优化已经满足整个仓库完整验证低于 60 秒的目标。
- 发布、版本升级、本地安装或客户端同步。
