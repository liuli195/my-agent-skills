# 发布运行时与规格增量字节保持

**Status（状态）：** ready-for-agent

## Problem Statement（问题说明）

发布工作流仍使用 Node.js 20（运行时）动作运行时，导致发布日志持续出现弃用警告；已有的运行时升级遗漏了候选包上传动作，且回归检查没有覆盖该动作。

MySpec（自有规格）的 Delta（增量）应用会在 Windows（视窗操作系统）上重新渲染整个规格库。平台默认换行转换会使未被 Delta 指定的规格文件产生字节差异，污染工作树并迫使调用方额外恢复文件。

## Solution（方案）

将发布工作流及其生成模板中的候选包上传动作升级到首个使用 Node.js 24（运行时）的 `@v6` 版本，并让工作流契约检查覆盖该动作。

让 Delta 应用以原规格库为字节保持基线：预览和最终原子应用复制未发生语义变化的文件，仅写入实际变化或新增的文件；目标文件和新增文件统一使用 `LF`（换行符）。删除的规格文件不保留。现有公开命令、Delta 语义、校验和失败恢复保持不变。

## User Stories（用户故事）

1. 作为发布维护者，我希望发布工作流不再调用 Node.js 20 动作运行时，从而不再产生已知弃用警告。
2. 作为工作流模板维护者，我希望新生成的发布工作流与当前发布工作流使用相同动作版本，从而不会重新引入旧运行时。
3. 作为规格维护者，我希望只应用一个能力的 Delta 时，其他能力的文件不产生 Git（版本管理）差异，从而能直接审查预期变更。
4. 作为 Windows 用户，我希望原本为 `LF` 或 `CRLF` 的非目标规格保留原始字节，从而不会被平台换行策略污染。
5. 作为规格维护者，我希望预览结果和最终原子应用遵循相同的文件保持规则，从而预览不会与最终工作树结果不一致。
6. 作为规格维护者，我希望目标规格仍能通过主规格校验，从而字节保持不会牺牲语义正确性。
7. 作为规格维护者，我希望应用失败时仍恢复原规格库，从而不会因保持文件字节而增加数据丢失风险。
8. 作为仓库维护者，我希望回归检查覆盖实际用户入口，从而入口行为变化不会只在私有辅助函数测试中被发现。

## Implementation Decisions（实现决定）

- 发布工作流和发布工作流模板保持现有触发器、权限、候选包上传行为和发布顺序，只升级候选包上传动作到 `@v6`。
- 工作流契约检查同时读取当前发布工作流和生成模板，拒绝已知 Node.js 20 运行时动作版本，并要求候选包上传动作使用 `@v6`。
- Delta 应用继续通过同一个公开命令完成预览和最终应用；不增加命令参数，不要求调用方恢复非目标文件。
- 规格应用内部以原规格库为保持基线。语义结果与原文件等价的文件直接保留原始字节；语义变化、新增文件使用统一 `LF` 输出；删除结果对应的旧文件被移除。
- 预览和最终原子应用共用同一套保持规则；现有目录级原子替换和失败恢复继续生效。
- 不新增依赖，不扩展发布流程，不改变 Delta 操作、主规格校验或重复应用语义。

## Testing Decisions（测试决定）

- #123 使用工作流契约的公开测试接缝，覆盖当前发布工作流和发布模板；检查动作版本及现有候选包发布顺序，不执行真实发布。
- #259 使用公开 `myspec apply-delta` 命令和临时规格库，不直接测试私有写入辅助函数。
- #259 回归案例同时提供 `LF` 和 `CRLF` 原始文件，Delta 只修改一个能力；预览和最终应用均检查非目标文件的原始字节完全不变、目标语义改变、目标输出为 `LF`，并通过主规格校验。
- 回归检查覆盖应用失败恢复和相同 Delta 重复应用，确保现有原子性和幂等性不退化。
- 实现阶段先以同一回归检查产生红灯，再以公开入口转绿；随后运行 Build and Verify（构建与验证）快速检查，并完成 Windows（视窗操作系统）真实入口冒烟。

## Out of Scope（范围外）

- 不修改已关闭的 #260 或历史 `myspec/changes/` 记录。
- 不升级其他 GitHub Action（自动化动作），不调整发布权限、触发方式或 npm（Node 包管理器）发布认证。
- 不改变 MySpec 公开命令、Delta 语义、主规格格式、冲突状态或原子失败恢复协议。
- 不要求统一整个规格库已有文件的换行格式；只规定变化和新增文件使用 `LF`。
- 不执行真实发布、推送、合并或用户环境安装同步。
