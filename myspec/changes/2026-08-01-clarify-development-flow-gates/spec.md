# 明确 Pi Development Flow（Pi 开发流程）阶段依赖与门禁

## Problem Statement

Development Flow（开发流程）已经定义四个门禁等待点，但阶段参考文档没有在正文前统一说明本阶段依赖、进入条件、等待内容、通过条件和恢复位置。执行者可能把主 Skill（技能）中的门禁当成概述，在进入阶段正文后才发现约束，甚至用后续授权追认此前修改。

## Solution

在全部五份参考文档开头明确依赖和门禁。Requirements（需求）、Implementation（实施）和 Delivery（交付）分别说明自己负责的四个既有门禁；Initialization（初始化）只说明初始化授权及返回位置；Resume（恢复）只识别四个门禁中的首个未完成项。缺少核心依赖、加载失败或门禁未通过时停止，并报告准确恢复入口。

## User Stories

1. 作为 Development Flow 使用者，我希望进入阶段正文前看到本阶段依赖，以便缺少核心 Skill 时立即停止。
2. 作为 Development Flow 使用者，我希望进入阶段正文前看到适用门禁，以便知道当前允许执行什么。
3. 作为需求确认者，我希望需求、测试接缝和纵向票据获批后才发布需求产物。
4. 作为需求确认者，我希望需求产物提交后流程展示实施计划并等待独立实施授权。
5. 作为实施授权者，我希望未收到实施授权时流程不修改代码、行为或其他状态。
6. 作为规格确认者，我希望整体审查和验证完成后单独确认正式 MySpec（自有规格）差异。
7. 作为交付授权者，我希望推送、PR（拉取请求）创建或更新、合并及最终清理等待独立交付授权。
8. 作为初始化使用者，我希望初始化授权不会被误记为四个开发门禁中的任意授权。
9. 作为恢复流程使用者，我希望流程从已有证据识别首个未完成门禁，而不创造或推断授权。
10. 作为维护者，我希望契约检查能发现任一参考文档遗漏依赖块或门禁块。
11. 作为维护者，我希望真实 Pi（编码代理）证明缺少授权时流程停止且仓库保持不变。

## Implementation Decisions

- 保留现有四个门禁，不新增门禁或权限体系。
- 五份参考文档都在正文前设置醒目的依赖块和门禁块。
- Requirements 负责门禁 1，并在需求产物提交后停在门禁 2。
- Implementation 以门禁 2 为进入条件，并在验证和整体审查完成后停在门禁 3。
- Delivery 负责门禁 3 和门禁 4。
- Initialization 说明自己的初始化授权和完成后的返回位置，但不把它命名为第五个开发门禁。
- Resume 只重建四个门禁的完成状态并恢复首个未完成门禁。
- 每个依赖块列出本阶段核心外部 Skill；缺失、不可读、加载失败或使用替代入口时停止。
- 每个门禁块说明检查清单、通过条件、必须等待的单独确认和失败后的恢复入口。
- 实施授权只允许执行已确认实施计划中的修改，不能追认门禁前的修改。
- 只修改 Skill 文本和现有测试，不修改 Pi Extension（Pi 扩展）程序。

## Testing Decisions

- 扩展现有 Pi Development Flow 契约检查，覆盖全部五份参考文档开头的依赖块和门禁块。
- 契约检查验证四个既有门禁与各文档职责对应，不接受新增门禁或缺失恢复入口。
- 最高公开测试接缝是在临时 Git（版本管理）仓库中启动新的 Pi 进程，加载本地 Development Flow 包并进入各参考入口。
- 真实冒烟确认缺少对应授权时流程停止，报告恢复门禁，并且仓库 Git 状态保持不变。
- 所有正式检查通过 Build and Verify（构建与验证）入口运行。

## Out of Scope

- 不新增第五个开发门禁。
- 不建设新的授权范围或权限模型。
- 不修改插件程序、Pi 本体或用户级 Skill。
- 不修改用户或机器配置、安装状态及外部客户端。
- 不改变四个门禁原有顺序和业务含义。

## Further Notes

本变更解决 GitHub Issue（问题）#250。变更属于 Standard（标准）Flow Level（流程等级）：它修复 Development Flow 的可观察执行规则，但实现只涉及 Skill 文本、契约检查和只读真实冒烟。
