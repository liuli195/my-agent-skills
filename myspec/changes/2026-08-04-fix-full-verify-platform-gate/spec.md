# 修复跨平台 Full Verify（完整验证）合并门禁

## Problem Statement

当前持续集成（CI）已经运行 Linux 和 Windows 平台验证，但合并门禁只读取名为 `Full Verify` 的单个平台任务。另一个平台任务失败时，拉取请求可能仍被判断为通过并进入合并，导致“完整验证”与实际合并安全性不一致。

## Solution

将 `Full Verify` 定义为唯一的跨平台验证汇总门禁：所有纳入门禁的平台验证任务必须成功，汇总门禁才成功；任一任务失败、取消或跳过时，汇总门禁必须失败或保持阻塞。保留现有平台验证内容和统一验证入口，不扩展到外部仓库。

## User Stories

1. 作为仓库维护者，我希望 Linux 和 Windows 验证都成功后才允许合并，从而避免单个平台失败被遗漏。
2. 作为拉取请求流程使用者，我希望流程读取的 `Full Verify` 就是跨平台汇总结果，从而不需要理解各个平台任务的内部名称。
3. 作为验证失败的维护者，我希望失败平台能让唯一必需检查失败，从而能直接定位并修复问题。
4. 作为仓库维护者，我希望现有平台验证并行执行，从而不会因增加汇总门禁而不必要地串行化检查。

## Implementation Decisions

- 平台验证任务继续独立执行，新增一个最终汇总任务作为唯一 `Full Verify` 必需检查。
- 汇总任务等待 Linux 和 Windows 任务完成，并将每个任务的结果限定为 `success` 才视为通过。
- 汇总任务在依赖任务失败、取消或跳过后仍执行结果判断，避免被跳过状态伪装成成功。
- 现有拉取请求流程继续读取名为 `Full Verify` 的必需检查；不修改其运行时代码和远端检查名称。
- 本次变更只修复本仓库的持续集成门禁，不抽取外部仓库通用工作流，也不修改 Build and Verify（构建与验证）插件。

## Testing Decisions

- 最高测试接缝是真实拉取请求的 GitHub 必需状态检查：成功场景下 `Full Verify` 必须指向汇总任务；平台失败场景下该检查必须失败或保持阻塞。
- 本地回归检查验证工作流契约：平台任务仍存在且并行，汇总任务依赖全部平台任务，并严格检查任务结果。
- 按测试驱动开发（TDD）先让工作流契约检查在当前实现上失败，再实现最小汇总门禁并让同一检查通过。
- 完成实现后通过 Build and Verify 快速验证，并执行一次真实拉取请求成功路径冒烟；平台失败路径使用受控持续集成失败场景验证，不以本地静态检查替代。

## Out of Scope

- 不修改 Build and Verify 插件或其配置语义。
- 不修改 PR Flow（拉取请求流程）运行时代码。
- 不扩展外部仓库或发布通用可复用工作流。
- 不改变 Linux、Windows 工作树验证的具体命令和覆盖范围。
- 不自动修改 GitHub Rulesets（GitHub 规则集）；现有必需检查名称保持不变。

## Further Notes

问题 #237 的历史证据表明，Windows 任务失败已经能够被 GitHub 记录，但未进入必需检查结果。该变更补齐的是平台结果到合并门禁之间的汇总接缝，而不是重新增加验证内容。
