# 规格与交付

仅在实施、验证和基于固定基线的限定审查全部验收通过后加载此参考文档。

## MUST — 必须依赖

- 当前阶段必须可读并实际使用官方 MySpec（自有规格）路由和 `pr-flow-complete`（完成拉取请求流程）；需要规格变更时使用 `my-spec-add`（新增自有规格）。依赖缺失、不可读或无法核验时，停在交付阶段。
- 门禁二前不得应用规格差异、切换分支、合并、同步基础分支或清理工作树。完整 PR Flow（拉取请求流程）只在门禁二授权后执行；失败时保留现场并在原授权中恢复失败动作。
- 交付和清理必须依据 Git worktree registration（Git 工作树登记），而不是 `main` 名称、路径名称或宿主判断工作树身份；安全操作不得使用强制清理。

## 流程编排

1. 按官方 MySpec 路由，根据已验证行为准备完整正式规格预览；重新核对预览、需求数量、验证证据、已知风险和准确交付动作。完成条件是预览完整、差异未提前应用且实施阶段证据可复核。
2. 在“核心摘要”中完整展示正式规格摘要、验证证据、已知风险和准确 PR（拉取请求）动作，明确当前是`门禁二——规格与交付`，然后判断上下文是否对当前门禁动作给出明确授权。两个门禁采用同一语义：展示完整内容后，“确认”“可以”“继续实施/交付”等明确授权可以；不得要求固定口令。沉默、提问、修改需求、仅确认某个细节、以前门禁授权或含义不清不能视为当前授权，不确定时停留并澄清。完成条件是只记录一次门禁二授权或明确阻塞。
3. 门禁二授权后，重新核对被引用状态，通过 MySpec 应用并验证已批准规格，然后调用 `pr-flow-complete`。该次授权同时覆盖规格应用和选定完整交付，不再请求第二次交付确认；失败时保留状态并恢复失败动作。完成条件是每个动作都有实际结果和恢复状态。
4. 只有门禁二授权后，完整 PR Flow 才可切换分支、合并、同步基础分支和执行安全、非强制清理。使用 `--remove-worktree`（删除工作树参数）时，primary worktree（主工作树）绝不会被删除；完成后它在实际 target/base branch（目标/基础分支）的最新提交上检出该分支。registered linked non-primary worktree（已登记关联非主工作树）只有活跃 Agent（代理）会话仍在其中时，才在该提交上以 detached HEAD（分离头）状态保留；外部调用时删除。如果切换提交前发现活跃 cwd（当前工作目录）在目标提交中不存在且未被 Git 忽略，停止且不设置 `removeWorktreePending`（工作树删除待处理）或外部 `nextCommand`（下一命令）。完成条件是清理状态和工作树登记、实体路径、提交、分支证据一致。
5. 在触发交付的步骤中执行完成检查：报告规格有效性、已合并 PR、已同步基础分支、已删除分支以及工作树登记和实体目录结果。primary worktree 的登记和实体目录仍存在、已在实际目标/基础分支最新提交、源分支已删除、状态为 `cleanup_complete` 且无 `removeWorktreePending` 或外部 `nextCommand` 时，明确报告安全保留主工作树；活跃会话中的关联工作树以 detached HEAD 指向该提交时同样可报告成功保留。其他实体工作树目录报告准确路径、原因和证据；只有需要强制清理该准确遗留项时，才另行请求明确授权。完成检查不是第三个授权门禁，且其他 PR Flow 停止状态仍是未完成、可恢复状态。
