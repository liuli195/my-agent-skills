# 规格与交付

仅在实施、验证和基于固定基线的审查均验收通过后加载此参考文档。

## 门禁二——规格与交付

1. 使用官方 MySpec（自有规格）路由，包括在需要规格变更时使用 `my-spec-add`（新增自有规格），根据已验证行为准备完整的正式规格预览。请求确认前，重新检查预览、需求数量和准确的交付动作。不得提前应用规格差异。
2. 使用上级规定的两个输出区块，展示正式规格摘要、验证证据、已知风险和准确的 PR（拉取请求）动作。只请求`规格与交付`；这一次确认同时授权规格应用和所选的完整 PR Flow（拉取请求流程）。
3. 确认后，重新检查所引用的状态，通过 MySpec（自有规格）应用并验证已批准的规格，然后自动调用 `pr-flow-complete`（完成拉取请求流程）。不得请求第二次交付确认。如果应用或交付失败，保留状态，并在同一个持续有效的确认下恢复失败动作。
4. 只有在此次确认后，完整 PR Flow（拉取请求流程）才可以切换分支、合并、同步基础分支并执行安全且非强制的清理。工作树身份来自 Git worktree registration（Git 工作树登记），而不是 `main` 名称、路径名称或宿主。使用 `--remove-worktree`（删除工作树参数）时，primary worktree（主工作树）绝不会被删除，完成后会在实际 target/base branch（目标/基础分支）的最新提交上检出该分支；registered linked non-primary worktree（已登记关联非主工作树）只有当活跃 Agent（代理）会话仍位于其中时，才会在该提交上以 detached HEAD（分离头）状态保留，从外部调用时仍会被删除。如果切换提交时活跃 cwd（当前工作目录）在目标提交中不存在且未被 Git（版本管理）忽略，则在切换前停止。将 active-session retention（活跃会话保留）报告为成功，不得设置 `removeWorktreePending`（工作树删除待处理）或移交外部 `nextCommand`（下一命令）。其他所有 PR Flow（拉取请求流程）停止状态都应视为未完成且可恢复，不得视为最终完成。

## 完成检查

报告交付后的实际最终状态：规格有效性、已合并的 PR（拉取请求）、已同步的基础分支、已删除的分支和工作树结果。使用 `--remove-worktree`（删除工作树参数）时，如果 primary worktree（主工作树）的 Git registration（Git 登记）和实体目录仍存在、它在实际 target/base branch（目标/基础分支）的最新提交上检出该分支、源分支已删除，并且状态是 `cleanup_complete`（清理完成），且不存在 `removeWorktreePending`（工作树删除待处理）或外部 `nextCommand`（下一命令），则明确保留主工作树属于安全完成。registered linked non-primary worktree（已登记关联非主工作树）只有当活跃会话仍位于其中，并且其 HEAD（当前提交）以 detached HEAD（分离头）状态指向该提交时，才可以在相同状态下安全完成；从外部调用时应将其删除。两种保留都应报告为成功，而不是清理遗留。任何需要切换提交、但活跃 cwd（当前工作目录）在目标提交中不存在且未被 Git（版本管理）忽略的情况，都必须在切换前停止。对于仍然存在的其他实体工作树目录，报告其准确路径、原因和证据；只有需要强制清理该准确遗留项时，才单独请求明确授权。
