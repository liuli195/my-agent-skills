# 需求

仅在执行需求路由和`门禁一——开始开发`时加载此参考文档。

## MUST — 必须依赖

- Full（完整）路径必须按入口规则解析并依次加载、读取和实际调用 `subagent-policy`（子代理策略）、由 Architect（架构师）实际使用的 `codebase-design`（代码架构）、`grill-with-docs`（带文档拷问）及其调用的 `grilling`（拷问）和 `domain-modeling`（领域建模）、`to-spec`（转为规格）与 `to-tickets`（转为票据）。
- Fast（快速）路径必须按入口规则解析并依次加载、读取和实际调用 `to-spec` 与 `to-tickets`。
- 任一依赖无法按入口规则唯一加载时立即停止，报告失败依赖、当前步骤和需求阶段恢复位置；只记录名称或自行替代不算加载。

## 流程编排

1. 只读证明仓库根目录、Git（版本管理）工作树登记、有名称的非 `main` 功能分支、干净起始状态和固定验证基线；记录工作树、分支、票据顺序和真实阻塞项。门禁一授权前保持只读并沿用当前工作树和分支。完成条件是全部证据可由只读检查复核。
2. 选择 Flow Level（流程等级）。Fast（快速）使用当前会话逐项具备的可复现失败检查、已验证根因、现有公开测试接缝、最高层级真实用户入口、一个纵向切片和无未解决需求的证据；安全、权限、数据、迁移、发布、机器状态、跨系统或破坏性风险，以及范围扩大或第二个独立切片，使用 Full（完整）。**Full（完整）**是其他情况的默认等级，并在门禁一记录等级和证据。
3. Full（完整）路径先实际调用并核验 `subagent-policy`，在首次委派前按固定角色、模型、思考强度和读写边界准备提示词；再委派 Architect（架构师）实际使用 `codebase-design`，核验源码位置、不确定项、可观察结果、范围和最高层级公开测试接缝；随后实际调用 `grill-with-docs`，并核验它实际调用 `grilling` 与 `domain-modeling`；最后依次实际调用 `to-spec` 和 `to-tickets`。每一步都记录来源、产出和当前会话可复核的实际使用证据。
4. Fast（快速）路径逐项核验并复用当前会话证据；实际调用 `to-spec` 固定可观察契约和最高层级公开测试接缝，再实际调用 `to-tickets` 验证已有请求是否是一个可独立观察的纵向票据。已有单一纵向票据时沿用现有票据；其余请求按纵向票据结果拆分。
5. 将需求产物保存到同一 change 目录，并遵循 `docs/agents/issue-tracker.md`：`to-spec` 写入 `myspec/changes/<change-name>/spec.md`，`to-tickets` 将每张票据按依赖顺序分别写入 `myspec/changes/<change-name>/issues/NN-<slug>.md`，不得改用 `.scratch`。完成条件是规格和全部票据非空，且可观察范围和公开测试接缝已经写入。
6. 门禁一准备完成时，必须明确领域术语、可观察范围、目标产品、最高层级真实用户入口、可观察成功结果、风险要求的失败或恢复路径、公开测试接缝、纵向票据、固定基线、工作树、分支、流程等级、证据和阻塞项；同时读取 `spec.md` 和全部 `issues/*.md`，核对命名、状态、顺序、阻塞、可观察范围和测试接缝。任何产物缺失、空白或不一致时立即停止并保留门禁一恢复位置；全部有证据后，在“核心摘要”中完整展示当前门禁`门禁一——开始开发`，并取得用户的明确授权以执行当前门禁动作。
7. 门禁一内容完整且取得明确当前授权后进入实施；该授权在实施、验证及失败恢复期间持续有效。需求或测试接缝改变时返回需求路由。完成条件是进入实施的证据和授权均可复核。
