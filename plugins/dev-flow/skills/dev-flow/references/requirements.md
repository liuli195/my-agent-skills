# 需求

仅在执行需求路由和`门禁一——开始开发`时加载此参考文档。

## MUST — 必须依赖

- 当前阶段必须可读并实际使用 `subagent-policy`（子代理策略）、`codebase-design`（代码架构）、`grill-with-docs`（带文档拷问）、`domain-modeling`（领域建模）、`to-spec`（转为规格）和 `to-tickets`（转为票据）。普通 `grilling`（拷问）不能替代 `grill-with-docs`；缺少、不可读或无法核验任一依赖时，停在需求阶段。
- Full（完整）路径必须先使用经 `subagent-policy` 校验的只读 Architect（架构师），并要求其读取和使用 `codebase-design`；随后当前会话必须读取并实际使用 `grill-with-docs`、`domain-modeling`、`to-spec` 和 `to-tickets`。主代理不得以自有分析或子代理自报替代这些证据。
- Fast（快速）可以复用当前会话已满足的证据，但必须逐项核验：可复现失败检查、已验证根因、既是现有公开测试接缝又是最高层级真实用户入口的位置、一个纵向切片、无未解决需求，并且不含 Full 风险。范围扩大、出现第二个独立切片，或涉及安全、权限、数据、迁移、发布、机器状态、跨系统或破坏性风险时，改用 Full（完整）。已有单一纵向票据时，`to-tickets` 只验证无需拆分，不制造重复票据。
- 任一必需证据缺少、不可读、未实际使用或无法核验，不能进入实施；应报告阻塞项并停在需求阶段。

## 流程编排

1. 只读证明当前仓库根目录、已登记 Git（版本管理）工作树、有名称的非 `main` 功能分支、干净起始状态和固定验证基线；记录工作树、分支、票据顺序和真实阻塞项。首次确认前不写入、不创建或切换工作树/分支、不发布需求变更。完成条件是全部证据可由只读检查复核。
2. 选择 Flow Level（流程等级）。Fast（快速）只在当前会话逐项具备其必需证据且没有安全、权限、数据、迁移、发布、机器状态、跨系统或破坏性风险时使用；否则，**Full（完整）**是其他情况的默认等级，并在门禁一记录等级和证据。两种等级都保留两次确认、TDD（测试驱动开发）红灯到绿灯、固定基线且 `checked` 非空的 Build and Verify（构建与验证）、真实入口冒烟和独立审查。完成条件是所选等级及其证据可复核。
3. Full（完整）路径按顺序委派经策略校验的 Architect（架构师）读取并使用 `codebase-design`，核验其源码位置、不确定项、可观察结果、范围和最高层级公开测试接缝；随后当前会话读取并使用 `grill-with-docs`、`domain-modeling`、`to-spec`、`to-tickets`。只解决仍未确定的一个决策或领域术语；范围、模块、接口、接缝、风险或流程等级变化时，回到整体设计并重新取得所需证据。每一步的完成条件是对应依赖确实读取、结果实际使用且可由当前会话记录核验。
4. Fast（快速）路径逐项核验并复用当前会话证据；使用 `to-spec` 固定可观察契约和最高层级公开接缝，使用 `to-tickets` 验证已有请求是否已经是一个可独立观察的纵向票据。已有单一纵向票据时只记录“无需拆分”，不生成重复票据；若不是单一纵向票据才拆分。完成条件是票据、接缝、可观察结果和证据均不重复且可核验。
5. 门禁一准备完成时，必须明确领域术语、可观察范围、目标产品、最高层级真实用户入口、可观察成功结果、风险要求的失败或恢复路径、公开测试接缝、纵向票据、固定基线、工作树、分支、流程等级、证据和阻塞项。只有这些项目全部有证据支持，才在“核心摘要”中完整展示`门禁一——开始开发`并判断当前上下文是否明确授权该动作。

6. 两个门禁都不得要求固定回复措辞或固定口令，也不得要求用户逐字回复“开始开发”或“规格与交付”。完整展示当前门禁内容后，上下文中对当前门禁动作的明确授权（例如“确认”“可以”“继续实施/交付”）即可；沉默、提问、修改需求、仅确认某个细节、以前门禁授权或含义不清不能视为授权，不确定时停留并澄清。门禁一授权只进入实施阶段；门禁二授权才覆盖规格应用和选定交付动作。完成条件是当前授权语义已明确且未把非授权上下文误判为授权。
7. 门禁一确认后，确认在实施、验证及其失败恢复期间持续有效；需求或接缝改变时返回本需求路由。门禁一未授权或必需证据不完整时，停止在需求阶段，不能进入实施。完成条件是只进入已授权且证据完整的下一阶段。
