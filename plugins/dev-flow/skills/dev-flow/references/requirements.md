# 需求

仅在执行需求路由和`门禁一——开始开发`时加载此参考文档。

## MUST — 必须依赖

- Full（完整）路径必须加载、读取并实际使用 `subagent-policy`（子代理策略）、`codebase-design`（代码架构）、`grill-with-docs`（带文档拷问）、`domain-modeling`（领域建模）、`to-spec`（转为规格）和 `to-tickets`（转为票据）。
- Fast（快速）路径必须加载、读取并实际使用 `to-spec` 与 `to-tickets`。

## 流程编排

1. 只读证明仓库根目录、Git（版本管理）工作树登记、有名称的非 `main` 功能分支、干净起始状态和固定验证基线；记录工作树、分支、票据顺序和真实阻塞项。门禁一授权前保持只读并沿用当前工作树和分支。完成条件是全部证据可由只读检查复核。
2. 选择 Flow Level（流程等级）。Fast（快速）使用当前会话逐项具备的可复现失败检查、已验证根因、现有公开测试接缝、最高层级真实用户入口、一个纵向切片和无未解决需求的证据；安全、权限、数据、迁移、发布、机器状态、跨系统或破坏性风险，以及范围扩大或第二个独立切片，使用 Full（完整）。**Full（完整）**是其他情况的默认等级，并在门禁一记录等级和证据。
3. Full（完整）路径由当前会话按顺序委派并核验经策略校验的 Architect（架构师）实际使用 `codebase-design`（代码架构）的结果，核验源码位置、不确定项、可观察结果、范围和最高层级公开测试接缝；随后当前会话加载、读取并实际使用 `grill-with-docs`、`domain-modeling`、`to-spec`、`to-tickets`，记录每项依赖的来源、产出和实际使用。每一步的完成条件是对应证据可由当前会话复核。
4. Fast（快速）路径逐项核验并复用当前会话证据；使用 `to-spec` 固定可观察契约和最高层级公开测试接缝，使用 `to-tickets` 验证已有请求是否是一个可独立观察的纵向票据。已有单一纵向票据时沿用现有票据；其余请求按纵向票据结果拆分。
5. 门禁一准备完成时，必须明确领域术语、可观察范围、目标产品、最高层级真实用户入口、可观察成功结果、风险要求的失败或恢复路径、公开测试接缝、纵向票据、固定基线、工作树、分支、流程等级、证据和阻塞项。全部项目有证据支持后，在“核心摘要”中完整展示`门禁一——开始开发`；完整展示当前门禁内容后，取得用户的明确授权以执行当前门禁动作；语义不明确时停留澄清。
6. 门禁一内容完整且取得明确当前授权后进入实施；该授权在实施、验证及失败恢复期间持续有效。需求或测试接缝改变时返回需求路由。完成条件是进入实施的证据和授权均可复核。
