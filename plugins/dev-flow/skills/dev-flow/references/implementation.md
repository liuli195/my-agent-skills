# 实施与验证

仅在`门禁一——开始开发`获得确认后加载此参考文档。

## MUST — 必须依赖

- 当前阶段必须可读并实际使用 `subagent-policy`（子代理策略）、`tdd`（测试驱动开发）、`build-and-verify`（构建与验证）和 `code-review`（代码审查）。缺少、不可读或无法核验任一依赖时，停在实施阶段。
- 开发与验证必须保持门禁一确认的同一 Git（版本管理）工作树、同一非 `main` 分支和固定基线；可写调用严格串行，不能创建或切换工作树/分支。首次委派前按 `subagent-policy` 验证宿主配置；每次委派都只选择该次校验允许的宿主原生角色和适配器。没有经过验证的适配器，在委派前停止。
- 功能、缺陷和集成行为必须使用 `tdd` 红灯到绿灯；文档或行为中性的配置只使用最小相关检查。正式验证唯一使用 `build-and-verify`，且结果必须为 `status: passed`、`checked` 非空；跳过或空结果不算通过。

## 流程编排

1. 在任何写入前重新只读核对已登记工作树、同一有名称的非 `main` 分支、干净状态和固定基线；失败即停止。完成条件是工作树和分支身份、基线及主工作树未变化均有证据。
2. 对每个纵向票据，从门禁一绑定的目标产品最高层级真实用户入口开始：先写并运行最小可观察失败检查，再做最小实施修改，再重跑同一检查确认转绿，然后进入下一票据。红灯到绿灯检查、最终冒烟和行为验收均使用同一入口；已批准票据不变，需求或接缝变化立即返回需求阶段。完成条件是每个票据都有可观察红证据、绿证据和范围归属。
3. 严格按票据顺序实施；需要子代理时，首次委派前按 `subagent-policy` 校验宿主配置，随后每次从该次校验允许的角色和适配器中选择，并在单一已验证目标工作树中派发。返回报告不等于完成：主代理必须检查实际文件、差异、提交、分支、工作树和票据证据。完成条件是派发符合已验证契约且实际结果满足票据；校验失败或实际结果不符时停在实施阶段。
4. 阅读并使用 `build-and-verify`，运行 `build-and-verify verify --project <current-worktree> --base <fixed-baseline>`；只接受 `status: passed` 且 `checked` 非空的结果，并把固定基线之后的实际差异、预期干净状态和主工作树未变化作为证据。完成条件是正式验证结果可复核。
5. 通过门禁一绑定的目标产品入口执行最终真实入口冒烟，覆盖主要成功路径以及门禁一确认的风险所要求的失败或恢复路径；原始且已脱敏的事件、输出、退出码和 Git（版本管理）前后状态留存为证据，内部测试不能替代冒烟。完成条件是同一入口的行为验收和冒烟均通过。
6. 在固定基线上使用 `code-review` 执行独立审查，范围限定为实际差异和必要上下文；解决阻塞性发现后重跑受影响的检查和冒烟，并只审查修复差异。完成条件是不存在未解决的阻塞性审查发现。
7. 当工作树、分支和基线正确，差异只包含已批准票据，所有红绿检查通过，Build and Verify 为 `passed` 且 `checked` 非空，真实入口冒烟和行为验收通过，限定审查无阻塞项时，加载[规格与交付](delivery.md)并准备门禁二。检查或审查失败时，在同一门禁一授权下恢复失败步骤，不重新请求开始开发授权。
