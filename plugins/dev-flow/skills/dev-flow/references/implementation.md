# 实施与验证

仅在`门禁一——开始开发`获得确认后加载此参考文档。

## MUST — 必须依赖

- 当前阶段必须加载、读取并实际使用 `subagent-policy`（子代理策略）、`tdd`（测试驱动开发）、`build-and-verify`（构建与验证）和 `code-review`（代码审查）。

## 流程编排

1. 在任何写入前重新只读核对已登记的同一 Git（版本管理）工作树、同一非 `main` 分支、干净状态和固定基线；开发与验证期间沿用该工作树、分支和基线。首次委派前按 `subagent-policy` 验证宿主配置和适配器。完成条件是工作树、分支、基线及主工作树未变化均有证据。
2. 对每个纵向票据，从门禁一绑定的目标产品最高层级真实用户入口开始：先写并运行最小可观察失败检查，再做最小实施修改，再重跑同一检查确认转绿，然后进入下一票据。红灯到绿灯检查、最终冒烟和行为验收均使用同一入口；需求或接缝变化时返回需求路由。完成条件是每个票据都有可观察红证据、绿证据和范围归属。实施、返工和审查修复均不得修改或提交 `myspec/specs/`；规格候选只能保存在目标工作树 `.local/spec-work/`。
3. 严格按票据顺序实施；可写调用严格串行。需要子代理时，首次委派前按 `subagent-policy` 校验宿主配置，随后每次从该次校验允许的角色和适配器中选择，并在单一已验证目标工作树中派发。返回报告作为线索，主代理检查实际文件、差异、提交、分支、工作树和票据证据。主代理验收每次实施、返工或审查修复返回的实际文件、提交与差异时，发现已跟踪或未跟踪的正式规格路径即判定 `REWORK_REQUIRED`，不得接受票据。完成条件是派发符合已验证契约且实际结果满足票据。
4. 阅读并使用 `build-and-verify`，运行 `build-and-verify verify --project <current-worktree> --base <fixed-baseline>`；正式验证的完成条件是结果为 `status: passed` 且 `checked` 非空，并且固定基线之后的实际差异、预期干净状态和主工作树未变化均有证据。
5. 通过门禁一绑定的目标产品入口执行最终真实入口冒烟，覆盖主要成功路径以及门禁一确认的风险所要求的失败或恢复路径；保留原始且已脱敏的事件、输出、退出码和 Git（版本管理）前后状态作为证据。完成条件是同一入口的行为验收和冒烟均通过。
6. 在固定基线上使用 `code-review` 执行独立审查，范围限定为实际差异和必要上下文；解决阻塞性发现后重跑受影响的检查和冒烟，并只审查修复差异。完成条件是不存在未解决的阻塞性审查发现。
7. 当工作树、分支和基线正确，差异只包含已批准票据，所有红绿检查通过，Build and Verify（构建与验证）为 `passed` 且 `checked` 非空，真实入口冒烟和行为验收通过，限定审查无阻塞项时，先运行固定基线后的正式规格差异检查：依次执行 Git（版本管理）命令 `git diff --name-only <fixed-baseline> -- myspec/specs/` 和 `git ls-files --others --exclude-standard -- myspec/specs/`。任一命令失败即停止。任一结果非空时逐项列出提前写入的文件，停留实施阶段，不准备门禁二，也不自动创建回退提交；结果均为空才可加载[规格与交付](delivery.md)并准备门禁二。检查或审查失败时，在同一门禁一授权下恢复失败步骤。
