# Retro To Issues

把对话历史转成去重后的 issue tracker（问题跟踪器）候选项，然后只在用户审阅后写入。

本技能只记录问题。使用本技能时，不修复代码、配置、工作流或外部工具；除非用户明确开启单独的修复任务。

## 流程

1. 读取仓库上下文。
   - 如果当前存在仓库，先读取它的 agent instructions（代理指令）或链接规则，再起草输出。
   - 遵守目标仓库的语言、术语、标签体系和 issue 格式。
   - 如果要写入、评论、重开或调整 GitHub issue，读取目标仓库的问题分流规则；没有仓库规则时使用本技能内置的问题分流契约。
   - 如果没有仓库规则，使用简洁 Markdown 和用户要求的语言。

2. 恢复会话事实。
   - 优先使用当前对话。
   - 如果用户要求跨会话回忆，或当前上下文不足以还原事实：
     1. 平台提供会话历史查询能力时，查询当前项目的相关历史；
     2. 否则请用户补充缺失事实。
   - 只在需要时补充相关本地证据：PR 或 issue 编号、命令、错误文本、状态名、日志、状态文件或工具输出。
   - 不确定项标记为不确定。不要编造根因。

3. 过滤、追溯根因和合并。
   - 先以用户明确指定的复盘范围为准。用户未明确排除时，开发、PR、发布和本地同步是必须分别检查的基线；用户指定了其他流程或范围时必须一并检查，不能用这四个基线阶段替代用户范围；用户明确限定只复盘某些范围时不得擅自扩张。
   - 对每个具体缺陷继续追问其流程根因，例如任务切分、测试时机、真实环境反馈、验证边界、人工恢复或规则冲突。
   - 具体缺陷已经修复，不等于流程根因已经解决；只有具体缺陷和底层流程问题都已持久解决时才排除。
   - 只有当底层系统性问题仍存在时，才保留临时绕过项。
   - 合并根因相同的问题观察，不要用多个表面症状重复建项。

4. 分类。
   - 阻断：流程停止，或需要人工介入。
   - 效率：流程成功，但需要过多等待、token 使用、重复 review（审查）、handoff（交接）或机械操作。
   - 规则冲突：行为与已记录的仓库规则冲突。

5. 路由候选问题。
   - 由当前仓库的代码、配置、文档、自动化、CI 或工作流导致的问题，路由到当前仓库。
   - 由外部工具、外部技能、插件、服务或上游运行时导致的问题，默认不路由到当前仓库。
   - 对外部问题，如果目标仓库没有明确给出，先询问用户是否提交到上游，以及使用哪个仓库。
   - 如果路由仍不明确，在扫描或写入前停止，并只问一个简短问题。

6. 审阅前先去重。
   - 使用可用的 GitHub 查询能力扫描每个目标仓库的全部 issue；使用 `gh` CLI（命令行工具）时运行：
     `gh issue list --state all --limit 1000 --json number,title,state,labels,url,body`
   - 如果没有可用的 GitHub 查询能力或认证，停在候选表格，不写入。
   - 先在本地搜索可能重复项，再读取可能匹配的 issue 和评论。
   - 此步骤只读。不要创建、评论、重新打开、关闭、编辑或打标签。
   - 如果存在 open（未关闭）的同主题 issue，必须添加复现/上下文评论，禁止新建issue。
   - 如果 closed（已关闭）issue 以同一根因复现，必须重新打开并添加复现/上下文评论，禁止新建 issue。
   - 只有在不存在同主题 issue，或根因/验收标准有实质差异时，才可以创建新 issue。

7. 动态优先级评估。
   - 生产/发布不可用、数据丢失、安全风险 → P0
   - 流程停止或需人工介入，无绕过方案 → P1
   - 流程可完成但代价过高 → P2
   - 瑕疵或不便，有绕过方案 → P3
   - 最近 7 天内被报告/复现 ≥ 3 次 → 提升 1 级（上限 P0）
   - 最近一次报告/复现已超过 14 天 → 降低 1 级（下限 P3，P0 自动衰减豁免）
   - 输出时标注：
       - 基线级别 + 调整后级别 + 调整原因（复现次数/衰减）
       - 例："P2 → P1（复现 3 次/7 天）"
       - 例："P0（衰减豁免，30 天未复现但保持 P0）"

8. 给用户审阅
   - 创建或评论 issue 前，必须向用户展示去重后的候选表格。
   - 必填列：问题编号、类别、优先级、详细解释、建议解决方案、triage、建议 GitHub 动作、目标仓库。
   - 说明已经扫描了哪些目标仓库，以及找到了哪些可能匹配项。
   - 用户确认前，不写入 GitHub。

9. 写入已确认记录
   - 如果动作为“创建新 issue”，使用本技能内置的新问题正文契约组织正文。
   - 如果动作为“评论已有 issue”，只写新的上下文或复现，不使用新问题正文契约。
   - 如果仓库使用 category（类别）、state（状态）、priority（优先级）这类标签角色，分别只应用一个。
   - 如果标签冲突，或缺少3类必需标签中的任何一种，必须停止并询问，禁止继续流程。

10. 验证和清理
   - 重新读取已创建或更新的 issue，确认状态、标签和 URL。
   - 删除为扫描或 issue 正文创建的本地临时文件。
   - 返回最终表格，附 GitHub 链接，并说明跳过或不确定的项目。

## 问题分流契约

没有仓库规则时，使用以下标准 triage（问题分流）值：

- `needs-triage`
- `needs-info`
- `ready-for-agent`
- `ready-for-human`
- `wontfix`

写入前检查：

- category（类别）、state（状态）、priority（优先级）各只能有一个值；
- 缺少任何一类必需值或存在冲突时，停止并询问用户；
- 目标仓库另有规则时，以仓库规则为准。

## 新问题正文契约

创建新 issue 时使用以下最小结构：

```markdown
### 问题
说明观察到的行为及其影响。

### 证据
列出已确认的复现、错误文本、日志或相关链接。

### 建议解决方案
说明建议的处理方向，不把未验证推测写成根因。

### 验收标准
- [ ] 可验证的完成条件

### 补充信息
记录优先级依据、不确定项和相关问题。
```

## 输出契约

- 简洁、具体。
- 使用目标仓库要求的语言和风格。
- 用户可见表格和新 issue 正文里保留实现建议。
- 重复 issue 的评论只写复现/上下文；除非用户明确要求，否则不写解决方案细节。
- 禁止记录密钥、token、私人凭据或个人数据。
